## C1. 墙钟可以拆成「有效工作 + 空转」两部分

**数字**（2026-09-23 修正为采样跨度口径）：`cap4_hc 202.8 + 16.1 = 218.9`（采样跨度，墙钟 213.0）；`foyer_hc 250.1 + 47.4 = 297.5`（墙钟 291.3）；`cap1 340.0 + 193.6 = 533.6`（墙钟 527.4）。各 run 的跨度比墙钟长约 6 分钟，是采样器早于第一个请求启动造成的。
**对照**：11 条静态 + 9 条 Foyer，全表一致
**反例检查**：两条臂各自证明两项独立——`default`（无控制）把空转压到 11.4%（−13.8 分钟）
但忙时涨 11.1 分钟、墙钟只快 2.7 分钟；`foyfix_hc`（全关节流）反过来，空转涨 129 分钟
而忙时降 5.4 分钟。（此前这里用的是 `bres`，它的干净重跑后两个分量同向下降，不再构成反例。）
**路径**：`scripts/frontier.py`；空转从 `metrics.csv` 的 `sglang:num_running_reqs == 0` 段累加

**状态：可用。** 注意措辞——这是**分解**，不是"模型"。

## C2. 步时间可以被两个独立方法测到，且两者排序一致

**数字**（反推 / 逐请求）：

```
cap4_hc   29.0 / 25.7 ms        cap5   35.9 / 31.2 ms   ← 两个方法都判异常
cap3_hc   28.0 / 24.6 ms        bres_r2 29.5 / 24.8 ms   ← 干净重跑后不再异常
cap2      26.9 / 22.8 ms        hz1    28.5 / 24.6 ms
foyer_hc  28.2 / 23.8 ms
```

**方法一** = busy 时间 × **busy 期间条件**在跑均值 ÷ 产出 token（从 `metrics.csv` + `steps.jsonl`）。⚠ 2026-09-23 修正：原来用的是全时段均值，等于把空转采样也算进去，τ 系统性偏低一个 busy 占比（cap1 从 28.8 变 18.5）
**方法二** = 逐请求 `(total_duration_ms − first_token_ms) / (output_len_actual − 1)`

**系统性差 8–16%，排序完全一致。**
**反例检查**：这正是审计要查的——如果两者不相关，C2 就该删。它们相关。
**⚠ 未解决**：`metrics.csv` 里 `itl_p50/p90`、`e2e_p50`、`ttft_p50` **全是空的**，
引擎侧的延迟指标从未被采集。**方法二是替代品，不是引擎直采。**

**状态：可用，但必须写成"两个导出量互相印证"，不能写成"引擎实测步时间"。**

## C3. 引擎空转是结构性的，占墙钟 7.4%–36.3%

**数字**：`cap4 10.4% / cap3 14.0% / foyer_hc 15.9% / bres_r2 13.9% / cap2 18.4% / cap1 36.3%`（`decomp.csv`）
段长：中位 5–10 s，p90 20–25 s，最长 366–386 s
**成因**：会话在 `tool_wait` 期间不发请求 + 存活会话只有 ~2 个
**对照**：并发越低空转越多（cap1 36.3% → cap4 7.4%），单调
**反例检查**：`default` 把空转压到 11.4%（全表第六低）却只快 2.7 分钟 → **证明"填空转"本身不产生收益**，这条主张必须带上这个反例
**路径**：`metrics.csv` 的 `num_running_reqs == 0` 连续段累加

**状态：可用。必须同时报 `default` 的反例，否则会被误读成"填上就能快"。**
