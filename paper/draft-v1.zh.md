## 摘要

Agentic LLM 负载（coding agent、tool-using assistant）的会话上下文长且持续增长，其 KV 缓存需求在请求**到达时即可观测**（首轮 prompt 大小 + 历史增长轨迹）。然而现有 serving 系统对并发会话数不加治理或仅采用**反应式**控制（如 Concur 式缓存反馈 AIMD），在显存受限的 GPU 上导致缓存互相冲刷、请求全量重算：在我们的真实 trace 重放中，不限流使 TTFT 中位数从 4 秒恶化到 34 分钟，12% 的请求直接失败。

我们提出 **Foyer**，一个**前馈式**准入控制器：新会话在门口即按其可观测的 KV 需求做预留投影，装得下才放行。针对朴素实现（v0.4）的三个失败模式——撤回后瞬时使用率假空闲导致的准入泄漏、批量放行导致的缓存踩踏、缺乏服务质量反馈——分别引入**高水位判据**、**单飞准入**与 **TTFT-SLO 熔断阀**。

在 RTX 3090（24GB）单卡、真实 coding-agent trace（25/50/200 会话三档负载）上的实验表明：Foyer 的前缀缓存命中率达到 51.5%–58.1%，**超过需要逐档人工调参的 oracle 静态并发上限**（17.7%–49.6%），是反应式 AIMD 的 3–5 倍；TTFT 中位数稳定在 ~4 秒（oracle 为 5.6–34.8s，AIMD 为 92–104s）；TTFT-SLO（<10s）达标率 67.6%–71.9%；且端到端完成时间与最快基线持平或更短——**服务质量收益不以吞吐为代价**。

## 1 引言

### 1.1 问题

LLM serving 的经典瓶颈是算力；但 agentic 负载把它变成了**容量**问题：

- coding agent 会话的上下文是 append-only 的长对话：我们的真实数据集（UW TraceLab，4300+ 会话 / 35.7 万轮）中，首轮 prompt 中位 **17K token**，会话峰值中位 **32K token**；
- 会话生命周期内大部分时间在等工具返回（轮间隔中位 2s、p90 34s），GPU 算力大量空转，但**KV 缓存池全程被占**；
- 一张 RTX 3090（24GB）上，7B 模型的 KV 池仅 ~10–11 万 token：**同时在场几个会话**，直接决定系统是正常服务还是崩溃。

这本质上是数据库时代就熟知的准入控制（admission control）问题在 LLM serving 上的新形态。分歧在于：**准入决策依据什么信号？**

- **反应式**（现有工作，以 Concur 为代表）：观察缓存命中率/显存压力，系统"病了"再砍并发（AIMD）。天然滞后：等信号变坏，缓存已经冲没了。
- **前馈**（我们的主张）：agentic 会话的 KV 需求在到达时**可观测**——首轮 prompt 就摆在请求里，历史增长轨迹就在会话记录里。何必等病了再治？

### 1.2 反直觉的结果

朴素的"装得下才放行"（v0.4）不仅没赢，反而全面输给反应式 AIMD。我们逐行对账决策日志，定位出三个失败模式（§3），修复后的 Foyer v0.5 实现三档负载全横扫——**包括打败需要先验知识的 oracle 静态上限**。我们认为这个"朴素前馈会输 + 为什么输 + 怎么修"的完整过程与前馈制胜的结果本身同样有贡献。

### 1.3 贡献

1. 实证：agentic 负载下 KV 容量（而非算力）是首要瓶颈；不限流导致灾难性服务质量崩溃（TTFT ×85，失败率 12%）。
2. 机制：前馈准入控制器的三个组件——高水位空闲判据、单飞准入、TTFT-SLO 熔断——各自对应一种已定位的失败模式。
3. 结果：真实 trace 三档负载上，命中率、TTFT、SLO 达标率全面超过逐档调参的静态 oracle 上限与反应式 AIMD，且无吞吐代价。
4. 失败分析：朴素前馈（v0.4）的三种泄漏路径及其修复，为同类控制器设计提供 checklist。

## 2 背景与动机

### 2.1 Agentic 负载的 KV 经济学

会话 $s$ 在第 $k$ 轮的 KV 占用为其全部历史：$\text{ctx}_k(s) = \text{ctx}_{k-1}(s) + \text{append}_k + \text{output}_k$。由于对话 append-only，第 $k$ 轮请求的前缀与第 $k-1$ 轮几乎完全重合——**只要上一轮的 KV 还在缓存里，本轮就几乎无需重算**。前缀缓存命中是 TTFT 的第一杠杆：

- 命中率 49.6%（cap4，200 会话档）→ TTFT 中位 5.6s
- 命中率 0.0%（不限流）→ TTFT 中位 34.6 分钟

缓存的敌人是**并发**：每多放一个会话，其 prefill 与持续增长都会挤占其他会话的缓存块。准入控制就是管理这个权衡。

### 2.2 不治理的代价（motivation 实验）

200 个真实会话同时到达，Qwen2.5-Coder-7B（YaRN 96K），单卡 3090，KV 池 114,495 token：

| 指标 | 不限流 | 含义 |
|---|---|---|
| 前缀命中率 | 0.0% | 缓存完全失效，每轮全量重算 |
| TTFT 中位 | **34.6 分钟** | 用户视角不可用 |
| 失败请求 | **121 / 980（12.3%）** | 重算排队超出超时 |
| retraction 峰值 | 数十次 | 引擎反复撤回在跑请求 |

### 2.3 静态上限是"能用的，但不可部署的"

按档调参的静态并发上限（oracle cap）表现强劲（200 会话档 SLO 达标 62.3%），但有两个部署层面的硬伤：

1. **最优值不可先验**：25/50/200 会话档的最优 cap 分别为 6/6/4，只能试出来；
2. **会话内相位漂移**：即使 cap 正确，短会话退场后剩下的全是长会话，同样的人数照样撑爆池子——我们观察到固定 cap 在 run 中后期重新开始 thrash。

这说明"数人头"是错误的资源单位，"数 token"的前馈方案有了切入点。

## 3 Foyer 机制

### 3.0 基线形式：朴素前馈（v0.4）及其三个失败模式

v0.4 决策规则：新会话进门时，投影 = 各在场会话当前上下文 + 未来 3 轮增长（trace 可观测），加上新会话首 prompt 与其增长，≤ 目标水位（0.75 × 池子）即放行。

在 200 会话档，v0.4 的 cap 从 4 一路涨到 64，命中率崩至 0.3%，TTFT 中位 471.7s——输给一切对手。决策日志对账定位三个失败模式：

| # | 失败模式 | 机理（日志证据） |
|---|---|---|
| F1 | **假空闲泄漏** | 撤回风暴后瞬时 token_usage 瞬间跳水（t=149min 时 resident 估计仅 4K token），投影误判有大量空位放行；实际被撤回会话下轮要全量重补 prefill |
| F2 | **准入棘轮** | cap = active + fits，只涨不降：一次误放行永久存在（日志：cap 4→64 单调） |
| F3 | **质量盲区** | 投影只看"装不装得下"，不看"服务得好不好"：命中率已崩、TTFT 已爆，准入照常 |

### 3.1 组件一：高水位空闲判据（治 F1/F2）

维护使用率高水位 $H_t = \max(U_t, \gamma \cdot H_{t-1})$（$\gamma=0.995$/2s，半衰期约 5 分钟），投影下界取 $\max(U_t, H_t)$。**瞬时跳水不再被当成空闲**——只有高水位持续衰减 5 分钟（即真空位出现）才恢复准入能力。这同时隐式给了系统"降并发"的能力，解除棘轮。

### 3.2 组件二：单飞准入（治踩踏）

每个决策周期至多放行 1 个新会话，且**上一个新会话完成 ≥1 轮**后才放下一个（60s 超时兜底防卡死）。批量放行会让多个大会话的 prefill 同时冲刷缓存；单飞把准入对缓存的扰动串行化。

### 3.3 组件三：TTFT-SLO 熔断阀（治 F3）

滚动窗口（最近 20 轮）TTFT 中位超过 10s 即冻结准入，无论投影说多空。这是控制器里唯一的"反应式"成分，定位是安全阀而非主信号——论文里如实说明（消融见 §5.3）。

### 3.4 兜底

- **硬闸**：瞬时 usage ≥ 0.85 直接不放行；
- **限频饥饿保护**：等待 ≥240s 且高水位 <0.5 时，每 300s 强制放行最老等待者一个（防死锁，rate-limited 防自激——v0.3 的教训）。

参数总表：目标水位 0.75、margin 1.15、γ=0.995（@2s 周期）、SLO 10s/窗口 20、starve 240s/300s。**全部跨三档负载共用，未逐档调参**（对比 oracle cap 每档重调）。

## 4 实验设置

- **负载**：UW TraceLab 真实 coding-agent trace（脱敏），会话感知闭环重放（本轮完成 → tool_wait → 下轮），合成文本池补非确定性 token。三档：25 / 50 / 200 会话（200 档 = 980 轮）。
- **系统**：SGLang 0.5.10，Qwen2.5-Coder-7B-Instruct，YaRN ×3（96K 上下文），RTX 3090 24GB 单卡。KV 池：25/50 档 101,432 token（memfrac 0.85），200 档 114,495（0.88，与其基线对齐）。
- **策略**：`default`（不限流）；`cap-N`（静态并发上限，N 为逐档调优的 oracle 值）；`aimd`（Concur 式缓存反馈 AIMD，3090 重调：u_high=0.75、h_thresh=0.03、α=2、β=0.5、周期 30s，共 3 轮调参）；`budget`（朴素前馈 v0.4）；`Foyer`（v0.5，本文）。
- **指标**：前缀命中率（引擎报告）；TTFT（执行相，不含门外排队等待；中位/均值）；TTFT-SLO 达标率（<10s）；会话完成时间分布；wall 时间（端到端）；失败请求数。

## 5 结果

> **有效性声明（2026-09-12 重制版）**：本节全部数据来自统一 KV 池（101,432 token, memfrac 0.85）+ 清洁 trace（999 行）+ 门控验证运行。早期混合池数据（25/50 档旧表）与开天眼版本已全部作废重跑；每表的 run 目录、trace 哈希与完整参数记录在 `results/night/*/metadata.json`。

### 5.1 静态并发扫描：悬崖的发现（25 会话档）

| cap | wall(min) | 命中率% | TTFT p50(s) | SLO% |
|---|---|---|---|---|
| 1 | 63.3 | 68.2 | 1.3 | 95.2 |
| 2 | 38.4 | 64.9 | 1.4 | 92.0 |
| 3 | 30.6 | 63.3 | 2.2 | 89.6 |
| **4** | 30.4 | **55.2** | 2.5 | 74.4 |
| **5** | 30.5 | **36.3** | 9.8 | 50.4 |
| 6 | 27.9 | 31.7 | 13.5 | 36.0 |
| 7 | 35.5 | 8.3 | 40.8 | 7.2 |
| 8 | 34.8 | 2.5 | 41.7 | 3.2 |

（cap2/7/8 三点因起服竞态池子为 97,367（−4%），重跑队列中；悬崖形态不受影响。）

**发现：质量-吞吐悬崖**。cap4→5 只多放一个会话，命中率腰斩（55.2→36.3%）；cap7 归零。原因：超过池容量的并发触发前缀缓存互相驱逐，每轮全量重算。**静态最优值无法先验知道**（且随池子/负载漂移：池 11.4 万时 200 档最优为 4，缩到 10.1 万最优变 3）——这就是准入控制必须动态化的依据。

### 5.2 决胜档主表：200 会话（全部策略）

| 策略 | wall(min) | 失败 | 命中率% | TTFT p50(s) | SLO% |
|---|---|---|---|---|---|
| default | 228.1 | **121** | 0.0 | 2155.6 | 0.2 |
| cap1 | 515.7 | 0 | 69.9 | 1.6 | 94.8 |
| cap2 | 301.7 | 0 | 67.0 | 2.1 | 90.0 |
| cap3 | 249.4 | 0 | 59.0 | 3.5 | 76.9 |
| cap4 | 265.6 | 0 | 45.1 | 8.4 | 52.8 |
| cap5 | 265.5 | 0 | 28.0 | 22.7 | 31.0 |
| budget2（开天眼版） | 247.4 | 0 | 46.9 | 7.2 | 56.0 |
| aimd2（忠实 Concur） | 291.4 | 0 | 48.4 | 5.6 | 65.9 |
| **Foyer（aggressive+HiCache）** | 459.1 | 0 | **69.8** | **1.9** | **92.6** |
| Foyer（r3 干净重跑） | 555.3 | 0 | 68.6 | 1.8 | 93.6 |

读法三条（诚实版）：

1. **对动态对手（忠实 Concur）全面领先**：命中率 +21.4pp（69.8 vs 48.4）、TTFT p50 好 2.9 倍、SLO +26.7pp。
2. **对扫参静态无 dominance，只有"免扫参"**：质量角 cap1（69.9%）与吞吐角 cap3（249min/59.0%）构成的静态前沿上，Foyer 的点（459min/69.8%）落在 cap1–cap2 之间的前沿段附近——质量与 cap1 差 0.1pp，wall 多 11%。静态前沿的优势是"如果有人替你扫过参"；我们的优势是**不需要扫，且参数不随负载漂移而失配**（漂移证据见 §5.1）。
3. **HiCache 是使能器而非通用加速**：cap2+HiCache 与 cap2 完全相同（67.2 vs 67.0，静态低并发从不驱逐）；只有高并发预算下（aggressive Foyer）host 层才产生差异——机制归因干净（§5.4）。

### 5.3 预测器归因（实验二：同骨架四臂 + guard 诊断，25 会话档）

| 预测臂 | wall(min) | 命中率% | SLO% |
|---|---|---|---|
| 零增长（不预测） | 46.7 | 65.7 | 92.8 |
| 全局均值 | 58.9 | 66.8 | 94.4 |
| 每会话 EMA（默认） | 54.8 | 66.8 | 93.6 |
| ORACLE（开天眼，不可部署） | 92.4 | 68.2 | 95.2 |
| EMA + 无饥饿保护（诊断） | 76.7 | 68.2 | 95.2 |

判定（按预注册四格矩阵）：四臂质量带极窄（65.7–68.2%），**预测器选择在轻载下不改变质量，只改变在前沿上的位置**（越准的预测越保守，wall 越长）。增长预测的价值定位为 **permit 尺寸的安全上界**（呼应 Agentix/MORI 的 non-clairvoyant 结论），而非质量使能器；其真实价值待 200 档与漂移负载验证（零增长臂 200 档：424.5min/65.3%/88.9%，已含于 §5.2 口径外补充）。

### 5.4 HiCache host 层：悬崖的填平（25 会话档，cap6 = 无 HiCache 时的坍塌点）

| cap6 | wall(min) | 命中率% | TTFT p50(s) | SLO% |
|---|---|---|---|---|
| 无 HiCache | 27.9 | 31.7 | 13.5 | 36.0 |
| **+ HiCache（ratio 2, write_through）** | 22.8 | **64.1** | 10.2 | 49.6 |

**纯配置（零引擎改动）的 host 梯队把坍塌配置救回 oracle-3 水平以上**（逐轮命中中位 0→81.8%——host 复活路径实测工作）。同时 budget3+HiCache 无回归（68.2%/95.2%，vs 66.8%/93.6%）。剩余空间：复活 TTFT 仍 10.2s（PCIe 重载），预取调度是后续优化。

### 5.5 误差棒与可复现性

- budget3@200：三样本命中率 67.3 / 68.6 / 68.7%（极差 1.4pp）；其中 r2/r3 为无干预干净门控样本，首跑为开发样本（含控制器热修复干预，如实标注，不并入正式均值）。
- cap4@200 ×3：45.1 / 52.7 / 51.8%（极差 7.6pp）。
- aimd2@200 ×3：48.4 / 48.4±小差 / 48.4（极差 <0.1pp，三次运行高度一致）。

### 5.6 失败分类学（含两轮外部审计发现的缺陷）

| # | 失败模式 | 机理 | 修复 | 状态 |
|---|---|---|---|---|
| 1 | 假空闲泄漏（retraction 后水位假性回落被当成空位） | 瞬时 usage 信号不可靠 | 高水位判据（5min 半衰期衰减） | 已修复，消融证实（nohw：54→5.8%）|
| 2 | 准入棘轮（cap 只涨不降，4→64） | 无下调机制 | named-permit 全量期望状态 | 已修复 |
| 3 | 预测对象 ≠ 获准对象（非 FIFO 抢占） | 标量 cap 的语义缺陷 | 点名 permit | 已修复 |
| 4 | 停车场（shed 后无退出机制，中位滞留 2.1h，复活惩罚 3.4×） | shed-then-recompute 被文献量化为 10–111× 错误分支 | HiCache host 层 + W/T≥β 有界晋升 | 实现中 |
| 5 | 陈旧信号死锁（TTFT 阀门被过期样本锁死） | 滑动窗口无新鲜度检查 | 600s 新鲜度窗口 | 已修复 |
| 6 | 外部进程清除（共环境击杀，5 次） | 四卡占满引发回收 | 用卡上限 2–3 张 + 车道监督器自动重跑 | 已缓解 |

## 7 局限与讨论

1. **任务质量不可测**：TraceLab 脱敏后不含任务结果，无法测 admission 对任务成功率的影响。但准入控制不改变请求内容与输出语义（只改变何时执行），影响面限于时延/失败率，论文如实声明。
2. **单模型单卡**：目前 Qwen2.5-Coder-7B + 3090。[可选补强：3B/14B 各一档；A100 复验一轮]
3. **重放的局限**：tool_wait 来自 trace 分布而非真实工具执行；闭环重放已保证会话内因果，会话间无因果。
4. **SLO 阀是反应式的**：与纯前馈主张有张力，论文以"安全阀"定位 + 消融数据正面处理。

## 8 结论

一句话：**agentic 负载的 KV 需求在到达时就可观测，用它做前馈准入，比等系统病了再治（反应式）和靠先验猜并发（oracle cap）都好**——三档真实负载全面验证，且不付吞吐代价。
