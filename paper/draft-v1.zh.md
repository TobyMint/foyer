## 摘要

Agentic LLM 负载（coding agent、tool-using assistant）的会话上下文长且持续增长。在单张 24GB 卡上，7B 模型的 KV 池只装得下几个会话，于是**并发会话数直接决定系统是正常服务还是崩溃**：不加治理时，会话互相驱逐、每轮全量重算——在 200 会话档上，命中率 **1.6%**、TTFT 中位 **29.6 分钟**、SLO 达标率 **3.0%**（`pois200_default`；同一 trace 上 cap2 是 67.7% / 2.2 秒 / 89.5%）。

本文测量这类负载的一个结构性事实，并据此重新定位准入控制的设计问题。

**(1) 墙钟对并发是台阶，不是曲线。** 主表 14 条策略上，引擎并发低于 1.4 的墙钟全部落在 297–340 分钟、且**彼此不单调**（并发 2.04 的 321.8 分钟比 1.99 的 310.5 还慢）；1.4 以上的全部落在 257–267 分钟。**中间没有过渡带，因此不存在"最优并发值"可调。** 我们用第二个独立的量验证了这个台阶——聚合解码吞吐（由 `generation_tokens_total` 算出，与墙钟来自完全不同的原始数据）：并发 ≥1.4 的一组吞吐高 20–26%，且分母（总生成 token）在 14 个 run 间只差 0.76%。台阶可分解为 `1.20× = 1.08×（忙占比）× 1.11×（忙时吞吐）`，即约一半是少空转、一半是批处理。

**(2) 台阶另一侧的收益是用 SLO 买的，不是免费的。** 那 ~14% 的墙钟对应 SLO 从 ~89% 掉到 55–62%（cap4 的 TTFT p50 是 7.2 秒）。因此 makespan 的无约束最优解**不可部署**，SLO 必须按约束而非目标处理。

**(3) 真问题是控制变量选错了。** 按会话侧的量做准入，会**系统性地高估引擎的真实占用**，我们测到两个独立来源：逻辑上下文之和比物理驻留 KV 高估 **~1.8×**（前缀共享），在飞会话数比引擎实际在跑的请求数高估 **~2.0×**（tool_wait），且后者比值随并发从 0.64 漂移到 0.38、**不是常数**。这解释了为什么按容量账本准入的控制器会过度保守、停在台阶边缘之前。

**Foyer** 是按第 (3) 条设计的准入控制器：只读引擎遥测的实测物理占用，不读会话台账。在 SLO ≥85% 的约束下，它是主表 13 条策略里最快的 [待补：与匹配基线的配对实验]。我们如实报告其边界：它的保守性在引擎并发 ~1.4 处是有代价的——批处理收益（+20%）大于它多保住的命中率（+20pp）所值的钱，因此它**不能**在无约束 makespan 上赢过 cap4，也不主张能赢。

此外我们给出：数据有效性守卫（§3.4，池子静默缩水会伪造出"质量退化 5.9pp"的假象）、失败分类学（§5.6，含两轮外部审计发现的缺陷）、以及三类到达过程下的对照（§5.8）。

[待补：匹配对实验（cap2+HiCache vs Foyer+HiCache，并发跑+换卡，见 `docs/three_paths_20260921.md` §决议）；cap3_fixed 定崖位；rl90fix/rl99fix 判决第 (3) 条]

## 1 引言

### 1.1 问题

LLM serving 的经典瓶颈是算力；但 agentic 负载把它变成了**容量**问题：

- coding agent 会话的上下文是 append-only 的长对话：我们的真实数据集（UW TraceLab 公开语料；本次导出核对的库内含 8,058 个会话 / 66.5 万轮）中，首轮 prompt 中位 **17K token**，会话峰值中位 **32K token**；
- 会话生命周期内大部分时间在等工具返回（轮间隔中位 2s、p90 34s），GPU 算力大量空转，但**KV 缓存池全程被占**；
- 一张 RTX 3090（24GB）上，7B 模型的 KV 池仅 ~10–11 万 token：**同时在场几个会话**，直接决定系统是正常服务还是崩溃。

这本质上是数据库时代就熟知的准入控制（admission control）问题在 LLM serving 上的新形态。分歧在于：**准入决策依据什么信号？**

- **反应式**（现有工作，以 Concur 为代表）：观察缓存命中率/显存压力，系统"病了"再砍并发（AIMD）。天然滞后：等信号变坏，缓存已经冲没了。
- **前馈**（我们的主张）：agentic 会话的 KV 需求在到达时**可观测**——首轮 prompt 就摆在请求里，历史增长轨迹就在会话记录里。何必等病了再治？

### 1.2 三个反直觉的结果

1. **朴素前馈会输**：最直接的"装得下才放行"（v0.4）不仅没赢，反而全面输给反应式 AIMD——逐行对账决策日志后我们定位出三种泄漏路径（§3.0），修复后才反超。
2. **命中率冠军不等于性能冠军**：我们的控制器一度在质量上并列第一、却比**逐档调参的静态**慢 52%。归因发现根因不在容量核算（余量参数），而在**我们自己为了安全加的机制**——高水位地板虚占了 29% 的预算，单飞准入把放行速率锁在"每分钟一个"（§5.7）。回收高水位地板并把预算重新定价后，完成时间下降 47%（单飞保留；地板修复后它的边际影响仅约 ±1 分钟）。
3. **保护是双向的**：同一批机制既在防错、也在收税。高水位地板防住了"读数假跳水"（真实故障）却同时虚占预算；主机层缓存（HiCache）救回了坍塌配置（cap6 命中率 31.7%→64.1%），但在我们的控制器上它同时让会话驻留更久、更久地占着预算（−3.2pp SLO 换 −23% wall）。**安全机制的代价必须被测量，而不是被假设。**

### 1.3 贡献（v2.0 重写：不再主张机制新颖性）

**统一口径：本文有两个贡献，都是"测量 + 由测量导出的设计规则"，不是新机制。**
（组会、周报、汇报均用这一套，不再拆成三条机制。）

**贡献 1（测量）：墙钟-并发关系是台阶，以及台阶的代价结构。**

- 台阶本身：14 条策略上，引擎并发 <1.4 与 ≥1.4 分成两簇，中间无过渡带（§5.9）。
- 独立验证：用聚合解码吞吐（另一个量、另一份原始数据）复现同一台阶，并通过
  "总生成 token 离散度 0.76%"的可比性闸门（§5.9）。
- 分解：`1.20× = 1.08×（忙占比）× 1.11×（忙时吞吐）`——一半少空转、一半批处理。
- 代价：台阶另一侧的 ~14% 墙钟对应 SLO 从 ~89% 掉到 55–62%（§5.2、§5.9）。

**贡献 2（设计规则）：控制变量必须取实测物理占用，不能取会话侧台账。**

会话侧的两个量都系统性高估引擎真实状态，且我们都测了：

```
逻辑上下文之和 → 物理驻留 KV      高估 ~1.8×   （前缀共享）
在飞会话数     → 引擎在跑请求数   高估 ~2.0×   （tool_wait），比值随并发 0.64→0.38 漂移
```

Foyer 是按这条规则实现的控制器（§3.1 的账本、§3.2 的挂起/复活作为实现手段）。
**其收益目前是条件性的**：在 SLO ≥85% 约束下它是最快的，但这一条依赖 §5.10 的
匹配对实验；若配对差不显著，贡献 2 降级为"一条测量得到的设计规则"，不含性能主张。

**明确不主张的（v1.1 曾主张，现已撤回）**：

| 撤回的主张 | 为什么 |
|---|---|
| 容量核算准入 + 命名许可 是新的 | ThunderAgent 已覆盖 |
| 状态保留式挂起 是新的 | MORI 用同一套 SGLang v0.5.10 + HiCache 覆盖 |
| 有界复活 是新的 | 等价于 HRRN（Brinch Hansen 1971） |

这三样**仍然实现在系统里、仍然在 §3 描述、仍然在实验里生效**，只是定位从
"创新点"降为"我们的控制器采用的既有技术"。**不要在摘要、引言、贡献列表或汇报里
再称它们为创新点。**

支撑性内容同样作为证据陈述，不列为贡献：数据有效性守卫（§3.4）、失败分类学（§5.6）、

## 2 背景与动机

### 2.1 Agentic 负载的 KV 经济学

会话 $s$ 在第 $k$ 轮的 KV 占用为其全部历史：$\text{ctx}_k(s) = \text{ctx}_{k-1}(s) + \text{append}_k + \text{output}_k$。由于对话 append-only，第 $k$ 轮请求的前缀与第 $k-1$ 轮几乎完全重合——**只要上一轮的 KV 还在缓存里，本轮就几乎无需重算**。前缀缓存命中是 TTFT 的第一杠杆：

- 命中率 45.1%（cap4，200 会话档）→ TTFT 中位 8.4s
- 命中率 0.0%（不限流）→ TTFT 中位 **40.3 分钟**

缓存的敌人是**并发**：每多放一个会话，其 prefill 与持续增长都会挤占其他会话的缓存块。准入控制就是管理这个权衡。

### 2.2 不治理的代价（motivation 实验）

200 个真实会话同时到达，Qwen2.5-Coder-7B（YaRN 96K），单卡 3090，KV 池 101,432 token：

| 指标 | 不限流 | 含义 |
|---|---|---|
| 前缀命中率 | 0.0% | 缓存完全失效，每轮全量重算 |
| TTFT 中位 | **40.3 分钟** | 用户视角不可用 |
| 失败请求 | **121 / 999（12.1%）** | 重算排队超出超时 |
| retraction 峰值 | 数十次 | 引擎反复撤回在跑请求 |

### 2.3 静态上限是"能用的，但不可部署的"

按档调参的静态并发上限（oracle cap）表现强劲——200 会话档最好的质量点 cap1 达 69.9% 命中率、94.8% SLO——但有两个部署层面的硬伤：

1. **安全值不可先验**：25 会话档上 cap3 仍有 64.9% 命中率，**只多放一个会话（cap4）就掉到 55.2%，cap5 掉到 36.6%**；最优值是多少、离悬崖有多远，只能靠全量扫描试出来。
2. **"最优"本身取决于目标与负载**：质量最优（cap1）、吞吐最优（cap3）与折中（cap2）在静态前沿上是三个不同的点；会话构成一旦变化（长会话占比、增长的快慢），同一个 cap 就落在不同位置。

这说明"数人头"是错误的资源单位，"数 token"的依据才是切入点。

## 3 Foyer 机制

### 3.0 机制演进：一条设计原则

**朴素前馈（v0.4）**：新会话进门时，投影 = 各在场会话当前上下文 + 未来 3 轮增长，加上新会话首 prompt 与其增长，≤ 目标水位（0.75 × 池子）即放行。它在 200 会话档的 cap 从 4 一路涨到 64、命中率崩至 0.3%、TTFT 中位 471.7s，输给一切对手。决策日志对账定位出三个失败模式：

| # | 失败模式 | 机理（日志证据） |
|---|---|---|
| F1 | **假空闲泄漏** | 撤回风暴后瞬时 token_usage 瞬间跳水（t=149min 时 resident 估计仅 4K token），投影误判有大量空位放行；实际被撤回会话下轮要全量重补 prefill |
| F2 | **准入棘轮** | cap = active + fits，只涨不降：一次误放行永久存在（日志：cap 4→64 单调） |
| F3 | **质量盲区** | 投影只看"装不装得下"，不看"服务得好不好"：命中率已崩、TTFT 已爆，准入照常 |

**v0.5 的三个保险**：针对 F1/F2 引入**高水位地板**（瞬时跳水不算空闲），针对踩踏引入**单飞准入**（每周期至多放行一个），针对 F3 引入 **TTFT-SLO 熔断阀**。**这三个保险在当时都是对的**——其时的准入不可撤销（并发上限只涨不跌，误放即永久超卖），所以"一次放一个、放完看一眼"是唯一理性做法。

**v3 的回收**：命名许可（§3.1）使准入变为**可撤销**——放错可以请出去。原先逼着我们极度谨慎的前提消失了，但两个保险没有被回收。§5.7 的自诊断量化了这笔遗留成本：**高水位地板虚占 29% 的准入预算、单飞准入把放行速率锁在约每分钟一个**，在 25 会话档的基线配置上合计多花 47% 的完成时间。回收后（地板关闭、预算重定价、单飞保留）完成时间从 62.1min 降到 33.0min。本文由此得到一条设计原则：

> **保护层的代价必须被测量；能力演进之后，旧保护必须被重新评估，否则它会从护栏变成天花板。**

### 3.1 容量核算准入

**账本**：控制器每周期（2s）维护一本显式账，放行判据为

$$m \cdot \Big[\sum_{i \in \mathcal{A}} (x_i + \hat{g}_i) + (x_s + \hat{g}_s)\Big] \le \rho \cdot C_{pool}$$

其中 $x$ 为会话的已知上下文（在场者取实测、新到者取首轮 prompt），$\hat g$ 为未来 $H$ 轮的增长估计（会话内 EMA 混合全局先验），$m$ 为会话级安全余量，$\rho$ 为池子预算系数。**不使用未来负载信息，也没有需要逐负载调整的并发参数。**

**命名许可**：控制器写下的不是标量并发数，而是**本周期允许运行的确切会话集合**；执行层按名字执行。计划的账 = 实际跑的人，超卖在结构上不可能（这同时修复了 F2 的根源：标量语义下的非 FIFO 抢占会让"计划放行"与"实际获准"错位）。

**保留的安全阀**（均针对真实故障，非默认保守）：瞬时占用硬闸；TTFT-SLO 熔断（唯一的反应式成分，定位为安全阀而非主信号）；限频饥饿保护（等待超时强制放行一位，防死锁）。**已回收的机制**：高水位地板（实测虚占 29% 的准入预算）。**单飞准入保留在主配置中**，但地板修复后已不再是瓶颈——关掉它只换到 +1.2pp 命中率、却慢 3%（§5.7 完整 A/B）。

### 3.2 状态保留式挂起

当准入需要收回容量时，被暂停会话的 KV **不丢弃**，而是下移至主机内存驻留（引擎原生分层缓存：`--enable-hierarchical-cache` 等纯配置开关，零引擎改动）；会话重新获准时按需装载回显存，**只需搬运、无需重算**（20K token 的 KV ≈1.1GB，PCIe Gen3 ×16 下装载约 0.1s 量级，而重算约 4.3s 量级——均为估算，直接测量在后续工作中）。

它的意义不只在省时间：**没有它，"暂停"就等于毁掉会话已有的工作**，准入控制只能拒绝、不能暂存；有了它，暂停成为可逆操作，准入控制才敢于激进。代价边界同样要如实说明：低并发时无驱逐、完全无效；在我们当前控制器上它以约 3pp 的质量换取 23% 的完成时间（§5.4）。

### 3.3 有界复活（设计，尚未验证）

被挂起的会话按优先级 $\Pi_i(t) = W_i(t)/T_i$ 降序接回，其中 $W_i$ 为自挂起起的等待时间，$T_i$ 为复活代价且**按 KV 所在层级定价**：KV 仍在主机层则 $T_i$ 为装载代价，已被丢弃则 $T_i$ 为重算代价——同等等待下，前者优先级高出约一个数量级。由于 $W_i$ 单调增长，等待有上界是可达的；实际实现需要一个显式的等待上限 $W_{max}$ 兜底（否则源源不断的"廉价"挂起会话可以无限插队）。复活占用容量时走与准入同一本账（同一份命名许可）。**本节为设计与分析，实现与实验验证列为后续工作。**

### 3.4 数据有效性守卫（工程前提）

准入预算是以 KV 池容量为物理前提的，因此**每次运行都必须核对池子**：引擎按起服时的空闲显存分配池，同一张卡上其他任务的残留会让池子静默缩水。我们的守卫做三件事：运行框架在起服后校验池子是否等于基准值，不符则重启重试、仍不符则中止该运行而不记录；运行登记表对异常池子的运行标警；论文的全部表格由 `scripts/make_tables.py` 从运行产物一键重建（含该校验），避免"表里的数字与实际运行对不上"。这套守卫在本项目中抓出过三处会伪造结论的池子缩水（其中一处曾伪造出"质量退化 5.9pp"的假象）。

## 4 实验设置

## 5 结果

> **有效性声明（2026-09-16 修订）**：本节数据全部来自统一 KV 池（101,432 token, memfrac 0.85）+ 清洁 trace + 门控验证运行。**池子即准入预算的物理前提，因此每一条 run 都必须核对池子**：SGLang 按起服时的空闲显存分配池，同一张卡上的其他任务会让池子静默缩水（实测出现 48,234 / 84,528 / 97,367 三种缩水值），产出的数据看似正常却不可比。现已（a）在运行框架中强制校验池子、不符则重启重试、仍不符则中止该 run 而不记录；（b）登记表对异常池子的 run 标警；（c）受影响的 run 全部移入 `results/night/_invalid/` 并在本表中重跑。每表的 run 目录、trace 哈希与完整参数在 `results/night/*/metadata.json`，全部表格可由 `scripts/make_tables.py` 一键重建。

读法三条（诚实版）：

1. **对动态对手（Concur）全面领先**：命中率 +21.4pp（69.8 vs 48.4）、TTFT p50 好 2.9 倍、SLO +26.7pp。
2. **对扫参静态：质量角微占优，吞吐角是真实权衡**：与质量角 cap1（515.7min/69.9%）相比，Foyer（459.1min/69.8%）**同等质量下快 11%**，即略占优于静态前沿的质量端；但与吞吐角 cap2（301.7min/67.0%）相比，我们慢 52% 换 +2.8pp 命中——这是尚未消除的真实差距（成因与修复见 §5.7）。静态前沿的前提是"有人替你扫过参"；我们的优势是**不需要扫，且参数不随负载漂移而失配**（漂移证据见 §5.1）。
3. **HiCache 是使能器而非通用加速**：cap2+HiCache 与 cap2 完全相同（67.2 vs 67.0，静态低并发从不驱逐）；只有高并发预算下（aggressive Foyer）host 层才产生差异——机制归因干净（§5.4）。

### 5.3 预测器归因（实验二：同骨架四臂 + guard 诊断，25 会话档）

| 预测臂 | wall(min) | 命中率% | SLO% |
|---|---|---|---|
| 零增长（不预测） | 46.7 | 65.7 | 92.8 |
| 全局均值 | 58.9 | 66.8 | 94.4 |
| 每会话 EMA（默认） | 54.8 | 66.8 | 93.6 |
| ORACLE（开天眼，不可部署）⚠️ 实现有缺陷、作废（见下） | 92.4 | 68.2 | 95.2 |
| EMA + 无饥饿保护（诊断） | 76.7 | 68.2 | 95.2 |

判定（按预注册四格矩阵）：可解读的三臂（零增长 / 全局均值 / EMA）实测质量带极窄（65.7–66.8%），墙钟差异明显（46.7–58.9min）——**在轻载下，预测器选择不明显改变质量，主要改变墙钟**。但其**独立收益尚未证明**：EMA 相对零增长多花 17.4% 墙钟、仅多 1 个请求跨过 SLO 线（n=1）。把增长预测定位为 **permit 尺寸的安全上界**（呼应 Agentix/MORI 的 non-clairvoyant 结论）是**待验证假设**，不是结论。

⚠️ **oracle 臂（92.4min）的实现有缺陷，不得引用**：旧实现把会话全生命周期的 input+output 累加后恒定返回——既不随轮次衰减、也不受 H=3 轮窗口约束，且重复计入首轮 input。因此"**越准的预测越保守（wall 越长）**"这一单调性结论不成立，**已从本稿删除**。实现已重写为 `G*(t) = max(0, C(t+3) − C(t))`，**重跑尚未进行**（见文末待办）。其真实价值待 200 档与漂移负载验证（零增长臂 200 档 424.5min/65.3%/88.9% 属旧、未去节流配置，与 §5.2 修复配置不可直接比较）。

### 5.4 HiCache host 层：悬崖的填平（25 会话档，cap6 = 无 HiCache 时的坍塌点）

| cap6 | wall(min) | 命中率% | TTFT p50(s) | SLO% |
|---|---|---|---|---|
| 无 HiCache | 27.9 | 31.7 | 13.5 | 36.0 |
| **+ HiCache（ratio 2, write_through）** | 22.8 | **64.1** | 10.2 | 49.6 |

**纯配置（零引擎改动）的 host 梯队把坍塌配置救回 oracle-3 水平以上**（逐轮命中中位 0→81.8%——host 复活路径实测工作）。但在我们的控制器上它不是免费的：budget3+HiCache 为 42.0min/66.3%/90.4%，对比无 HiCache 的 54.8min/66.8%/93.6%——**快 23% 但命中 −0.5pp、SLO −3.2pp**（机制：KV 保活使会话驻留更久、更久地占着预算）。因此它的正确定位是**用少量质量换取激进准入的空间**，而非通用加速。剩余空间：复活 TTFT 仍 10.2s（PCIe 重载），预取调度是后续优化。

| # | 失败模式 | 机理 | 修复 | 状态 |
|---|---|---|---|---|
| 1 | 假空闲泄漏（retraction 后水位假性回落被当成空位） | 瞬时 usage 信号不可靠 | 曾用高水位地板；**后经自诊断回收**（其虚占 29% 预算，§5.7） | **机制已回收**——假空闲由 `max(引擎实测, 会话账本)` 双账本取严兜住 |
| 2 | 准入棘轮（cap 只涨不降，4→64） | 无下调机制 | named-permit 全量期望状态 | 已修复 |
| 3 | 预测对象 ≠ 获准对象（非 FIFO 抢占） | 标量 cap 的语义缺陷 | 点名 permit | 已修复 |
| 4 | 停车场（shed 后无退出机制，中位滞留 2.1h，复活惩罚 3.4×） | shed-then-recompute 被文献量化为 10–111× 错误分支 | HiCache host 层 + W/T≥β 有界晋升 | 实现中 |

### 5.7 自我诊断：瓶颈是准入节流，不是容量核算（2026-09-15）

§5.2 读法 2 指出我们比静态吞吐角慢 52%。会话完成时间分解显示，其中 **97% 是"在门口等待"**——于是我们沿控制器的决策日志逐项排查（每 2 秒一条，含账面各项分解）。

**诊断结论**：瓶颈不是容量核算的余量（m、ρ），而是两个 v0.5 时代的安全机制在 v3 中被继续沿用：

1. **高水位地板**（为防"读数假跳水"而设）：实测它平均虚增 22.4k token ≈ **预算的 29%**；85% 的决策周期里账本用的是地板推出的占用而非在场会话的真实上下文；结果是"门外有人排队、同时账面剩余 ≥30k（放一个会话所需）"的周期**仅占 14%**。
2. **单飞准入**（一次只放一个 + 等其完成首轮或 60 秒）：v0.5 时代准入不可撤销（并发上限只涨不跌，误放即永久超卖），故必须极其谨慎；v3 的 named permit 使准入可撤销后，该节流已冗余，但**未被回收**——这正是失败分类学中"保护层未随能力演进回收"的新条目。

**单变量 A/B（25 档，当前代码，同一负载与池子）**：

| 配置 | wall(min) | 命中率% | SLO% | 平均并发 |
|---|---|---|---|---|
| 基线（当前代码） | 62.1 | 67.7 | 95.2 | 1.03 |
| 关单飞准入 | 53.2 | 66.4 | 92.8 | 1.25 |
| 关高水位地板 | 41.8 | 65.0 | 92.8 | 1.87 |
| 准入预算 0.75→0.95 | 43.4 | 62.3 | 89.6 | 1.72 |
| **关地板 + 预算 0.95** | **33.0 / 33.9**（重复） | **64.4 / 64.4** | 92.8 / 89.6 | 2.28 / 2.42 |
| 关地板 + 关单飞 | 34.1 | 65.6 | 88.0 | 2.25 |

**结论**：① 主因是高水位地板——关掉它 wall 降 33%、并发由 1.03 升至 1.87，代价是命中率 −2.7pp（地板本质上在为"驱逐压力"定价，关掉它是把质量换成吞吐，每 1pp 命中换回约 12% 时间）；② 再叠加预算上探，wall 降至基线的 **53%**（−47%），且两次重复的命中率完全一致（64.4%）；③ 单飞在其中只占 −14%，且地板修复后基本不再咬人。**修复后的工作点落在静态前沿上（cap2–cap3 之间，质量略高于两点的连线）**，即"慢 52%"这一差距的大部分是自身保守配置造成、可通过机制回收，而非准入控制本身的固有代价。0.75 与 0.95 两个预算点、地板开关的交互，以及 200 档的验证，见后续实验。

**分解**：`1.20× = 1.08×（忙占比）× 1.11×（忙时吞吐）`——约一半少空转、一半批处理。
（脚本 `scripts/throughput_decomp.py` 一键复现，内置离散度闸门。）

**一个反例收窄结论**：`default` 引擎并发最高（1.69）、忙占比也高（88.6%），
吞吐却只有 39.6 tok/s——因为其命中率 1.6%，算力被 prefill 重算吃掉。
→ 判据是 **并发高 ∧ 命中率没崩**，不是并发高。

**一条对我们不利的**：在引擎并发 ~1.4 上，批处理收益（+20%）**大于**命中率损失
（+20pp）。cap4 命中率比 Foyer 低 20pp，吞吐仍高 14%。**Foyer 的保守不是
"以少量速度换质量"，是停在批处理拐点之前。** 这正是 §5.10 与 rl90fix/rl99fix
要判决的。

## 7 局限与讨论

**1. 机制新颖性不成立（最重要的一条，写在最前）**。容量核算准入+命名许可被
ThunderAgent 覆盖，状态保留式挂起被 MORI 用同一套 SGLang v0.5.10 + HiCache 覆盖，
有界复活等价于 HRRN。本文因此**不主张机制新颖性**（见 §1.3）。这一条必须主动
写出来，不能等审稿人指出。

**2. 主表是单 run，且关键比较跨天**。§5.9 主表 14 行全部 n=1，同 trace 上唯一
一对同条件重复是两个 cap≈4 测量（259.1 / 257.6，差 0.6%）。而摘要里那个"最快的"
主张所依赖的两个臂（Foyer+HC 297.6 @09-20 vs cap2 310.5 @09-15）**相隔五天**，
在共享机器上。我们实测邻居的 24 核任务可把墙钟拉大 17–25%。**§5.10 的匹配对
实验就是为了消除这一条**；在它落地前，摘要与 §1.3 中任何性能领先的主张都标注为
条件性的。[待补：配对结果]

**3. 保守性的代价是真实的，我们不掩饰**。在引擎并发 ~1.4 上，批处理收益（+20%）
大于命中率损失（+20pp）：cap4 命中率比 Foyer 低 20pp，吞吐仍高 14%（§5.9）。
所以 Foyer **不能**在无约束 makespan 上赢过 cap4，本文也不主张能赢。
它的位置是"在 SLO 约束下可行且最快的候选"，不是"全面更快"。

**4. 台阶级的崖位未被分辨**。崖被夹在引擎并发 (1.33, 1.44) 之间，中间没有观测点
（原因是主表那个 cap3 点被 runner 竞态污染、实际跑的是 cap4）。`cap3_fixed`
[待补] 是唯一能定住崖位的测量。这一条影响 §5.9 全部关于"台阶在哪"的量化表述。

**5. 任务质量不可测**：TraceLab 脱敏后不含任务结果，无法测准入对任务成功率的影响。
但准入控制不改变请求内容与输出语义（只改变何时执行），影响面限于时延/失败率。

**6. 单模型单卡**：目前 Qwen2.5-Coder-7B + 3090。§5.9 的台阶结论依赖
"KV 池只装得下几个会话"这一比例关系，换模型/换卡后台阶位置会移动，
台阶**是否存在**需要复验。[可选补强：3B/14B 各一档；A100 复验一轮]

**7. 重放的局限**：tool_wait 来自 trace 分布而非真实工具执行；闭环重放已保证
会话内因果，会话间无因果。

**8. 负载形态**：主力实验采用"全体同时到达"（flash crowd，与 Concur 的批离线评测
同制度）；§5.8 补充了泊松到达与真实测量到达，但三种形态绝对负载不同、
只可比相对位置。

## 8 结论

（v2.0 重写。v1.1 的结论把三个机制当作已证明的贡献，其中两个已被覆盖、
第三个等价于 HRRN，故不再成立。）

本文在显存受限单卡上测量 agentic serving 的并发治理，得到两个结论。

**其一：墙钟对并发是台阶，不是曲线。** 14 条策略上，引擎并发低于 1.4 的墙钟
全部落在 297–340 分钟且彼此不单调，1.4 以上的全部落在 257–271 分钟，中间没有
过渡带。这个台阶由两个独立的量复现——墙钟与聚合解码吞吐，来自不同的原始数据——
并可分解为约一半"少空转"、约一半"批处理"。它的代价也是可测的：那 ~14% 的墙钟
对应 SLO 从 ~89% 掉到 55–62%。因此 makespan 的无约束最优不可部署，**SLO 必须
按约束处理，而按约束处理后，"最优并发"这个提法本身就不成立**——台阶上没有最优点，
只有落在哪一侧。

**其二：控制变量必须取引擎实测的物理占用。** 会话侧的两个量都系统性高估引擎真实
状态，我们分别测到了：逻辑上下文之和比物理驻留 KV 高估 ~1.8×（前缀共享），
在飞会话数比引擎实际在跑的请求数高估 ~2.0×（tool_wait），且后者比值随并发从
0.64 漂移到 0.38、不是常数。按会话侧的量准入的控制器，因此**系统性地过度保守、
停在台阶边缘之前**——这解释了我们自己早先版本的全部性能差距来源。

**我们明确不主张机制新颖性。** 容量核算准入与命名许可已被 ThunderAgent 覆盖；
状态保留式挂起被 MORI 用同一套 SGLang v0.5.10 + HiCache 覆盖；有界复活等价于
HRRN。这些机制仍实现在我们的系统里并在实验中生效，但它们是既有技术，不是本文的
贡献。**本文的贡献是上面两条测量，以及由第二条导出的设计规则。**

一条方法学上的教训，与结论同等重要：**系统自己的安全机制会成为性能天花板，
而且它的代价必须被测量、不能被假设**——我们用量化归因证明，两个为早期缺陷设计的
保护层（高水位地板、单飞准入）压制了 47% 的完成时间，而它们的原始设计前提
（准入不可撤销）早已不复存在。同理，本文全部数据都受一个守卫保护：池子会因邻居
占卡而静默缩水，曾伪造出"质量退化 5.9pp"的假象。在共享、显存受限的真实设备上，
**"测量保护的代价、并随能力回收保护"与设计机制本身同样重要**。
