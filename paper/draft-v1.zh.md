## 摘要

Agentic LLM 负载（coding agent、tool-using assistant）的会话上下文长且持续增长。在单张 24GB 卡上，7B 模型的 KV 池只装得下几个会话，于是**并发会话数直接决定系统是正常服务还是崩溃**：不加治理时，会话互相驱逐、每轮全量重算——在 200 会话档上，命中率 **1.6%**、TTFT 中位 **29.6 分钟**、SLO 达标率 **3.0%**（`pois200_default`；同一 trace 上 cap2 是 67.7% / 2.2 秒 / 89.5%）。

本文测量这类负载的一个结构性事实，并据此重新定位准入控制的设计问题。

**(1) 并发买到的是并行度，不是效率。** 主表 14 条策略上，引擎并发低于 1.4 的墙钟全部落在 297–340 分钟、且**彼此不单调**（1.11 的 321.8 比 1.04 的 310.5 还慢）；1.4 以上的全部落在 257–271 分钟；**中间 (1.33, 1.44) 一个观测点都没有**。逐请求的直接测量（`steps.jsonl` 的每请求解码时长）显示：**每个请求自己的解码速率不随并发上升，是持平的**（并发 1→2 为 0.95×，36.4 → 34.6 tok/s；会话内配对中位 0.95–0.97）。聚合吞吐随并发上升，只因为**同时在飞的请求更多**。由此墙钟近似正比于并发的 −1/2 次方（预测比值 1.19，实测 1.21）——**即数据支持一条平滑单调的曲线，不支持台阶**。

> ⚠ **本文不主张"台阶/相变"。** 逐请求速率随并发不升反降（见上），聚合吞吐近似
> 线性的并发 × 速率，因此墙钟应当是**平滑单调**的。我们看到的"两簇"更可能只是
> 在 (1.33, 1.44) 处**没有采样**，而不是那里存在不连续。`cap3_fixed` 落在缺口正中。

**(2) 高并发那一簇的收益是用 SLO 买的，不是免费的。** 那 ~14% 的墙钟对应 SLO 从 ~89% 掉到 55–62%（cap4 的 TTFT p50 是 7.2 秒）。因此 makespan 的无约束最优解**不可部署**，SLO 必须按约束而非目标处理。

**(3) 真问题是控制变量选错了。** 按会话侧的量做准入，会**系统性地高估引擎的真实占用**，我们测到两个独立来源：逻辑上下文之和比物理驻留 KV 高估 **~1.8×**（前缀共享），在飞会话数比引擎实际在跑的请求数高估 **~2.0×**（tool_wait），且后者比值随并发从 0.64 漂移到 0.38、**不是常数**。这解释了为什么按容量账本准入的控制器会过度保守、停在低并发那一簇里。

**Foyer** 是按第 (3) 条设计的准入控制器：只读引擎遥测的实测物理占用，不读会话台账。在 SLO ≥85% 的约束下，它是主表 13 条策略里最快的 [待补：与匹配基线的配对实验]。我们如实报告其边界：它停在低并发簇，因此**不能**在无约束 makespan 上赢过高并发的静态档（cap4），本文也不主张能赢——代价就是那一档的墙钟差，没有别的东西可回收。

此外我们给出：数据有效性守卫（§3.4，池子静默缩水会伪造出"质量退化 5.9pp"的假象）、失败分类学（§5.6，含两轮外部审计发现的缺陷）、以及三类到达过程下的对照（§5.8）。

[待补：匹配对实验（cap2+HiCache vs Foyer+HiCache，并发跑+换卡，见 `docs/three_paths_20260921.md` §决议）；cap3_fixed 定崖位；rl90fix/rl99fix 判决第 (3) 条]

## 1 引言

### 1.1 问题

LLM serving 的经典瓶颈是算力；但 agentic 负载把它变成了**容量**问题：

- coding agent 会话的上下文是 append-only 的长对话：我们的真实数据集（UW TraceLab 公开语料；本次导出核对的库内含 8,058 个会话 / 66.5 万轮）中，首轮 prompt 中位 **17K token**，会话峰值中位 **32K token**；
- 会话生命周期内大部分时间在等工具返回（轮间隔中位 2s、p90 34s），GPU 算力大量空转，但**KV 缓存池全程被占**；
- 一张 RTX 3090（24GB）上，7B 模型的 KV 池仅 ~10–11 万 token：**同时在场几个会话**，直接决定系统是正常服务还是崩溃。

这本质上是数据库时代就熟知的准入控制（admission control）问题在 LLM serving 上的新形态。分歧在于：**准入决策依据什么信号？**

- **反应式**（现有工作，以 Concur 为代表）：观察缓存命中率/显存压力，系统"病了"再砍并发（AIMD）。天然滞后：等信号变坏，缓存已经冲没了。
- **前馈**（我们的主张）：agentic 会话的 KV 需求在到达时**可观测**——首轮 prompt 就摆在请求里，历史增长轨迹就在会话记录里。何必等病了再治？

### 1.2 四个反直觉的结果（v2.0：第 4 条是本文贡献 2 的来源）

1. **朴素前馈会输**：最直接的"装得下才放行"（v0.4）不仅没赢，反而全面输给反应式 AIMD——逐行对账决策日志后我们定位出三种泄漏路径（§3.0），修复后才反超。
2. **命中率冠军不等于性能冠军**：我们的控制器一度在质量上并列第一、却比**逐档调参的静态**慢 52%。归因发现根因不在容量核算（余量参数），而在**我们自己为了安全加的机制**——高水位地板虚占了 29% 的预算，单飞准入把放行速率锁在"每分钟一个"（§5.7）。回收高水位地板并把预算重新定价后，完成时间下降 47%（单飞保留；地板修复后它的边际影响仅约 ±1 分钟）。
3. **保护是双向的**：同一批机制既在防错、也在收税。高水位地板防住了"读数假跳水"（真实故障）却同时虚占预算；主机层缓存（HiCache）救回了坍塌配置（cap6 命中率 31.7%→64.1%），但在我们的控制器上它同时让会话驻留更久、更久地占着预算（−3.2pp SLO 换 −23% wall）。**安全机制的代价必须被测量，而不是被假设。**
4. **账本算得越准，可能越错——因为它算错了对象。**（**本文贡献 2 的来源**）
   我们专门造了一本容量账去替代"数人头"，它工作正常：准入时刻读到池子占用的 92%。
   但引擎遥测说实际只占 **52%**。**账本没有算错数，是数错了东西**——
   逻辑上下文之和不是物理驻留 KV（前缀共享让前者高估约 1.8×），
   在飞会话数不是引擎在跑的请求数（tool_wait 让前者高估约 2.0×）。
   于是控制器**忠实地执行了一个偏高两倍的预算**，系统性地过度保守。
   这条教训是全文的转折点：**要把利用率推向引擎的真实容量，就必须用引擎自己的测量，
   而不是用会话侧的台账去推**（§1.3 贡献 2、§5.11）。

- 核心证据（§5.11）：逐请求测量（每请求自己的解码时长，`steps.jsonl`）显示
  **每请求解码速率不随并发上升**：并发 1/2/3 分别为 36.4 / 34.6 / 33.4 tok/s，
  1→2 为 **0.95×**。聚合吞吐随并发上升**只因为同时在飞的请求更多**。

## 2 背景与动机

### 2.1 Agentic 负载的 KV 经济学

会话 $s$ 在第 $k$ 轮的 KV 占用为其全部历史：$\text{ctx}_k(s) = \text{ctx}_{k-1}(s) + \text{append}_k + \text{output}_k$。由于对话 append-only，第 $k$ 轮请求的前缀与第 $k-1$ 轮几乎完全重合——**只要上一轮的 KV 还在缓存里，本轮就几乎无需重算**。前缀缓存命中是 TTFT 的第一杠杆：

- 命中率 45.1%（cap4，200 会话档）→ TTFT 中位 8.4s
- 命中率 0.0%（不限流）→ TTFT 中位 **40.3 分钟**

缓存的敌人是**并发**：每多放一个会话，其 prefill 与持续增长都会挤占其他会话的缓存块。准入控制就是管理这个权衡。

### 2.2 不治理的代价（motivation 实验）

200 个真实会话同时到达，Qwen2.5-Coder-7B（YaRN 96K），单卡 3090，KV 池 101,432 token：

| 指标 | 不限流 | 含义 |
|---|---|---|
| 前缀命中率 | 0.0% | 缓存完全失效，每轮全量重算 |
| TTFT 中位 | **40.3 分钟** | 用户视角不可用 |
| 失败请求 | **121 / 999（12.1%）** | 重算排队超出超时 |
| retraction 峰值 | 数十次 | 引擎反复撤回在跑请求 |

### 2.3 静态上限是"能用的，但不可部署的"

按档调参的静态并发上限（oracle cap）表现强劲——200 会话档最好的质量点 cap1 达 69.9% 命中率、94.8% SLO——但有两个部署层面的硬伤：

1. **安全值不可先验**：25 会话档上 cap3 仍有 64.9% 命中率，**只多放一个会话（cap4）就掉到 55.2%，cap5 掉到 36.6%**；最优值是多少、离悬崖有多远，只能靠全量扫描试出来。
2. **"最优"本身取决于目标与负载**：质量最优（cap1）、吞吐最优（cap3）与折中（cap2）在静态前沿上是三个不同的点；会话构成一旦变化（长会话占比、增长的快慢），同一个 cap 就落在不同位置。

这说明"数人头"是错误的资源单位，"数 token"才是对的切入点。

**但本文还要再往前一步**：光把单位从"会话数"换成"token 数"并不够——**这个 token 数
必须来自引擎的实测，不能来自会话台账**。我们最初的账本正是"数 token"的，它依然把
利用率算高了一倍（§1.2 第 4 条），因为它数的是**逻辑上下文之和**而非**物理驻留 KV**。
单位选对了，**观测点**选错了，一样会错。这是 §1.3 贡献 2 的由来。

## 3 Foyer 机制

> §3.1 的**状态保留式挂起**（经 §3.2）被 **MORI** 用同一套栈（SGLang v0.5.10 +
> HiCache）覆盖；§3.3 的有界复活**等价于 HRRN**（Brinch Hansen 1971）；
> §3.1 的**"按 KV 容量准入"这一层**被 **ThunderAgent** 的聚合水位线覆盖
> （但**逐会话前瞻核算与命名许可未见覆盖**，见 §6.0.1）。
> 无论覆盖到哪一层，**本文都不据此主张新颖性**。完整出处见 §6.0。

> 到底怎么决策，§5 的全部数字无从复现；二是 **§3.0 那条设计原则是本文自己的**，
> 而它只能从这套机制的演进史里讲出来。
>
> **写作纪律**：本节任何一处都不要出现"我们提出/我们首次/新颖"这类措辞。
> 要引号引起来的对照关系在 §6.0 的表里。

### 3.0 机制演进：一条设计原则

**朴素前馈（v0.4）**：新会话进门时，投影 = 各在场会话当前上下文 + 未来 3 轮增长，加上新会话首 prompt 与其增长，≤ 目标水位（0.75 × 池子）即放行。它在 200 会话档的 cap 从 4 一路涨到 64、命中率崩至 0.3%、TTFT 中位 471.7s，输给一切对手。决策日志对账定位出三个失败模式：

| # | 失败模式 | 机理（日志证据） |
|---|---|---|
| F1 | **假空闲泄漏** | 撤回风暴后瞬时 token_usage 瞬间跳水（t=149min 时 resident 估计仅 4K token），投影误判有大量空位放行；实际被撤回会话下轮要全量重补 prefill |
| F2 | **准入棘轮** | cap = active + fits，只涨不降：一次误放行永久存在（日志：cap 4→64 单调） |
| F3 | **质量盲区** | 投影只看"装不装得下"，不看"服务得好不好"：命中率已崩、TTFT 已爆，准入照常 |

**v0.5 的三个保险**：针对 F1/F2 引入**高水位地板**（瞬时跳水不算空闲），针对踩踏引入**单飞准入**（每周期至多放行一个），针对 F3 引入 **TTFT-SLO 熔断阀**。**这三个保险在当时都是对的**——其时的准入不可撤销（并发上限只涨不跌，误放即永久超卖），所以"一次放一个、放完看一眼"是唯一理性做法。

**v3 的回收**：命名许可（§3.1）使准入变为**可撤销**——放错可以请出去。原先逼着我们极度谨慎的前提消失了，但两个保险没有被回收。§5.7 的自诊断量化了这笔遗留成本：**高水位地板虚占 29% 的准入预算、单飞准入把放行速率锁在约每分钟一个**，在 25 会话档的基线配置上合计多花 47% 的完成时间。回收后（地板关闭、预算重定价、单飞保留）完成时间从 62.1min 降到 33.0min。本文由此得到一条设计原则：

> **保护层的代价必须被测量；能力演进之后，旧保护必须被重新评估，否则它会从护栏变成天花板。**

### 3.1 容量核算准入

**账本**：控制器每周期（2s）维护一本显式账，放行判据为

$$m \cdot \Big[\sum_{i \in \mathcal{A}} (x_i + \hat{g}_i) + (x_s + \hat{g}_s)\Big] \le \rho \cdot C_{pool}$$

其中 $x$ 为会话的已知上下文（在场者取实测、新到者取首轮 prompt），$\hat g$ 为未来 $H$ 轮的增长估计（会话内 EMA 混合全局先验），$m$ 为会话级安全余量，$\rho$ 为池子预算系数。**不使用未来负载信息，也没有需要逐负载调整的并发参数。**

**命名许可**：控制器写下的不是标量并发数，而是**本周期允许运行的确切会话集合**；执行层按名字执行。计划的账 = 实际跑的人，超卖在结构上不可能（这同时修复了 F2 的根源：标量语义下的非 FIFO 抢占会让"计划放行"与"实际获准"错位）。

**保留的安全阀**（均针对真实故障，非默认保守）：瞬时占用硬闸；TTFT-SLO 熔断（唯一的反应式成分，定位为安全阀而非主信号）；限频饥饿保护（等待超时强制放行一位，防死锁）。**已回收的机制**：高水位地板（实测虚占 29% 的准入预算）。**单飞准入保留在主配置中**，但地板修复后已不再是瓶颈——关掉它只换到 +1.2pp 命中率、却慢 3%（§5.7 完整 A/B）。

### 3.2 状态保留式挂起

当准入需要收回容量时，被暂停会话的 KV **不丢弃**，而是下移至主机内存驻留（引擎原生分层缓存：`--enable-hierarchical-cache` 等纯配置开关，零引擎改动）；会话重新获准时按需装载回显存，**只需搬运、无需重算**。

> **⚠ 更正（2026-09-21）**：本节早先写"装载约 0.1s、重算约 4.3s，**均为估算，
> 直接测量在后续工作中**"。这是错的——**我们已经测过了**，而且测出的重算代价比
> 那个数大得多。实测（同一张卡、同一模型、同一上下文长度）：

```
搬运（PCIe）    0.005 ms/token   →  20K token ≈ 0.1 s
重算（prefill）  1.08 ms/token   →  20K token ≈ 21.6 s
比值            216×
```

> 那个 4.3s 的旧数字比实测小了约 5 倍，方向上是**偏乐观**的——它会让"重算"
> 显得比实际便宜。**凡是引用本节旧版本的地方都要按实测值改。**
>
> **这个比值还有一个本文依赖的推论**：搬运与重算的代价都随上下文长度线性增长，
> 上下文变长时**约掉了**，所以 216× 是个与上下文无关的常数，**不存在交叉点**。
> 因此"搬还是算"不是代价权衡，而是容量约束——这个推论是 §6.5 的一部分。

它的意义不只在省时间：**没有它，"暂停"就等于毁掉会话已有的工作**，准入控制只能拒绝、不能暂存；有了它，暂停成为可逆操作，准入控制才敢于激进。代价边界同样要如实说明：低并发时无驱逐、完全无效；在我们当前控制器上它以约 3pp 的质量换取 23% 的完成时间（§5.4）。

### 3.3 有界复活（设计，尚未验证）

被挂起的会话按优先级 $\Pi_i(t) = W_i(t)/T_i$ 降序接回，其中 $W_i$ 为自挂起起的等待时间，$T_i$ 为复活代价且**按 KV 所在层级定价**：KV 仍在主机层则 $T_i$ 为装载代价，已被丢弃则 $T_i$ 为重算代价——同等等待下，前者优先级高出约一个数量级。由于 $W_i$ 单调增长，等待有上界是可达的；实际实现需要一个显式的等待上限 $W_{max}$ 兜底（否则源源不断的"廉价"挂起会话可以无限插队）。复活占用容量时走与准入同一本账（同一份命名许可）。**本节为设计与分析，实现与实验验证列为后续工作。**

> **⚠ 这不是一个新规则（v2.0 新增）。** `Π_i = W_i / T_i` 的降序与
> `(W_i + T_i) / T_i` 的降序**完全相同**——除一个常数加项外两者是同一个序，
> 也就是 **HRRN（Brinch Hansen, 1971）**。把 `T_i` 按 KV 所在层级定价（主机层 =
> 装载、已丢弃 = 重算）只是给 HRRN 的服务时间赋了一个物理含义，**不改变它的性质**。
> 所以本节不作为贡献，也不要在摘要或贡献列表里出现。保留它的理由是：§3.2 的挂起
> 需要一个接回顺序，而这是实际实现里用的那个。

### 3.4 数据有效性守卫（工程前提）

准入预算是以 KV 池容量为物理前提的，因此**每次运行都必须核对池子**：引擎按起服时的空闲显存分配池，同一张卡上其他任务的残留会让池子静默缩水。我们的守卫做三件事：运行框架在起服后校验池子是否等于基准值，不符则重启重试、仍不符则中止该运行而不记录；运行登记表对异常池子的运行标警；论文的全部表格由 `scripts/make_tables.py` 从运行产物一键重建（含该校验），避免"表里的数字与实际运行对不上"。这套守卫在本项目中抓出过三处会伪造结论的池子缩水（其中一处曾伪造出"质量退化 5.9pp"的假象）。

## 5 结果

> **有效性声明（2026-09-16 修订）**：本节数据全部来自统一 KV 池（101,432 token, memfrac 0.85）+ 清洁 trace + 门控验证运行。**池子即准入预算的物理前提，因此每一条 run 都必须核对池子**：SGLang 按起服时的空闲显存分配池，同一张卡上的其他任务会让池子静默缩水（实测出现 48,234 / 84,528 / 97,367 三种缩水值），产出的数据看似正常却不可比。现已（a）在运行框架中强制校验池子、不符则重启重试、仍不符则中止该 run 而不记录；（b）登记表对异常池子的 run 标警；（c）受影响的 run 全部移入 `results/night/_invalid/` 并在本表中重跑。每表的 run 目录、trace 哈希与完整参数在 `results/night/*/metadata.json`，全部表格可由 `scripts/make_tables.py` 一键重建。

读法三条（诚实版）：

1. **对动态对手（Concur）全面领先**：命中率 +21.4pp（69.8 vs 48.4）、TTFT p50 好 2.9 倍、SLO +26.7pp。
2. **对扫参静态：质量角微占优，吞吐角是真实权衡**：与质量角 cap1（515.7min/69.9%）相比，Foyer（459.1min/69.8%）**同等质量下快 11%**，即略占优于静态前沿的质量端；但与吞吐角 cap2（301.7min/67.0%）相比，我们慢 52% 换 +2.8pp 命中——这是尚未消除的真实差距（成因与修复见 §5.7）。静态前沿的前提是"有人替你扫过参"；我们的优势是**不需要扫，且参数不随负载漂移而失配**（漂移证据见 §5.1）。
3. **HiCache 是使能器而非通用加速**：cap2+HiCache 与 cap2 完全相同（67.2 vs 67.0，静态低并发从不驱逐）；只有高并发预算下（aggressive Foyer）host 层才产生差异——机制归因干净（§5.4）。

### 5.3 预测器归因（实验二：同骨架四臂 + guard 诊断，25 会话档）

| 预测臂 | wall(min) | 命中率% | SLO% |
|---|---|---|---|
| 零增长（不预测） | 46.7 | 65.7 | 92.8 |
| 全局均值 | 58.9 | 66.8 | 94.4 |
| 每会话 EMA（默认） | 54.8 | 66.8 | 93.6 |
| ORACLE（开天眼，不可部署）⚠️ 实现有缺陷、作废（见下） | 92.4 | 68.2 | 95.2 |
| EMA + 无饥饿保护（诊断） | 76.7 | 68.2 | 95.2 |

判定（按预注册四格矩阵）：可解读的三臂（零增长 / 全局均值 / EMA）实测质量带极窄（65.7–66.8%），墙钟差异明显（46.7–58.9min）——**在轻载下，预测器选择不明显改变质量，主要改变墙钟**。但其**独立收益尚未证明**：EMA 相对零增长多花 17.4% 墙钟、仅多 1 个请求跨过 SLO 线（n=1）。把增长预测定位为 **permit 尺寸的安全上界**（呼应 Agentix/MORI 的 non-clairvoyant 结论）是**待验证假设**，不是结论。

⚠️ **oracle 臂（92.4min）的实现有缺陷，不得引用**：旧实现把会话全生命周期的 input+output 累加后恒定返回——既不随轮次衰减、也不受 H=3 轮窗口约束，且重复计入首轮 input。因此"**越准的预测越保守（wall 越长）**"这一单调性结论不成立，**已从本稿删除**。实现已重写为 `G*(t) = max(0, C(t+3) − C(t))`，**重跑尚未进行**（见文末待办）。其真实价值待 200 档与漂移负载验证（零增长臂 200 档 424.5min/65.3%/88.9% 属旧、未去节流配置，与 §5.2 修复配置不可直接比较）。

### 5.4 HiCache host 层：悬崖的填平（25 会话档，cap6 = 无 HiCache 时的坍塌点）

| cap6 | wall(min) | 命中率% | TTFT p50(s) | SLO% |
|---|---|---|---|---|
| 无 HiCache | 27.9 | 31.7 | 13.5 | 36.0 |
| **+ HiCache（ratio 2, write_through）** | 22.8 | **64.1** | 10.2 | 49.6 |

**纯配置（零引擎改动）的 host 梯队把坍塌配置救回 oracle-3 水平以上**（逐轮命中中位 0→81.8%——host 复活路径实测工作）。但在我们的控制器上它不是免费的：budget3+HiCache 为 42.0min/66.3%/90.4%，对比无 HiCache 的 54.8min/66.8%/93.6%——**快 23% 但命中 −0.5pp、SLO −3.2pp**（机制：KV 保活使会话驻留更久、更久地占着预算）。因此它的正确定位是**用少量质量换取激进准入的空间**，而非通用加速。剩余空间：复活 TTFT 仍 10.2s（PCIe 重载），预取调度是后续优化。

### 5.7 自我诊断：瓶颈是准入节流，不是容量核算（2026-09-15）

§5.2 读法 2 指出我们比静态吞吐角慢 52%。会话完成时间分解显示，其中 **97% 是"在门口等待"**——于是我们沿控制器的决策日志逐项排查（每 2 秒一条，含账面各项分解）。

**诊断结论**：瓶颈不是容量核算的余量（m、ρ），而是两个 v0.5 时代的安全机制在 v3 中被继续沿用：

1. **高水位地板**（为防"读数假跳水"而设）：实测它平均虚增 22.4k token ≈ **预算的 29%**；85% 的决策周期里账本用的是地板推出的占用而非在场会话的真实上下文；结果是"门外有人排队、同时账面剩余 ≥30k（放一个会话所需）"的周期**仅占 14%**。
2. **单飞准入**（一次只放一个 + 等其完成首轮或 60 秒）：v0.5 时代准入不可撤销（并发上限只涨不跌，误放即永久超卖），故必须极其谨慎；v3 的 named permit 使准入可撤销后，该节流已冗余，但**未被回收**——这正是失败分类学中"保护层未随能力演进回收"的新条目。

**单变量 A/B（25 档，当前代码，同一负载与池子）**：

| 配置 | wall(min) | 命中率% | SLO% | 平均并发 |
|---|---|---|---|---|
| 基线（当前代码） | 62.1 | 67.7 | 95.2 | 1.03 |
| 关单飞准入 | 53.2 | 66.4 | 92.8 | 1.25 |
| 关高水位地板 | 41.8 | 65.0 | 92.8 | 1.87 |
| 准入预算 0.75→0.95 | 43.4 | 62.3 | 89.6 | 1.72 |

**结论**：① 主因是高水位地板——关掉它 wall 降 33%、并发由 1.03 升至 1.87，代价是命中率 −2.7pp（地板本质上在为"驱逐压力"定价，关掉它是把质量换成吞吐，每 1pp 命中换回约 12% 时间）；② 再叠加预算上探，wall 降至基线的 **53%**（−47%），且两次重复的命中率完全一致（64.4%）；③ 单飞在其中只占 −14%，且地板修复后基本不再咬人。**修复后的工作点落在静态前沿上（cap2–cap3 之间，质量略高于两点的连线）**，即"慢 52%"这一差距的大部分是自身保守配置造成、可通过机制回收，而非准入控制本身的固有代价。0.75 与 0.95 两个预算点、地板开关的交互，以及 200 档的验证，见后续实验。

### 5.11 并发买到的是什么：逐请求解码速率的直接测量（v2.1 重写，**推翻了 v2.0 的结论**）

> **⚠ 本节在 2026-09-21 晚被推翻并重写。** v2.0 曾在这里报告一条"批处理曲线"，
> 称"速率随并发单调陡升、1→2 大致翻倍（33.5 → 62.3 tok/s）"，并把它作为贡献 1 的
> 核心证据。**那个结论是错的**，错在两处测量方法，而正确方法给出的方向**相反**。
> 下面先给正确结果，再说明错在哪里——**这一段要保留，它比结论本身更能说明问题**。

**正确测量**：`steps.jsonl` 记录了**每个请求**的 `submit_timestamp`、
`complete_timestamp`、`first_token_ms`、`output_len_actual` 与 `server_prefix_hit_rate`。
逐请求解码速率因此可以直接算：

```
decode_rate = (output_len - 1) / (total_duration - first_token_ms)
```

（首 token 在 TTFT 时刻到达，其余 token 摊在剩下的时间里。）并发取该请求
`[submit, complete]` 窗口内的 `num_running_reqs` 均值。只保留 `output_len ≥ 32`
的步——更短的轮次被 `finish_reason=length` 截断，其"速率"是截断位置的产物。

| 并发 | run 数 | 逐请求 tok/s | 命中率 | 未缓存 prompt | 上下文 |
|---|---|---|---|---|---|
| 1 | 6 | **36.4** | 52.3% | 14,580 | 33,554 |
| 2 | 6 | **34.6** | 55.2% | 10,937 | 26,739 |
| 3 | 5 | **33.4** | 64.5% | 7,182 | 21,840 |
| 4 | 1 | 28.7 | 57.2% | 8,628 | 20,554 |

**逐请求解码速率不随并发上升**（1→2 为 **0.95×**）。
六个 run 里五个单独看都是这个方向：cap2 42.2→40.5，Foyer 41.0→37.9→39.9，
t85 38.6→35.1，rl90 32.5→31.4→31.1，rl99 32.2→29.0→25.6→28.7。

**⚠ 这个结论经得起最强的一种混淆控制。** 上表有个反常识处：并发越高的桶，
**命中率越高、上下文越小**（与"并发高→驱逐多→命中率低"相反），说明分桶可能带
选择性——高并发时恰好轮到短上下文的轮次，那样"速率下降"就可能是分出来的而不是测出来的。
所以另做一次**会话内配对**：只看同一个会话，比较它**自己**在并发 1 与并发 2 下的轮次。
会话身份、上下文轨迹、前缀共享结构因此全部被控制掉：

```
4 个 run：157 对   均值 0.976   中位 0.966   四分位 0.840–1.121
6 个 run：231 对   均值 1.017   中位 0.952   四分位 0.806–1.118
```

**这里必须给两个 run 集合，因为均值不稳定。** 逐会话比值有长右尾，
**均值会随 run 集合从 0.976 翻到 1.017（跨过 1）**；**中位则稳定在 0.95–0.97**。
所以会话内配对支持的结论是**"中位数在 1 以下"**，读作：**没有增益**；
它**不足以**支持"速率随并发下降"——那个说法我们不再用。

**结论因此是**：跨截面均值 0.95、会话内中位 0.95–0.97，两者都指向
**"并发不带来每请求效率增益"**；而"下降"这个更强的说法被撤回。
四分位跨过 1.0 说明单会话噪声大，这也正是不能依赖均值的原因。

**所以并发买到的是并行度，不是效率。** 聚合吞吐随并发上升，是因为**同时在飞的请求
更多**，不是因为每个请求跑得更快——后者反而略慢。

**这个结论比原来的更强，而且把 §5.9 的解释钉死了。** 若聚合吞吐 ≈ 并发 × 逐请求速率，
而后者随并发缓慢下降，则墙钟近似正比于 并发的 −1/2 次方：

```
预测 (1.48 / 1.04)^0.5 = 1.19      实测墙钟比 310.5 / 257.6 = 1.21     吻合
```

即数据支持一条**平滑单调**的曲线。**这与 §5.9 观察到的"两簇 + 中间未采样"并不矛盾，
但它把天平明确压向"陡降"那一侧：没有台阶，我们只是没有在缺口处采样。**

**对 SLO 论证是加强**：既然并发不带来任何每请求效率增益，只带来延迟代价，
那"再挤一点并发就白赚吞吐"就不存在——SLO 与 makespan 的取舍是**纯粹**的，
这正是 §5.2 观测到的样子。

#### 5.11.1 原来的结论错在哪（保留，作为方法学教训）

v2.0 的曲线是从 `metrics.csv` 的 `generation_tokens_total` 差分算的，两个错误：

1. **采样粒度与计数器粒度不匹配。** 引擎的计数器**不是每次抓取都更新**，
   而是大约每 10 秒批量跳一次。按固定 5 秒采样做差，一次突发会整个落进
   恰好接住它的那个区间，中间的区间读数为零。
   实测同一份数据：按采样差分是 33.5 tok/s，按计数器更新周期是 45.1 tok/s
   ——**低并发档被系统性低估约 25%**，而比较恰恰发生在低并发档。
2. **没有排除 prefill/decode 混合。** 修正粒度之后，1→2 从 +86% 变成 +47%；
   而此时又发现 t=2 的周期**处理了按比例更少的 prefill**（prompt/gen 39.7 vs 44.5）、
   **命中率更高**（58.7% vs 53.1%）。也就是说那 +47% 里有一部分是
   "每个生成 token 摊到的重算更少"，不是批处理。

换成逐请求测量后，两个问题一起消失——**因为是同一个请求自己的时长，不涉及计数器粒度，
命中率就在同一行可以同时看**。而方向也随之翻转。

> **方法学教训（值得写进论文）**：一个看起来干净的"并发↑→速率↑"曲线，
> 可以完全由采样方法制造出来。**聚合计数器在低速率下的差分极不可靠**；
> 只要逐请求的原始记录存在，就该用它，而不是用聚合计数器反推。

### 6.0.1 关于 ThunderAgent：我们的判据与它的不是同一个东西

早先我们把机制①整体判为"被 ThunderAgent 覆盖"。**核过全文（§4.3 调度策略）
之后，这个判断过宽了。**

ThunderAgent 的准入/恢复门控是**聚合水位线加滞回**，原文判据为

```
C_total < Σ_{τ=R} c_p  +  Σ_{τ=A} c_q · f(t_q)
```

即把各程序当前的 token 数按阶段加权求和，与 λ·C_total 比较，λ_max/λ_min 构成滞回
窗口（其文中取值均为 1，理由是"程序间共享的 prompt 已隐含预留了足够缓冲"）。
它的 `c_p` 是**当前**占用，`f(t_q)` 是对 acting 阶段程序的时间衰减折扣。

**它确实追踪每程序的上下文长度**——但只用于"最短优先"的挂起排序，
**门控本身不做逐会话的需求评估，不评估候选者，也不比对剩余余量**。
我们**没有找到任何许可/租约/预留机制**（其协调靠一个全局等待队列加
Restore/Pause 两个原语）。

**本文的判据是**

```
m · [ Σ_{i∈A} (x_i + ĝ_i)  +  (x_s + ĝ_s) ]  ≤  ρ · C_pool
```

三处不同，且都是实质的：**① 含候选会话** `(x_s + ĝ_s)`（前瞻，不是回顾）；
**② 含预测增长** `ĝ`（ThunderAgent 的 `c_p` 是当前值）；**③ 命名许可**——
控制器写下的不是标量并发数而是本周期允许运行的**确切会话集合**。

**一个对我们有利的巧合**：ThunderAgent 那个聚合水位线判据，**正是我们 v0.5 里的
"高水位地板"**——而我们实测它虚占 29% 的准入预算、在 25 会话档上多花 47% 的
完成时间，然后**把它回收了**（§3.0、§5.7）。所以我们不是"做了同一件事"，
而是**测出了那个机制保守在哪、并换掉了它**。这恰好落在本文贡献 2 上。

> **⚠ 未获取的部分，不要当作已穷尽**：我们抓取到的全文**在附录之前被截断**
> （A.3、B.1、F.2–F.3 未取到），那里可能另有接口或协议细节。
> 因此这里的表述是"**在可获取的正文里未见覆盖**"，不是"**不存在**"。
> 投稿前应把附录读完再定稿这一段。

**所以本文不主张机制新颖性。** §3 仍然完整描述这些机制，因为它们是 Foyer 的实现；
但它们在本文里的身份是"既有技术"，不是贡献。**贡献是 §6.5 那两条。**

### 6.1 Agentic serving 的准入与并发控制

Concur（**ICML 2026**）用缓存命中率/显存压力做反馈，系统"病了"再砍并发（AIMD）。
它的结构性弱点是滞后：等信号变坏时缓存已经被冲掉了。我们在 §5.2 给了同控制律、
同硬件、重调参数后的忠实复现。

### 6.2 状态保留与分层缓存

InferCept 在工具调用处暂停会话、保留或换出 KV 以腾出内存给更多请求（报 1.6–2×）。
Talaria 做可主机恢复的 KV 加准入租约。MORI 做分层准入，报 99% 对 59–76% 的 GPU 利用率，
**且其技术栈与本文完全相同（SGLang v0.5.10 + HiCache）**——这一条是我们自查时发现的，
也是撤回机制②主张的直接原因。

**本文与它们的差别不在机制，在控制变量**：它们按请求声明的长度或会话侧的容量做核算，
我们按引擎遥测的**实测物理占用**（§6.5、§5.11）。

### 6.3 前缀缓存与 KV 管理

radix cache（SGLang）、PagedAttention（SOSP '23）、VAttention（**ASPLOS 2025**）、
CacheGen / CacheBlend 等——它们优化"缓存怎么用"，我们关心"谁有资格用"。

> 一个引用纪律：PagedAttention 原文**没有** "60–80%" 和 "<4%" 这两个常见数字
> （那是 vLLM 博客的），论文自己的数是 20.4%–38.2%；它确实报告了 20–26% 的
> 注意力核延迟开销。VAttention 是 ASPLOS 2025 不是 OSDI '25。

### 6.4 调度与排队理论

work-conserving 调度已达最大吞吐（Dai et al., 2504.07347）——**这一条直接约束了
本文的目标表述**：准入控制不可能增加吞吐，它唯一的正当理由是延迟/SLO 或缓存保全。
所以本文把目标写成 goodput-under-SLO，而不是"最大化吞吐"。

高占用是**可证不稳定**的（Ao et al., 2606.15555）：无驱逐不动点不稳定，最大驱逐
极限环渐近稳定，相对无驱逐均衡吞吐损失最高达 50%。⚠ 该文抓取到的 HTML 缺 §6 数值
实验与附录，其 GPU 佐证是"声称但未验证"，且为 101 页预印本、未见同行评议——
**不作为定论引用，只作为"往高占用推需要谨慎"的旁证。**

低占用与 SLO 崩塌可以并存（inference-fleet-sim, 2603.16054）：报告一个利用率约 30%
的集群仍然 TTFT P99 不达标，原因是 agent 服务时长跨 10–300 秒，"一个 300 秒的请求
会把一个 KV 槽位锁住五分钟"。**这一条对我们很不利，必须正面处理**：我们观测到引擎
停在池子的 52%，倾向读作"控制器过于悲观"；但这篇说明低占用也可能单纯来自服务时长
重尾，与账本无关。

**这两个效应同时存在，本文不假定是哪一种，而是把它们分解开**：
§5.11 的同 run 配对量的是"给定并发下引擎能跑多快"，与账本无关；
§5.9 的两簇则说明低并发簇确实吞吐更低。至于**为什么**控制器停在低并发簇，
是账本悲观还是重尾服务时长，需要另一次实验才能分开——我们如实标为未决，
不写进结论。（这是我们自己的一个未补的洞，`docs/STATE.md` 有记录。）

⚠ 该文是商业化路由器的关联方预印本，取其"低占用不等于安全"这一点，不引其模型。

### 6.5 本文的位置

**在被抢占的机制之外，有两个缺口确实是空的，本文占这两个：**

**（一）prefill 余量的内存代价，没有人量化过。** 现有工作把 headroom 当作计算/token
预算处理（Sarathi-Serve、TAPER、Sangam）；内存侧的 headroom 只以两种不成体系的形式
存在——SGLang 的 ×0.95/×0.85 粗暴折扣，以及 vLLM 里未被报告的 `transient_peak_headroom`。
佐证其真实性：vLLM #57475（`gpu_memory_utilization=0.98` 时 KV 分配通过但图捕获 OOM，
仅剩 120.88 MiB；0.97 正常）；SGLang #35777（cookbook 推荐 0.90–0.94，报告者试
0.94/0.90/0.85/0.88 全失败，只有 0.80 + 关 prefill graph 能启动）。

**（二）实测的 p99-对-KV-占用曲线不存在。** 我们 grep 了 12 个官方页面与多篇论文：
没有任何实测的 p99-vs-KV-占用曲线，也没有同行评议工作用 Kingman 或
Pollaczek–Khinchine 论证利用率上限。最近的擦边是 Nie et al.、Ao et al. 与
inference-fleet-sim。本文的 §5.9 与 §5.2 正是在填这条曲线。

**以及一条方法学上的贡献（不属于上两条）**：§5.11 的撤回过程本身说明了一件事——
**聚合计数器能凭空造出一条不存在的"速率随并发上升"曲线**。我们先后被它骗过两次：
第一次造出"+86% 批处理"，修好采样粒度后变成"+47%"，换成逐请求测量后**方向翻转成 −5%**。
凡有逐请求原始记录，就不该用聚合计数器反推。

**距离最近的实测 SLO 悬崖来自 DistServe（OSDI '24）表 2**：vLLM 同置部署下
1.0 rps → 97.0%，1.5 → 65.5%，2.0 → 52.8%，3.0 → 36.7%，4.0 → 23.6%——
**负载涨 50%，达成率掉 31.5 个百分点**。该文自己的机制解释是"一旦 GPU 变成计算受限，
往批里再加请求不再提升 GPU 效率，而是按比例延长总处理时间"——**这与我们 §5.11
测到的"每请求速率随并发不升反降"是同一现象**，且互相印证。

## 7 局限与讨论

**1. 机制新颖性不成立（最重要的一条，写在最前）**。容量核算准入+命名许可被
ThunderAgent 覆盖，状态保留式挂起被 MORI 用同一套 SGLang v0.5.10 + HiCache 覆盖，
有界复活等价于 HRRN。本文因此**不主张机制新颖性**（见 §1.3）。这一条必须主动
写出来，不能等审稿人指出。

**2. 主表是单 run，且关键比较跨天**。§5.9 主表 14 行全部 n=1，同 trace 上唯一
一对同条件重复是两个 cap≈4 测量（259.1 / 257.6，差 0.6%）。而摘要里那个"最快的"
主张所依赖的两个臂（Foyer+HC 297.6 @09-20 vs cap2 310.5 @09-15）**相隔五天**，
在共享机器上。我们实测邻居的 24 核任务可把墙钟拉大 17–25%。**§5.10 的匹配对
实验就是为了消除这一条**；在它落地前，摘要与 §1.3 中任何性能领先的主张都标注为
条件性的。[待补：配对结果]

**3. 保守性的代价是真实的，我们不掩饰**。cap4 命中率比 Foyer 低 20pp，聚合吞吐
仍高 14%——因为它在飞的请求更多，**不是因为它每个请求更快**（§5.11）。
所以 Foyer **不能**在无约束 makespan 上赢过 cap4，本文也不主张能赢。
它的位置是"在 SLO 约束下可行且最快的候选"，不是"全面更快"。

**4. 两簇之间的过渡形态未被分辨（比"崖位未知"更严重）。** 缺口在引擎并发
(1.33, 1.44)，没有观测点（主表那个 cap3 点被 runner 竞态污染、实际跑的是 cap4）。
但问题不只是"位置未知"：§5.11 的同 run 曲线**平滑**，而平滑的分布移动应当产生
平滑的聚合曲线，所以**"不连续"与"陡峭平滑下降"这两种解释现有数据分不开**。
本文因此只说"两簇、中间未采样"。`cap3_fixed` 落在缺口正中，是唯一的判决测量：
落 ~300 → 陡降成立；落 ~258 → 两簇其实连续，"台阶"要撤回，改说"平滑下降 + 采样不足"。
完整论证见 `docs/throughput_decomposition_20260921.md` §7。

**5. 任务质量不可测**：TraceLab 脱敏后不含任务结果，无法测准入对任务成功率的影响。
但准入控制不改变请求内容与输出语义（只改变何时执行），影响面限于时延/失败率。

**6. 单模型单卡**：目前 Qwen2.5-Coder-7B + 3090。§5.11 的结论（每请求速率随并发
不升反降）依赖"KV 池只装得下几个会话"这一比例关系，换模型或换卡后**是否仍然成立**
需要复验。[可选补强：3B/14B 各一档；A100 复验一轮]

**7. 重放的局限**：tool_wait 来自 trace 分布而非真实工具执行；闭环重放已保证
会话内因果，会话间无因果。

**8. 负载形态**：主力实验采用"全体同时到达"（flash crowd，与 Concur 的批离线评测
同制度）；§5.8 补充了泊松到达与真实测量到达，但三种形态绝对负载不同、
只可比相对位置。

## 8 结论

（v2.0 重写。v1.1 的结论把三个机制当作已证明的贡献，其中两个已被覆盖、
第三个等价于 HRRN，故不再成立。）

本文在显存受限单卡上测量 agentic serving 的并发治理，得到两个结论。

**其一：并发买到的是并行度，不是效率。** 逐请求测量（每请求自己的解码时长）显示，
**每请求解码速率不随并发上升**：并发 1/2/3 分别为 36.4 / 34.6 / 33.4 tok/s，
1→2 为 0.95×。聚合吞吐随并发上升，**只因为同时在飞的请求更多**。由此墙钟近似
正比于并发的 −1/2 次方（预测比值 1.19，实测 1.21），数据支持**平滑单调**的曲线。
因此主表那"两簇"（297–340 与 257–271 分钟，中间 (1.33, 1.44) 未采样）
**更可能是采样缺口，而不是台阶**。

它的代价是可测的：那 ~14% 的墙钟对应 SLO 从 ~89% 掉到 55–62%。因此 makespan 的
无约束最优不可部署，**SLO 必须按约束处理**。

**其二：控制变量必须取引擎实测的物理占用。** 会话侧的两个量都系统性高估引擎真实
状态，我们分别测到了：逻辑上下文之和比物理驻留 KV 高估 ~1.8×（前缀共享），
在飞会话数比引擎实际在跑的请求数高估 ~2.0×（tool_wait），且后者比值随并发从
0.64 漂移到 0.38、不是常数。按会话侧的量准入的控制器，因此**系统性地过度保守、
停在台阶边缘之前**——这解释了我们自己早先版本的全部性能差距来源。

**我们明确不主张机制新颖性。** 容量核算准入与命名许可已被 ThunderAgent 覆盖；
状态保留式挂起被 MORI 用同一套 SGLang v0.5.10 + HiCache 覆盖；有界复活等价于
HRRN。这些机制仍实现在我们的系统里并在实验中生效，但它们是既有技术，不是本文的
贡献。**本文的贡献是上面两条测量，以及由第二条导出的设计规则。**

一条方法学上的教训，与结论同等重要：**系统自己的安全机制会成为性能天花板，
而且它的代价必须被测量、不能被假设**——我们用量化归因证明，两个为早期缺陷设计的
保护层（高水位地板、单飞准入）压制了 47% 的完成时间，而它们的原始设计前提
（准入不可撤销）早已不复存在。同理，本文全部数据都受一个守卫保护：池子会因邻居
占卡而静默缩水，曾伪造出"质量退化 5.9pp"的假象。在共享、显存受限的真实设备上，
**"测量保护的代价、并随能力回收保护"与设计机制本身同样重要**。
