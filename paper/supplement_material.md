## S1. 共租审计的取证细节（原文 §VI Reproducibility）

**外移内容**：窗内对照逐条读数。

判据（保留在正文）：一次审计把「与另外 ≥3 条 run 重叠 ≥1 小时」的 run 标记出来 ——
主 trace 12 条、变负载 2 条，共 14 条；造成那些窗口的事故本身还直接终止了四条 run，
那四条不出现在任何表里。**标记是风险提示，不是损害测量**：引擎侧计数器
（在跑数、池占用、驱逐、重算）在被影响与干净的 run 之间不可区分，所以审计只能
跑在客户端侧的逐请求解码间隔 τ₂ 上。

损害可见时幅度很大：最受影响的臂在被标记时 τ₂ 到 **33.3 ms**，重测为 **24.8 ms**，
而同一控制器族的十五条干净 run 是 **23.8--27.5 ms**。

**窗内对照（三个，都在同一条 run 自己内部）**：

| 对照 | 前 | 后 | 条件 |
|---|---|---|---|
| `cap1` | 前五个半小时的逐半小时中位 τ₂ = **20.3--20.9 ms** | 另两条 run 起来后的三个半小时 = **21.3 / 27.1 / 21.1 ms** | 邻居到达 |
| `t85` | 邻居离开前那半小时 = **29.8 ms** | 之后四个半小时 = **22.3--22.6 ms** | 邻居离开 |
| `rl99` | **32.4 ms** | **25.2 / 25.1 ms** | 邻居离开 |

同一条 run、同一策略、同一 trace，**变化跟着机器上还有谁走**。

**半小时窗口的选择理由**：它是最宽的、仍能分辨那次转换、且每个引用的桶里还放得下
二十步的窗口；更细的序列更噪，不支持分钟级分辨率的结论（`tau2_windows.csv`）。

**体量列看不出损害**：我们有前后两读的那条臂，被标记时复用 **0.6943** 的 prompt、
单独跑时 **0.6904**，两者都落在我们有两用数据的 26 条 host-tier run 的
**0.4511--0.6981** 区间内，而它的 τ₂ 从 **31.3 走到 24.8 ms**。
**提示性而非证明：一条臂就是一次比较。**

## S2. 控制器产物版本史（原文 §VI Reproducibility）

**外移内容**：四个哈希的逐条归属与不可分辨性的论证。

这些 run 记录了 `controller_budget3.py` 的**四个不同哈希**，四个都**不**匹配仓库副本，
所以**没有单一版本能复现每一个数字**。矛盾审计标记的那些臂**不是零散子集**，
而是其中一个副本下记录的**全部四条** run（那个副本没有别的 run），
而另一个小副本并不能打破这个平局 ——
**因此版本与共租无法用我们数据里的任何比较分开**。我们陈述这个混杂而不是给出一个解决。
重跑**同时**改变了争用窗口与控制器版本。

多数臂所跑的那个副本**仍在实验机上**，所以它与仓库的差异**可以被重新推导**而不是靠信任：
**22 行、两处** —— 它在 `waiting[:1]` 上跑单飞，而仓库副本扫整个队列；
以及把候选自己的 context 写在日志称作 `base` 的那个下限之上。
因此 §V「controllers leave memory unused」那一节测的是**修复加一个更松的准入率**，
不是「照原样写的那个修复」。

**窄测现在存在**（正文报告了它）：同一个副本、只改这一个表达式 —— 而它就是那条越过线的臂。
它自己的注释记录了那个表达式去掉了什么：**队首太大装不下时，它挡住在它之后的每一个更小的会话，
而引擎空转**。§V 那个不放行的窗口有这个形状，但它的日志不携带逐候选决定，所以我们不声称。

**一条适用于那个比较的保留**：启动 run 的 harness 脚本在其中并不相同 ——
基线的重复与 scan 臂记录了它的不同哈希，两条 `horizon=2` run 与两条 `single-flight off` run
也是（scan 臂自己的重复记录的是同一个）—— 而且更早的版本是**就地覆盖**的，
所以我们**既不能 diff 它们，也不能证明 launcher 没改别的**。
记录的参数与 build **确实**与仓库相符；控制器源码差的**只有**上面点名的那个表达式加一个注释块。

## S3. 七条撤回的完整细节

**正文保留**：七条撤回的**清单与一句话理由**（负结果论文的可信度特征）。
**本节**：每条的取证细节 —— 原来错在哪、真值是多少、怎么发现的、出处在哪份文件。
两条审计文件是写作期的工作记录（`paper/claims_audit.md` 与
`docs/claim_register_20260921.md`），**不是数字的权威来源**；下面每条都同时给出数据文件的出处。

**1｜步成本的分母。** 旧算法把 τ 除以**全时段**平均在跑数，却乘 busy 时间 —— 两个错误
相互抵消，于是两种测量方法「看起来一致」。真值：τ 系统性偏低，偏低的幅度**恰好等于该 run
的空转占比**（`cap1` 的 36.3%，正文写「36% for \texttt{cap1}」）。修法：改用
**busy 条件**下在跑均值（`gen_decomp.busy_stats`，全仓库唯一实现）。出处
`paper/data/decomp.csv`（`busy_min`/`idle_min`/`running`/`step_back_ms` 四列可复算）。

**2｜`tool_wait` 的读数。** 旧结论基于**中位数** 0.34 s，据此认为「会话从不离开引擎」。
真值：要求的均值 **15.82 s**、最大 300 s，799 次轮次转换里 **18.0%** 超过 10 s；控制器的
run 实测均值 **16.85 s**（差 1.03 s 归因于准入延迟）。出处 `paper/data/toolwait.csv`
（三种分母都在表里，`gen_toolwait.py` 的 docstring 记了它们的区别）。

**3｜oracle 单调性。** 旧论证「预测越准 → 策略越保守」（`--predictor oracle`）建立在一个
**实现有缺陷**的臂上，该臂不得引用。真值：`G*(t)=max(0,C(t+3)−C(t))` 重写后**没有重跑**，
所以这条单调性**没有测量**。出处 `docs/claim_register_20260921.md` 的「§四十四 第三节整段撤回」；
另见 `paper/supplement_material_intro.md` 的 oracle 臂讨论。

**4｜记账重复计费。** 旧算法把 `pausing_tokens` 加在 `measured` 之上，等于把已在引擎里的
会话再算一次。证伪不是推测：某 run 的日志里 `measured 97,180 + pausing 15,700 = 112,880`
**超过池子 101,432** —— 引擎不可能持有超过池子的不可回收 KV。后果非边际：`committed`
120--132k 对 91,289 的红线，多数周期一个都放不进。修法：只记日志、不计入。出处
`docs/claim_register_20260921.md` §五（C4 那一行）与 `controller_budget3.py` 及其不变量测试。

**5｜空转率不随并发单调下降。** 旧稿写「空转占比随平均并发单调下降」。真值（busy 条件口径）：
`no gate, no resv.` 在 $\overline{R}_{\text{busy}}$ 1.68 上闲 20.7%，而 `cap4` 在 1.65 上闲
10.4% —— 并发更高、反而更闲。逐字原文与读数在 `paper/supplement_material_model.md` 块 6；
数据出处 `paper/data/arm_running.csv` 与 `paper/data/decomp.csv` 的 `idle_pct` 列。

**6｜一次被反过来推翻的反驳。** 早期修订曾用两条**各自都错**的检查否掉「驱逐→重算」机制：
① 总 prefill token 与计划 prefill 之比恒为 1.00 —— 而 `prompt_tokens_total` 按构造就含
**缓存部分**，等于计划值之和，**探测不到重算**；② SGLang 报「没有撤回」—— 而基数缓存的
驱逐不是撤回（那个计数器数的是**在跑请求被中途抢占**）。逐字原文在
`paper/supplement_material_model.md` 块 M1；同族的「看起来像测量、其实是恒等式」的写法
与 §II 的段论证是同一族。

**7｜停摆审计的判据极性反了（2026-09-26 新增）。** 旧判据 (b) 要求 `valve` **为真**，
而日志里 `valve` 为真 = **阀门正在挡准入**，方向正好相反 —— 于是报出来的「窗口」其实是
**阀门在按设计工作**的周期。怎么量的：只看同一条 run 自己的联合分布（`foyer_rg4`）——
`valve` 为真的周期里放行过 29/5348 = **0.5%**，为假的周期里放行过 308/3137 = **9.8%**，
差一个数量级 ⇒ 为真抑制放行。改正后：4 条臂有窗口 → **1 条臂 1 个窗口（166.6 s，
采样跨度的 0.93%）**。旧数（4 条臂、195.0 / 240.1 s 等）与两套计数都在
`paper/data/stall.csv`（`n_windows_valve_holding` / `old_total_s` / `old_pct_span` 列）；
判据的方向由 `scripts/lab/gen_stall.py` 的 `_polarity_check()` 现场断言。

## S8. 池子为什么可能变短，以及短池影响什么（正文 §II 的守卫句指向这里）

**正文保留**：守卫本身（池子必须落在 $101{,}432 \pm 20$，否则该 run 作废、不记录）。

**为什么会长短不一**：SGLang 在**启动那一刻**按空闲显存定池子
（`mem_fraction_static` 0.85 $\times$ 当时的空闲量），所以同一台机器上、同一套参数的两条
run 可以给出不同的池子 —— 邻居先来一步占住显存，池子就小。实测（A100，名义 983,728）：
872,977 / 886,408 / 817,527 / 943,541 / 983,697 都出现过，对应的是「卡被占」而不是
「参数写错」。3090 侧的例子是 A100 那条 `a100_default_r2` 的同族：池子 817,527、
占用中位 95.3%、$\tau_2$ 222.7\,ms（正文 §VI 的披露句，读数在 S5.3）。

**短池影响什么、不影响什么**：
1. **占用**是按池子的**比例**报的 ⇒ 池子小的 run 占用被抬高，**跨池子的占用不可直接比**
   （817,527 那条读到 95.3%，而满池那条读 9.5% —— 差的是池子，不是策略）；
2. **兑现率需要满池** —— 一个 prompt 超过池子的步**根本不被执行**（引擎回一个 1-token
   的退化响应，runner 记成成功），所以容量对照实验（池子减半 / 四分之三）**不产生兑现率**，
   它量的是**服务能力的长度边界**，不是兑现率的下降（正文 §III 的容量控制段）；
3. **墙钟与 SLO 仍在同一条轴上**，所以 A100 的两张表里，池子短的那一条只影响它自己那一列
   的占用读数 —— 表 II 的 `cap1` 行因此被点名说明（971,456 而不是 983,728）；
4. **池子差 9.7 倍的两族（3090 / A100）不放进同一条前沿** —— 混算包络是错的，
   这是 `a100.csv` 表头自己写着的那条纪律。

**判据的落地**：`scripts/lab/run_matrix.py` 的 `TURNSTILE_EXPECT_POOL`（默认 101432）与
`TURNSTILE_POOL_TOL`。⚠ 这两个默认值是**机器相关**的 —— A100 的 lane 漏设它时，六次
server 启动给出的池子全被判 `POOL MISMATCH`，整整 35 分钟白等（见 S5.3 的第 3 次尝试）；
A100 侧现在显式设 983,728 / 容差 5,000（±0.5%），或显式设 0 关掉守卫。
