## 1. 研究问题与当前主张

**场景**：单张显存受限 GPU（RTX 3090 24GB）上的 agentic LLM 服务。7B 模型，
KV 池只有 101,432 token，而**一个会话的上下文中位数就有 23,187 token（占池子 22.9%），
p90 是 51,064（50.3%），最大 89,436（88.2%）**。

**主张**：容量核算准入（capacity-accounted admission）——控制器按 KV token 记账决定放行
哪些会话，而不是像静态并发上限（cap-n）那样用一个死数字。

**三个机制**（统一口径，不要再拆）：
1. **容量核算准入 + 命名许可**：控制器写下确切的会话 ID 集合，"计划放行的 = 实际运行的"
2. **状态保留式挂起**：被暂停的会话 KV 下沉主机内存（SGLang HiCache），复活是搬运不是重算
3. **有界复活**：按"等待时间 ÷ 复活代价"排序 —— **仅设计，未实现、未验证**

## 2. 评测设置（读数据前必须知道）

- **硬件**：RTX 3090 24GB ×4，共享机器（31 个用户在线，无调度器）
- **模型**：Qwen2.5-Coder-7B-Instruct，YaRN ×3，96K 上下文
- **引擎**：SGLang，`mem_fraction_static=0.85`
- **负载**：泊松到达，200 会话，λ=0.04/s（按语料实测峰值小时率标定），999 步
- **池子**：每个 run 起服时校验 = 101,432 token（容差 ±20），不符即中止重试
- **指标定义**：
  - **墙钟**：`metadata.wall_s`，整个回放从起跑到最后一个会话完成
  - **命中率**：引擎自报的前缀缓存命中率
  - **SLO%**：TTFT < 10s 的**步**占比（分母是成功步）
  - **TTFT 口径**：从"请求提交给引擎"算起，**不含门外排队与暂停**
  - **并发**：时间平均的活跃会话数

## 5. ⚠ 测量可信度警告（最重要的一节）

### 5.1 墙钟对 CPU 争用高度敏感

2026-09-20 23:16，同机用户起了一个吃 **2378% CPU（约 24 核 / 48 核）** 的任务。此后：

```
                       负载前      负载后
pois200_cap1          2.39 步/分 → 1.98 步/分    −17%
pois200_aimd2_paper   4.40 步/分 → 3.32 步/分    −25%

同一时段服务器解码吞吐   45.2 → 44.4 tok/s        −2%
```

**GPU 几乎没被抢，掉的是 CPU 侧**——runner 提交、tokenizer、调度器都在 CPU 上。

**含义**：被污染幅度（17–25%）**大于我们要测的策略差异**（Foyer 299 vs cap4 258 = 14%）。
因此——
- **墙钟只在 CPU 条件可比时才可比**
- **质量类指标（命中率/SLO/TTFT p50）不受影响**（按步统计）

### 5.2 最关键的几个对照是干净的

- `cap2 / cap3 / cap4 / cap5 / Foyer / Foyer+HiCache`：在安静时段采集
- `Foyer rl90 / rl99`：02:24 之后起跑，全程机器安静（负载 2–15/48）

### 5.3 其他已知偏差

- `Foyer rl90` 的池子 101430（差 2 token，0.002%），在守卫 ±20 容差内
- **不做重复实验**：关键配置只跑一次，单次结果视作稳定（项目决策 D8）。

## 6. 2026-09-21 夜间的实验：一次被否证的假设

### 6.1 假设

观测到 Foyer 的控制器账本长期停在"92% of budget"，而引擎实测只占池子 52%。
推断：**记账过于保守，导致并发上不去**。于是把内存从"优化目标"改成"红线"：

```
旧（v3）：projection = max(引擎实测, 逻辑上下文之和) + 行增长预留(3轮)
          准入条件 projection + 新会话×1.15 ≤ target_util × pool

新（foyer）：committed = 引擎实测 + 已放行未落地 + 增长预留×gs
            准入条件 committed + 新会话 ≤ target_util × pool
```

`--target-util` 成为唯一的激进程度旋钮。跑了两个档位。

### 6.2 结果：退步

```
                并发    墙钟      命中%   SLO%   引擎忙占比
Foyer (v3)      2.12   299.3    65.6   88.6    75%
Foyer rl90      2.84   300.2    57.7   77.8    81%
Foyer rl99      3.30   362.0    46.3   61.4    72%
静态 cap3       3.56   259.2    49.8   62.2    87%
静态 cap4       3.94   257.6    45.9   55.7    90%
```

**① 记账改动确实生效**（并发 2.12→2.84，引擎忙占比 75%→81%），
**② 但主要指标没动**（墙钟 299.3→300.2），**③ 质量掉了 7.9pp**。

### 6.3 机制（这是本次最有价值的发现）

```
并发上去 → 工作集超过池子 → 引擎驱逐 → 重算 → 单会话变慢
                                              ↓
                          多出来的并发被"变慢"吃掉，墙钟不动
                          命中率却实打实掉了
```

具体：rl90 并发 +0.72，但**单会话执行时间从 2.2 分涨到 2.9 分（+32%）**，
占用总量（并发×墙钟）从 634 涨到 852 会话·分钟（+34%），正好抵消。

**激进臂更差，它被自己的安全机制反噬**：rl99 的硬阀在 2162 次决策里触发
**971 次（45%）**——阀一响就不准入、还挂起会话，**引擎有 28% 的时间空转**
（cap3 只有 13%）。结果并发只到 3.30，墙钟却慢了 60 分钟，被 cap3 完全支配。

### 6.4 账本分解（解释平台区的成因）

```
                    rl90 (gs=0.35)        rl99 (gs=0.05)
红线                 91,287                100,418
引擎实测 中位        72,690 (80%)          70,189 (70%)
增长预留 中位        13,492 (15%)           1,883 ( 2%)
committed 中位       91,089 (100%)         80,003 (80%)
```

rl90 的增长预留正好吃掉了再放一个会话所需的余量
（`80% + 15% = 95%`，再加新会话 20% → 115% > 100%）。

### 6.5 这与文献警告一致

- **Ao et al. [2606.15555]**（101 页，未同行评议）：定理 2 证明无驱逐不动点**不稳定**，
  最大驱逐极限环的吸引域包含几乎所有内存边界初态；相对无驱逐均衡**吞吐损失最高 50%**。
  表述："服务过程本身制造未来的容量压力"。⚠ 抓到的 HTML 缺数值实验与真机附录。
- **DistServe (OSDI '24) 表 2**：vLLM 同置 SLO 达成率 1.0rps→97.0%、1.5→65.5%。
  机制原文："一旦 GPU 变成计算受限，往批里再加请求不再提升 GPU 效率，
  而是按比例延长总处理时间。"

## 7. 我们真正想解决的问题

**用户明确的两个指标，端到端优先、命中率其次**：

> "其实这两个指标，我最关注的、最想要的，是端到端指标，
> 我们应该是在保证端到端指标的同时，让我们的 TTFT 也能好一些。"

**现状是：端到端上我们打不过静态 cap3/cap4（299 vs 258 分，慢 16%）。**
这是当前最核心的未解问题。

而质量上我们明显更好（Foyer 65.6% vs cap3 49.8%）。所以现在的处境是
**"质量换速度"的帕累托点，而不是支配关系**。

## 8. 尚未解决的具体矛盾

1. **平台区之谜**：为什么并发从 2.0 到 2.84 墙钟纹丝不动，而 2.84 到 3.56 却掉 40 分钟？
   如果是平滑的排队论曲线，不该有这个台阶。
2. **空转**：rl90/rl99 的引擎有 19%/28% 的时间空转（cap3/cap4 只有 13%/10%），
   而队列里排着 55–100 个会话。是吸附振荡？单飞准入？还是别的？
   **如果能消掉这部分空转，墙钟大约能降 6–15%。**
3. **超订的代价**：算过——每会话约 23.6K token、新会话需 20K，
   **四个并发会话需要 117% 的池子**。所以跨过 3.5 那道崖必须**故意超订**，
   让引擎自己驱逐腾地方。这正是 §6.5 文献警告的区域，也是 cap3/cap4 实际在做的事
   （代价记在命中率上：49.8% / 45.9%）。
4. **公平基线缺失**：如果主表要用 `Foyer+HiCache`，配对基线应该是 `cap2+HiCache`
   （同一 trace、同一池子），这个 run 目前**不存在**。

## 9. 已确立的结论（证据强度已标注）

| 结论 | 强度 |
|---|---|
| 不限流会崩（命中 1.6%、SLO 3.0%） | 强，单次但极端 |
| 静态 cap-n 存在最优点，在 3–4 附近（~258 分） | 强，8 点扫描 |
| Foyer 命中率高于所有静态档（65.6% / 69.7%） | 强 |
| Foyer 墙钟慢于 cap3/cap4（299 vs 258） | 强 |
| Foyer+HiCache 在**高驱逐场景**大幅改善（25 档 cap6：27.9→22.8 分，命中 31.7%→64.1%） | 强 |
| Foyer+HiCache 在泊松档只小幅改善（299.3→297.6 分，命中 65.6→69.7%） | 中，单次 |
| **把利用率推高不改善端到端** | 中，2 个点 + 机制清晰 + 与文献一致 |
| 并发与墙钟是台阶关系而非平滑曲线 | 弱，5 个点，可能是噪声或混杂 |
| 墙钟对 CPU 争用高度敏感（17–25%） | 强，直接测量 |
