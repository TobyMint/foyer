这一页更正 `docs/a100_window_assessment_20260925.md` 里的两条判断 —— 两条都是**错的**。

## 更正一：模型在同一台机器上

我写「A100 上没有 coder + YaRN 模型」——那是因为我只搜了 `/data/models`。
模型其实在 **`/data/xbw/turnstile/models/qwen25-coder-7b-yarn96k`**，而且：

- trace 的 md5 与 3090 侧**逐位一致**（`df4bdd37e5b7241b2433edaeeea3789c`）；
- sglang 版本一致（0.5.10.post1）；
- harness 是同一份 `run_matrix.py`（含池子守卫与 gpu_watch）。

所以「四条轴同时动」这条理由**不成立**：同模型、同 trace、同引擎、同 memfrac，
**只改卡（→池子更大）这一个变量** —— 这正是论文 §III 那条因果主张缺的对照。

## 真正的拦路石：JIT kernel 编译

起跑报错不是显存，是：

```
sgl_kernel_jit_fused_rope_true_128_false_bf16_t_... 编译失败
fatal error: concepts: No such file or directory   （-std=c++20 需要 gcc>=10）
```

A100 上只有 **gcc 8 / gcc 9**（Ubuntu 20.04）；CUDA 12.1 支持到 gcc 12。
`/usr/local/gcc-14.3.0` 存在但与 CUDA 12.1 不兼容（实测 100 个错误）。

**为什么 3090 上没事**：它的 `~/.cache/tvm-ffi/` 里**已经有 9 月 7 日编译好的 kernel**，
根本不会重新编译。也就是说 **3090 跑的是陈旧缓存里的 kernel**，换成今天这份源码
它大概也编不过。这一条本身值得记（与「四个 running copy 的 hash 都与仓库不一致」
是同一类：**跑的不是你现在读到的那份东西**）。

**处置**：正在往 `/data/xbw/gcc12` 装 conda-forge 的 `gcc_linux-64=12`，
装好后用 `-ccbin` 指给 nvcc。装好之后**下一次窗口就能起跑**，不必重来。

## 预注册（已经写死在 lane 脚本里）

`lane_a100_dev.sh`：GPU0、device-only、memfrac 0.85、`TURNSTILE_EXPECT_POOL=0`
（**故意**关掉池子守卫 —— 80G 卡上池子本来就该大得多；关掉后 memfrac 钉在 0.85，
池子由卡自己决定，实际值写进 metadata）。

预测：3090 的 device-only 兑现率是 cap1 92.5% / cap2 89.7% / cap3 79.0% /
cap4 60.7% / cap5 36.4%（R̄ 1.00 → 1.84）。若「兑现率由容量定」，
A100 上同一批 cap 在同一 R̄ 上应兑现明显更高（预期 ≥85%），塌点被推到更高 R̄。
**若 A100 在同样 R̄ 上塌到同样水平，「容量定塌点」被证伪。两种结果都照实写。**

  （那会改步时间，正是本项目最忌讳的不可比）。要跑就跑同一份源码编出来的 kernel。
- 窗口关了就等下一次；装好的编译器不会白装。

## 起跑成功（02:47:30）

```
[02:47:30] lane a100_dev gpu 0 port 30091 runs [a100_cap4, a100_cap3, a100_cap5, a100_cap2]
[02:49:04] server healthy, pool=983728
```

**池子 983,728 tokens = 3090 的 101,432 的 9.70 倍。** 同模型、同 trace（md5 一致）、
同 memfrac（0.85）、同引擎版本、同 harness —— **只改卡这一个变量**。

修法（记下来，下次直接抄）：

```bash
conda create -y -p /data/xbw/gcc12 -c conda-forge gcc_linux-64=12 gxx_linux-64=12
export NVCC_PREPEND_FLAGS="-ccbin /data/xbw/gcc12/bin/x86_64-conda-linux-gnu-g++"
export CUDAHOSTCXX=/data/xbw/gcc12/bin/x86_64-conda-linux-gnu-g++
export PATH=/data/xbw/gcc12/bin:$PATH
```

⚠ **只设 `CUDAHOSTCXX` 不够** —— JIT 生成的 `build.ninja` 里写死了 `nvcc` 路径、
不带 `-ccbin`，所以必须用 nvcc 自己的 `NVCC_PREPEND_FLAGS` 注入（实测有效：
同一个 `.cu` 用它编出可执行文件并跑出结果）。

`TURNSTILE_EXPECT_POOL=0` 关掉了池子守卫并把 memfrac 钉在 0.85；实际池子
983,728 已写进 `metadata.json`。`gpu_watch.jsonl` 在记，`n_foreign=0`。

（池子不同、不可与主表混算前沿），要单独成表（如 `paper/data/a100.csv`），
只用于「同一 R̄ 上兑现率是否更高」这一个对照。
