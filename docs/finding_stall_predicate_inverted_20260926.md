# 「不放行窗口」审计的判据极性是反的 —— 2026-09-26

**一句话**：`gen_stall.py` 的判据 (b) 写的是「阀门开着（不是阀门挡的）」，
实现却是 `bool(e["valve"])`；而日志里 `valve` 为真 = **阀门已经跳闸、正在挡准入**。
于是这条审计选出来的「窗口」正是**阀门按设计在工作**的那些周期，
而正文把它们写成「阀门开着、控制器却不放人」——**把「阀门在起作用」说成了「控制器失灵」**。

这是本项目到目前为止**最重的一次修正**：它是全篇唯一的机制性主张所依附的那批数据。

---

## 一、怎么发现的

顺着「第 38 轮审查点名的未回答实验」去准备「队首阻塞修复后前沿会不会移动」时，
先要确认「修复前跑的是哪份代码」。查 `metadata.json` 的 `policy` 前缀发现
**两条控制器并存**（`budget3:` 与 `foyer:`），于是逐条对齐臂 → 控制器 → 日志字段，
顺手做了「窗口内到底被什么挡住」的检查。第一次看到窗口周期里
`usage = 0`、`resident = 0`、105 个会话在等、`budget` 空着 84k —— **不符合池子满**。
再核 `valve` 的语义，就翻出了极性。

## 二、证据（不依赖源码版本）

这批 run **不是同一版控制器跑出来的**：`metadata.json` 的 `code` 字段记着五个不同的
`controller_budget3.py` 哈希，而**有的版本与今天磁盘上那一份并不一致**
（`foyer_hc` 那批记的是 `2b573829083c`，日志里 `base_mode`/`base` 是 `None`；
`rg4`/`sf0_r2` 那批记的是 `f825bc768188`，与现盘一致）。
⚠ 我第一版把这条**过度概括**成了「跑出这些日志的都与现盘不同」并写进了三份文档 ——
**从一个 run 的日志推断到全部**，正是本项目「先核状态，再解释状态」那条的同类。
所以判据仍然要建立在**日志自身的经验语义**上：

| run | `valve` 为真的周期数 | 其中放行过的 | `valve` 为假的周期数 | 其中放行过的 |
|---|---|---|---|---|
| foyer_rg4 | 5348 | 29（0.5%） | 3137 | 308（9.8%） |
| foyer_hz0_r2 | 2543 | 11（0.4%） | 5412 | 216（4.0%） |
| foyer_bres_r2 | 1266 | 4（0.3%） | 6763 | 223（3.3%） |

`valve` 为真 ⇒ 放行率低一个数量级 ⇒ **`valve` 为真 = 准入被阀门挡住**。
已把这条做成 `gen_stall.py` 的 `_polarity_check()`：只用同一条 run 自己的日志，
若 `valve` 为真时的放行率 ≥ 为假时，**断言直接炸**（不会静默照抄）。

## 三、改正后是什么

判据 (b) 改成 `valve` **为假**（阀门没在挡），其余三条不变：

| | 旧判据（`valve` 为真） | 正判据（`valve` 为假） |
|---|---|---|
| 有窗口的臂 | 4 条 | **1 条**（`foyer_hc`） |
| 时长 | 173.2 / 195.0 / 240.1 s；foyfix 九段共 3036.2 s | **166.6 s** |
| 占墙钟 | 1.0% / 1.2% / 1.47%；foyfix 12.02% | **0.93%** |
| waiting 中位 | 111 / 128 / 89；foyfix 122 | **105** |

旧判据选出来的那四条的**性质**也查清了：**100% 的窗口周期**都满足
`ttft_p50_ms > 10 s`（SLO 阈值）而 `usage = 0` ——
**引擎的池子是空的、在跑请求数是 0，控制器却因为一份「还被认为是新鲜」的
TTFT 中位数持续挡着准入**（四条臂的中位数分别是 17.7 / 16.0 / 12.2 / 19.1 s）。
这是**阀门的记忆比拥塞长**，是阀门在工作，不是活性缺口。

正判据下那一个窗口的恢复走的是**饥饿逃生**（`forced=True`），
它之前的那次放行也是 —— 也就是说那段里正常路径一次都没成功。

## 四、连带推翻的一件事：队首阻塞解释不了这个窗口

正文原来写「我们把其中一个窗口追到了一个代码路径：只看队首 ⇒ 队首太大就堵住后面所有人」。
实测那个（现在唯一存在的）窗口：

- 队列里 **104** 个会话在等，队首是 **15,981 token**，队列里最大的 **63,403 token**；
- 红线上限 **96,360 token**，引擎自报池子**全空**（`usage = resident = 0`）。

**每一个在等的会话都放得进**，所以挡住它的**不是预算判据**，而是它**上游**的东西。
控制器没有记录足够细的每周期决策（`base` 是 `None`、`need` 恒为 0），
**我们无法指认是哪一个门**。正文已照实写成「we cannot name the gate that did」。

「只看队首」这句本身**仍然成立**，但依据换了 —— 换成一个**不依赖源码版本**的日志指纹：

| | 放行次数 | 其中乱序放行 | 占比 |
|---|---|---|---|
| 九条单飞开着的臂（各） | 200 | **0** | 0.0% |
| `foyer_sf0_r2`（单飞关） | 200 | 80 | 40.0% |
| `foyfix_hc`（另一个控制器，扫队列） | 200 | 116 | 58.0% |

「只看队首」的规则**不可能**在「更早到达的会话还在等」时放行别人；
能跳过被堵住的队首的规则则会。已做成 `gen_stall.py` 的断言：
**单飞开着的臂乱序放行必须为 0**，否则报错。

## 五、顺带查出的两条

1. **§VI 的「That is the code every run in this paper executed」过头了。**
   表 I 的 `all throttles off` 行（`foyfix_hc`）跑的是**另一个控制器**
   （`foyer:` 前缀），它**有**扫队列那段代码，而且单飞是关的。
   §I 与 §V 早就写明「all-throttles-off 跑的是另一个控制器」——
   **同一篇稿子里对同一条 run 有两种说法**，检查器一处没报（它不查「哪条 run 属于哪个控制器」）。
   已改成「驱动我们全部 run 的那个控制器」，并把修复的归属写清。
2. **`stall.csv` 少了 `old_pct_wall` 列。** 正判据下的 `pct_wall` 对 `foyfix_hc` 是 0，
   而正文在修正段里印的 12% 是**旧判据**下的占比 —— 那个数在新表里**无处可追**。
   是检查器报出来的（守卫读了 `pct_wall` 得到 0）。**守卫也会抄错列。**
3. **论文把「能核查的」说成了「不能核查」。** §VI 两处写着
   「只剩仓库那份 `a21bd2b63774` 留在机器上，四份副本已不在，所以那次比较无法重建」
   与「`f825bc768188` 是跑那条臂的副本、已不在仓库，读法无法复查」。
   **实测：机器上两份都在** ——
   `scripts/controller_budget3.py` = `a21bd2b63774`（仓库版），
   `TraceLab/replay/scripts/controller_budget3.py` = **`f825bc768188`**（跑过 37 条 run 的工作副本）。

   而且 diff 出来的东西比原来写的**更有用**（22 行、两处）：

   | 位置 | 仓库版 `a21bd2b63774` | 工作副本 `f825bc768188`（37 条 run 用的） |
   |---|---|---|
   | 队首 | `head = waiting`（**扫队列**） | `head = waiting if args.disable_single_flight else waiting[:1]` |
   | 投影 | `cand_base = s["ctx"] or s["prompt0"]` | `base = ...` —— **把日志里那个 `base`（投影底座）覆盖成候选会话的大小** |

   ⇒ (a) 「修复不在跑出这批结果的产物里」这句**是对的**，而且现在**有 diff 为证**；
   (b) 第二处解释了为什么有的 run 的日志里 `base` 会与 `usage=0` 并存；
   (c) `sf=0` 那条臂「考虑整队列且丢掉单飞」的读法**可以复查**，复查也确认了。

   ⚠ 论文里原来写的「23 行、一个 charge-mode flag」**不是这一对的差异**（这一对 22 行、
   两处都不是 charge-mode；两份都有 `charge_mode`）。那条读数是针对**已不在的**某个副本，
   现在无法与存世这一对对账 —— 正文已按「能核的核、不能核的照实说不确定」分开写。

   **规矩：说「无法核查」之前，先去 `find` 一遍。** 这与「把正说得更负没人防」是同一条 ——
   反方向的夸大不会触发「主张强于证据」那根弦。

## 六、残留不确定（不许当已解决）

- **那一个窗口被什么挡住，我们不知道。** 只知道不是预算、不是阀门、不是引擎忙。
- `foyer_hc` 在**旧**判据下窗口数 0、正判据下 1 —— 这不是矛盾，两个判据问的不是同一件事
  （旧判据问「阀在挡时控制器是否还放行」，正判据问「阀没挡时控制器是否放行」）。
- 「阀门记忆比拥塞长」的**具体新鲜度常数**没有查（源码里有 `--ttft-freshness-s`，
  但跑这批 run 的不是这一版），所以正文只写「a memory longer than the congestion」，
  **不写秒数**。
- 队首阻塞**是否曾在别的周期里真的绑住**，没有测（要逐周期重放队列状态，
  而控制器没记队列里各会话的尺寸）。

## 七、这次加了什么守卫

| 守卫 | 判据 |
|---|---|
| `_polarity_check()` | `valve` 为真时的放行率必须 **<** 为假时，否则断言炸 |
| `_single_flight` 断言 | 单飞开着的臂，乱序放行必须 **= 0** |
| §V 正判据窗口 时长/占比/waiting 中位 | 三条都 `ck_near` 钉在 `has such a window` 上 |
| §V 饥饿逃生 | 「starvation escape」必须出现 |
| §V 旧判据三条单段臂的时长 | 从 `old_total_s` 拼串比对 |
| §V 旧判据出现段的臂数 / foyfix 的段数 / 12% | 从 `n_windows_valve_holding`、`old_pct_wall` 现算 |
| §V 严格 FIFO 的臂数 / 两个乱序率 / 每臂放行次数 | 从 `fifo_*`、`admits` 现算 |

**八条新守卫全部做过反向测试**（改坏正文 → 确认报 MISS → 还原并验逐位相同），
另加一条**阴性对照**（把正文里一个**没有守卫**的数改掉 → 确认不报，
证明检查器不是「改什么都报」）。
