# 周报 2026-09-21 ｜ Foyer：agentic serving 的并发治理

**一句话**：本周的主要产出是**把"测量"本身做成了可核验的流程**，并据此重排了论文的
证据结构；同时补上了论文框架所依赖的关键测量。数据侧新增一个前沿点。

---

## 一、本周成立且可复现的结论

1. **不治理会坍塌。** 200 会话泊松档、24GB 单卡：命中率 **1.6%**、TTFT 中位 **29.6 分钟**、
   SLO **3.0%**、999 步里 **121 步失败**。（对照：cap2 为 67.7% / 2.2 秒 / 89.5%）
2. **逐请求解码速率不随并发上升。** 并发 1/2/3 分别是 **36.4 / 34.6 / 33.4 tok/s**，
   会话内配对中位 **0.95–0.97**。聚合吞吐随并发上升，只因为同时在飞的请求更多。
3. **"搬"比"算"便宜两个数量级。** 实测 **0.005 ms/token**（PCIe 搬运）对
   **1.08 ms/token**（prefill 重算）——20K token 是 0.1 秒对 21.6 秒。
4. **会话侧量与引擎侧量之间没有稳定换算系数**（本周新得）。同一时刻、同一会话集合上
   直接测量，比值在 99 个采样内 0.72–1.44，**符号会翻转**。

## 二、本周新落地的三件东西

**1. 断言台账（`docs/claim_ledger_20260921.md`）**
论文里每条断言登记**证据来源**与**状态**，只允许四种：实测可复现 / 推论 / 待核 / 已撤回。
**正文引用任何一条时状态必须一致；状态为"已撤回"的不许出现在摘要或结论。**
建立它的直接原因：本周发现三条已经写进论文的结论站不住，而**撤回的成本远高于当初核对的成本**。

**2. Q1 的五类资源同刻测量**
论文的核心问题要回答"会话级的账"和"引擎的物理占用"是不是同一个量，需要**同一时刻、
同一会话集合**上读五个量。此前控制器每一拍都从引擎端点取回全部指标，**只读走一个、
其余丢弃**；现在全部记入决策日志（含主机层、预分配、驱逐、retraction）。
**这是一个每拍自动累积的测量，不需要专门占卡时。**

**3. 配对实验协议（`docs/pair_design_20260921.md`）**
两臂并发、波次间交换 GPU、N 波随机化交叉 + 独跑对照，**判决规则先写下来**
（同号且极差小于中位一半才算稳定；不同号只能报"未检出差异"）。

## 三、数据侧

泊松主表已扩到 13 条策略并按引擎并发排序。**本周新增前沿点**：

| | 墙钟(min) | 命中率 | SLO% | TTFT p50 |
|---|---|---|---|---|
| **cap4 + HiCache** | **219.0** | 0.681 | 63.4% | 5473 ms |
| cap4 | 257.6 | 0.459 | 55.7% | 7215 ms |
| Foyer + HiCache | 297.6 | 0.697 | 89.8% | 2228 ms |
| cap2 | 310.5 | 0.677 | 89.5% | 2183 ms |

`cap4 + HiCache` 值得单独说：`cap4` 快但丢缓存、`cap2` 保缓存但慢，
**而它同时拿到 219 分钟和 0.681 命中率**——主机层缓存把"保缓存 vs 提并发"这个取舍
本身消掉了。**它是个静态配置，没有控制器。**

## 四、清理掉的几个坑（都影响过结论）

- **`cap3_r2` 实测跑的是 cap4**：`cap` 字段 200 条全是 3，但 **195/200 次准入发生在
  `active=3` 时**，落地后 4 个在飞。已作废重跑（`cap3_fixed`）。
- **KV 池会因邻居占卡静默缩水**：曾伪造出"质量退化 5.9pp"。现在每次起服校验池子
  （101,432 ±20），不符则重启重试。三次坏 run 已隔离。
- **陈旧采集进程**：存活 8–13 天的采集进程会持续追加空行，导致任何"末行减首行"的
  时长变成任意值。已清理并加了父进程消失即退出。

## 五、方法学（论文的骨架就在这里）

本周把若干个错误归成了一族，**共十次，覆盖四个环节**：

```
差分错对象  →  相除错对象  →  统计量选错  →  仪器选错
→ 引用了比产物旧的表  →  排队顺序破坏了实验自己的前提
→  用"与仓库一致"验证"与产物一致"（同义反复）
```

**十次里没有一次是数据错或算错。** 全是同一个形状：
**"这个数 / 这张表 / 这个流程，已经不是我以为的那个东西了"。**

这比任何单条测量结论都更值得写进论文——而且它是**可教的**：每一条都留下了
机制和判据，别人可以复用。

## 六、性能主张的现状（不回避）

**目前没有干净的证据说明我们的控制器更快。** 现有最好的一对同 SLO 比较是
`Foyer+HiCache` 对 `cap2`：墙钟 297.6 对 310.5、SLO 89.8% 对 89.5%，
**快 4.3%**——而这个幅度**与跨天不可归因的量级同阶**，不足以作结论。

**能干净回答它的只有配对实验**（两臂并发、同机器同条件）。协议已定，
**队列顺序目前会破坏它自己的并发前提，已定位、待修**。

**另外要指出的一个口径问题**：这些比较都依赖一个 **SLO 门槛**（当前取 TTFT<10s 的
占比 ≥85%）。门槛是**选的**不是测的：取 85% 时 Foyer 领先 4.3%，取 60% 时
`cap4+HiCache` 领先 26%。**同一份数据，门槛一换赢家就翻**——
所以这一条要先定口径，再谈结论（见 `docs/DECISION.md`）。
