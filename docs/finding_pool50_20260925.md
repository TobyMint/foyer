## 〇、这个实验是干什么的

A100 把池子**放大 9.7 倍**（101,432 → 983,728），兑现率不掉了。
但「放大」只有一个方向、一台机器。**半池是反方向**：同一张卡、同一条 trace、
同一个 cap，把池子**减半**（101,432 → 50,716）。
两个方向合起来，才是「池子大小 → 兑现率」的**因果**证据，
而不是「A100 恰好那样」的相关性。

`metadata.json` 核实：`policy=static=2`、`pool_tokens=50716`、
`trace_md5=df4bdd37e5`（与 3090 全池、A100 逐位相同）、`HICACHE unset`（device-only）、`rc=0`。

## 一、观察（`cap2_hp` vs 全池 `cap2`）

    配置        池子      R̄busy     τ₁    τ₂    兑现      occ_p50
    cap2 半池   50716    1.0818    25.7   21.3   0.8712    52.6%
    cap2 全池   101432   1.2714    27.4   22.8   0.8972    41.6%

兑现在半池上**确实更低**（87.1% vs 89.7%），方向对。

## 二、⚠ 但这两个数**不能直接比** —— R̄ 也变了

半池的 R̄ 是 **1.0818**，全池的是 **1.2714**。池子小，`static=2` 也塞不下两个会话了，
于是**并发自己降下来了**。所以在 R̄ 上比 87.1% vs 89.7%，是拿两个不同的工作点在比
—— 正是本项目 `gen_frontier_split.py` 头注释点名的「跨配置外推」那类错。

**正确做法：在同一个 R̄ 上比。** 全池那条兑现率对 R̄ 的曲线在
R̄ ∈ [0.998, 1.2714] 上是 cap1(0.9254) → cap2(0.8972)，线性插值到 R̄ 1.0818：

    0.9254 + (0.8972 - 0.9254) × (1.0818 - 0.998) / (1.2714 - 0.998)
      = 0.9254 - 0.0282 × 0.3065 = 0.9168

~~**所以：在同一 R̄ 1.082 上，池子减半把兑现率从 ~91.7% 压到 87.1%，低 4.6 pp。**~~
**← 这一句已作废（见页首）。87.1% 是虚报值，引擎自报只有 56.88%，且服务量不完整。**

（这个插值必须**由脚本算**，不许手写进正文 —— 见第三节。）

## 三、三条齐了之后要做的

1. **写生成器** `gen_pool50.py`（或并进 `gen_a100.py`）：把半池三条与全池的对照
   放在**同一 R̄ 轴**上，输出半池的 (R̄, 兑现) 连同**插值出来的全池参照值**与差值。
   **差值不许手算**。
2. 与 A100 合起来看：半池 0.5× / 全池 1.0× / A100 9.7× 三点，看兑现率是不是
   **单调**的 —— 那才是「池子大小 → 兑现率」的因果链。
   **注：cap4 那个方向由「跑不起来」给出，不由第三点给出** —— 三点用的是
   cap2 与 cap3 两个档在各池子下的读数，cap4_hp 只作为可行性边界的旁证。
3. **口径**：半池的 R̄ 与兑现都用 `gen_a100.one()` 算（它调 `gen_decomp.busy_stats`
   与 `gen_reuse.trace_ceiling`），**不另写一份实现** —— 本轮就是这么算的，
   上界 21,540,371 与全池、A100 三处一致。
4. 论文里写这条时要与 A100 一节一起写（都是「tier 决定空间」的因果证据），
   且同样**不许暗示跑过控制器** —— 半池跑的也是静态 cap。

**注意**：`cap2_hp` 的 R̄（1.0818）比全池 `cap2` 低，说明半池上**连 cap2 都到不了
原来的并发**。三条齐了要一起看这个「池子小 ⇒ R̄ 也上不去」的效应，
它是这个实验的**第二个**读数，不只是兑现率。
