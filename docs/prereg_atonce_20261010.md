# 预注册：一次性全倒负载 + 长会话（2026-10-10）

## 为什么跑这一轮

2026-10-10 用户决定**换负载轴与指标**：不再用「Δ vs 静态前沿 + deadline 达标率」，
改成**「我们的方案 vs 完全不管」的端到端时间**，并考虑采用文献里更常见的
「一次性全倒」（Concur 明文如此；PBKV / PKAS / ThunderAgent 的横轴也都是固定并发数）。

**这一轮要回答的唯一问题**：
> 在「长会话 + 一次性全倒」这个 regime 里，我们的方案相对无控制的端到端倍数是多少？

## 为什么是「长会话」

2026-10-10 从我们自己的数据推出的定量判据：

    端到端倍数 = 工作量比 × 吞吐比
    实测（pois200，5 轮会话）：2.84 × 0.36 = 1.03   ← 完全抵消，见
    docs/ 与 memory `work-ratio-times-throughput-ratio`

**工作量比上不去**，是因为 5 轮会话被驱逐一次只浪费 ~30K token。
语料里 20 轮会话**若每轮都被驱逐**，浪费是必要量的 **12.0 倍**（本 trace 实测）。
⇒ 把会话拉长是**唯一能撬动工作量比**的旋钮（另一条是换池子/负载比，3090 上动不了）。

## 负载是怎么造的

`/data/xbw/turnstile/data/replay_atonce25r.csv`：
- 来源：`replay_sessions_96k.csv`（语料 96K 过滤子集，5326 会话）
- 挑选：**≥20 轮的会话按「前 20 轮必要 prefill」排序后的中位 25 条**
  （避开最大/最小的尾部，取中位附近）
- 每会话取**前 20 轮**
- `arrival_time` **全部置 0** —— 这是与既有 trace 唯一的差别

| 量 | 值 |
|---|---|
| 会话 / 步数 | 25 / 500 |
| 必要 prefill | **1,532,302** token（首轮占 27%） |
| 若每轮都被驱逐 | **18,318,596** token = **12.0 倍** |
| 单步上下文 | 中位 38,426 / max 65,907（按 25 条那个子集） |
| tool_wait | 中位 125 ms / 均值 69,303 ms / p90 8,609 ms |
| 池子 | 101,432（3090 / memfrac 0.85 / HiCache ratio 2） |

## 两条臂

| run | policy | HiCache | 说明 |
|---|---|---|---|
| `atonce25_default` | `default` | **开** | 无控制基线（与控制器**同配置**，只差控制器） |

「无控制 + 无 HiCache」是另一个问题（那会同时差两样），不在本轮。

## 跑前写死的预期（三种，事后不许挑说法）

- **(a)** 若 no-control 的 makespan ≈ 我们方案的 **2~3.5 倍** ⇒ 机制故事成立，
  倍数来自「驱逐 → 重算」的浪费；
- **(b)** 若只差 **1.0~1.5 倍** ⇒ 「工作量比 × 吞吐比」在长会话下**仍然抵消**，
  这个方向死掉，如实记，并转向「换指标」或「换机器」；
- **(c)** 若 no-control **反而更快** ⇒ 我们的控制器在长会话下把吞吐压得太狠，
  下一步是改控制器（不是改负载）。

**额外会记的量**（不管走哪一支）：`default` 的实际工作量倍数（对照 12.0 的上界）、
冷回来比例、吞吐（K token/分钟）、deadline 达标率。

## 中期读数（2026-10-10 18:54，default 跑到 60 步）—— 机制成立，并据此写下定量预测

```
atonce25_default  60 步 | 必要 619,030 | 实测 uncached 1,142,310 | 倍数 1.85
                  轮>0 的 35 步里，冷回来 35 步 = **100%**
```

**无控制臂的每一次「会话回来」都是全量重算。** 1.85 还低只是因为此刻上下文
还小（后面会长到 65K）；按这条 trace，若**每一轮都冷**，终值上界是 **12.0 倍**。

### 由此写下的定量预测（看到终值之前记在这里）

```
倍数 = 工作量比 × 吞吐比
     ≈ [3 ~ 12]  ×  [0.36]        ← 0.36 是 5 轮 trace 上实测的吞吐比
```

- 若工作比走到 **9~12**：倍数 **3.2~4.3×** ⇒ 命中用户要的 3~4 倍；
- 若工作比只走到 **3~4**（尾部会话变少、回来时不再被驱逐）：倍数 **1.1~1.4×** ⇒ 方向不死但不够；
- 吞吐比在这一档**会不会变**是第二个未知数：长会话下我们并发只有 1~2，
  但无控制那边**每次回来都要重算 60K** —— 它的吞吐会被自己的重算拖住，
  所以 0.36 这个数**偏向对我们更有利**是可能的。**两个方向都记下，不许事后只挑一个。**

**判据的用法**：终值出来后，先用 `atonce_report.py` 打出两个因子，
**先看是哪个因子没到位**，再解释结果 —— 不许直接对着倍数讲故事。

### 第二次中期读数（2026-10-10 19:30，222 步）

```
atonce25_default  222 步 | 必要 1,034,000 | 实测 uncached 6,276,335 | 倍数 **6.07**
                  轮>0 的 197 步里，冷回来 197 步 = **100%**
```

```
轨迹：60 步 → 1.85   →   222 步 → 6.07   →   （上界 12.0）
```

**工作量比在向上走**，而且**冷回来仍然是 100%** —— 这条臂**从来没有一次**会话回来
是暖的。剩下的 278 步上下文更大（会长到 65K），所以终值预期落在 **8~12 之间**。

### ⚠ 同一时刻引擎自报的一个数**推翻了我的吞吐比假设**

```
metrics.csv: num_running_reqs = 1.0,  num_queue_reqs = 22.0,  used_tokens = 80,703
```

**无控制臂的有效并发是 1，不是 92。** 因为长会话的上下文（~60K）占掉池子的 60%，
**一次只装得下一个**。5 轮 trace 上那个「无控制跑 92 并发」的图景**在这一档不成立**。

⇒ 我上面写的「吞吐比 ≈ 0.36」是**从 5 轮 trace 搬过来的**，**很可能是错的**：
两边都在并发 1 附近时，吞吐比应该接近 **1**，于是

```
倍数 ≈ 工作量比 × 1 ≈ 8~12×
```

**但我现在不把它当成结论** —— 两个理由：
1. 我们这个臂在并发 1 上会不会有大量空转（等 tool_wait）还没量到；
2. 无控制臂的 136K token/分钟里**大部分是它自己重算出来的**，
   它的「吞吐」与我们的「吞吐」不是同一个意义上的量（这正是
   `atonce_report.py` 把「工作量」与「吞吐」分两列打的原因）。

**终值按实测走。**

### 第三次中期读数（2026-10-10 20:43，441 步）—— 工作量比基本到顶

```
atonce25_default  441 步 | 必要 1,430,753 | 实测 uncached 15,605,272 | 倍数 **10.91**
                  轮>0 的 416 步里，冷回来 416 步 = **100%**
```

```
轨迹：60 步 1.85  →  222 步 6.07  →  441 步 **10.91**  （上界 12.0）
```

**工作量比已经基本走到上界**（441/500 步 = 93% 的必要量已发生）。
⇒ **结论完全由吞吐比决定**：

```
倍数 = 10.91 × (我们吞吐 / 无控制吞吐)
要 3×   ⇒ 吞吐比 ≥ 0.28
要 4×   ⇒ 吞吐比 ≥ 0.37
```

**无控制臂此刻的吞吐**（供对照）：15.6M uncached / 约 116 分钟 ≈ **134K token/分钟**。
5 轮 trace 上我们自己的吞吐是 35.9K/min ⇒ 若照搬，比值 0.27 ⇒ **约 2.9×**。
**这一档会不会更高，是本轮剩下的唯一未知数。**

## 追加（2026-10-10 19:00）：排队了第三条臂 `atonce25_default_nohc`

**为什么追加**：上面两条臂**都开 HiCache**。而 **SGLang 的 HiCache 是 opt-in 旗标**

文献里 Concur 也正是把 `SGLang`（默认）与 `SGLang w/ HiCache` 并列为**两个** baseline。

⇒ 于是三条臂构成一个干净的分解：

| 臂 | HiCache | 控制器 | 说明 |
|---|---|---|---|
| `atonce25_default_nohc` | 无 | 无 | **最朴素的「完全不管」**（= 开箱 SGLang） |
| `atonce25_default` | 有 | 无 | 「不管，但上了 host tier」 |
| `atonce25_foyer` | 有 | 有 | 我们的方案 |

之间卡会空几十秒，第二条链会抢进去撞车（CLAUDE.md 记过同型的坑）。

⚠ **本轮主判据仍是 `atonce25_foyer` vs `atonce25_default`**（只差控制器一个变量）。
`_nohc` 那条是**追加的第二个对照**，用于回答「无控制的崩溃里，多少来自控制器缺位、
多少来自 host tier 缺位」。**两个倍数都要报，不许只报大的那个。**

## 已知的口径坑（我在本轮之前踩过一次）

- **会话端到端必须从【到达】算，不是从【被提交】算**。2026-10-10 我用
  `submit_timestamp` 当起点，把「控制器让会话在门外等」的时间漏掉，得出过一个
  **72 倍**的假读数；真值 **1.8 倍**。`atonce_report.py` 里有注释钉住这条。
- 本 trace 的 `arrival_time` 全 0 ⇒ run 起点 t0 的估计（`min(submit_timestamp −
  arrival_time_ms/1000)`）退化成 `min(submit_timestamp)`。
  **但两个口径在本轮【仍然不同】**：控制器臂的会话要等许可才被提交，
  所以它的 `submit_timestamp` 晚于 t0，「提交→跑完」会**系统性偏短**。
  只有「到达→跑完」能跟无控制臂比。`atonce_report.py` 打的是后者。

## 为什么加这一条

`data31`（无筛选，中位 11 轮）给出 **1.43×**，而旧 trace（25 会话 × 20 轮）给出 **2.19×**。
差别在**会话长度**：短会话在抖动开始之前就跑完了，把无控制臂的冷回来比例摊薄
（data31 实测 75%，旧 trace 100%）⇒ 工作量比只到 4.75（理论 9.9）。

**用户 2026-10-12 定调**：换成「长程会话」数据集。**这不是造假** ——
PBKV 原文做过同一件事且明说：
> "**Below 60 workflows, evictions are too rare to differentiate any policy.** ...
> We therefore adopt a concurrency of 72 ... to evaluate all policies under reasonable pressure."

**关键差别在【说没说】**：范围要在 §V 第一句明写，抽样要机械可复现。
