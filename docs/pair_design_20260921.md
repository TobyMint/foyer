# 配对实验：重新设计（2026-09-21，按外部核查 Q5/E 条）

> **背景**：主表那个 4.2% 的领先（Foyer+HC 297.6 vs cap2 310.5）**不可归因**——
> 两个 run 相隔五天、跑在共享机器上，而我们实测邻居的 24 核任务能把墙钟拉大 17–25%。
> 所以设计了配对：两臂**并发**跑在两个 GPU 上，波次之间**交换 GPU**，
> 估计量是配对差。`scripts/check_pair.py` 负责先验配对前提（重叠率 ≥80%）再报差值。
>
> **外部核查指出原设计有三个不足**，本文档是修正后的协议。

---

## 一、原设计的三个问题（外部核查指出，已确认）

**问题 1：两臂会互相干扰，而干扰可能不对称。**
两臂共享同一台机器的 CPU、内存带宽、PCIe 与主机层缓存带宽。我们**已经测过**
这种干扰的量级：邻居的 24 核任务把我们的墙钟拉大 **17–25%**，而 GPU 解码只掉 2%
——**agentic 编排层是 CPU 侧的**。问题在于：如果干扰对两臂**不对称**（例如 Foyer
的控制循环本身要跑 Python、CPU 占用更高），那么配对差里就混进了"谁更吃 CPU"，
而不是"谁调度得更好"。**交换 GPU 消不掉这一项**，因为两臂始终在同一台机器上。

**问题 2：一轮交换不足以估计方差。**
现有设计是 A/B + B/A 两个波次，只能给出 2 个配对差。两个数无法区分"真实差值"
和"这一晚的机器状态"。

**问题 3：判决规则缺一个"同时跑有没有改变效应"的对照。**
并发跑是**有意**造成互相干扰的——这是设计的一部分（两臂经历同一条件）。但必须
验证：**并发跑出来的差值，与各自独跑时的差值，是不是同一个**。如果并发让差值
变大或变小，那这个差值就只在这个特定并发条件下成立。

## 二、修正后的协议

### 2.1 结构：N 个随机化交叉波次

```
波次   gpu2        gpu3        产出
 A     cap2+HC     Foyer+HC    配对差 d_A = wall(cap2HC) − wall(FoyerHC)
 B     Foyer+HC    cap2+HC     配对差 d_B = wall(FoyerHC) − wall(cap2HC)   ← 换卡
 C     cap2+HC     Foyer+HC    配对差 d_C                                    ← 换回
```

- **每波两臂并发**（同一机器条件），**波次之间交换 GPU**（消掉卡特定效应）。
- **估计量**：符号统一到 "cap2HC − FoyerHC" 后，取 N 个配对差的**中位与极差**。
  - 报 **N 个差值本身**，不只报均值——GPT 要的"报告每对差值"。
  - 用**中位**而非均值：本项目的逐会话比值已经吃过一次长右尾让均值翻方向的亏
    （`docs/claim_ledger_20260921.md` I2）。
- **N=3 起步**（A/B/C 已在队列里的 A/B 之外再加一个），若要更强再加。

### 2.2 独跑对照（"同时跑有没有改变效应"）

```
对照   gpu2        gpu3
 S1    cap2+HC     （空闲）    ← 独跑
 S2    Foyer+HC    （空闲）    ← 独跑
```

- 目的**不是**测绝对墙钟（那本来就是随机器状态漂移的），而是看
  **独跑差值 vs 并发差值**是否一致。
- 若两者差得远 → 并发条件改变了效应，配对差只能声明为该条件下的结论。
- **只有 2 条 run，但必须独跑**（另一张卡留空），所以是 2 × 5h 串行 ≈ 10h 挂钟。

> ⚠ **代价要说清楚**：3 个交叉波次 = 6 条 run = 30 卡时；
> 加 2 条独跑对照 = 10 卡时。合计 **40 卡时 ≈ 20 小时挂钟**（两卡并行时波次并行、
> 对照串行）。这比原设计（4 条 run、20 卡时）翻了一倍。

### 2.3 版本绑定（GPT D2 条）

**两臂必须用同一套控制器/runner 构建**，且**每个 run 的 metadata 要记下控制器 hash**。
理由：297.6 分钟那条 Foyer+HiCache 来自旧的 `budget3` 配置，
**不能用来验证新实现**。方法版本与实验行必须绑定，否则整张表在版本上不自洽。

具体做法：跑之前记录 `md5sum` 的 `controller_foyer.py` / `session_runner` / `run_matrix.py`，
写进本次实验的 README，并在表格脚注里引用该 hash。

### 2.4 判决规则（先写下来，免得事后找理由）

| 结果 | 结论 |
|---|---|
| 3 个配对差同号、且极差 < \|中位\|/2 | 效应稳定，可写进论文 |
| 3 个配对差**不同号** | **效应不稳定**，配对差不可作为主张，只能报"未检出差异" |
| 并发差值与独跑差值差得远 | 结论限定为"在两臂并发条件下的差值" |

**不许**：只报均值、只报最好的一波、或把不显著的差值写成"趋势"。

## 三、仍然存在的、无法用这个设计消除的局限

1. **两臂始终同机**。CPU / 内存 / PCIe 的相互干扰**无法通过交换 GPU 消除**，
   只能通过独跑对照**估计**它的影响。若独跑对照也指向同一方向，可信度提高；
   若不一致，结论必须限定条件。
2. **一晚的机器状态无法与"这一轮的效应"分离**。N 个波次只能估计**当晚内**的方差。
   跨夜的漂移仍然存在——这正是原设计失败的根源。**所以任何跨夜的比较都不要做。**
3. **N=3 仍然很小**。极差是弱方差估计，不构成置信区间。论文里**不许**把它写成置信区间。
