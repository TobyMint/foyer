# 发现：**Δ 里有相当一部分是「墙钟 × 前沿斜率」的几何项**，不是控制器的行为

2026-09-28，补跑第 1 组落地后做早期读数时发现。**这是本轮最重要的一处。**

## 一、机制

判决量是

```
delta = slo_pct − front_slo(wall_min)          （gen_table.py:221）
```

前沿是 (墙钟, SLO) 空间里的一条**分段折线**。所以 **Δ 对墙钟有一阶依赖**，
斜率就是前沿自己在该处的斜率：

```
锚点：(207.85, 28.93) (209.14, 68.47) (230.31, 81.88) (295.02, 91.59) (527.43, 94.79)

209.1 → 230.3 段：0.6336 pp/分   ← 最陡（最左端）
230.3 → 295.0 段：0.1500 pp/分
295.0 → 527.4 段：0.0138 pp/分   ← 最平
```

**在中段，判决带 ±1.0 pp 只值 6.7 分钟墙钟。**

## 二、把墙钟固定住，看还剩多少散布（「若各次墙钟相同」）

对 `replicates.csv` 的每一组：把该组**全部 run 的墙钟都换成组均值**
（SLO 保持各自实测），重算 Δ 全距。

```
组                                    n      实测Δ全距   墙钟固定后   墙钟占比
cap4+HiCache (frontier anchor)       2        7.55       5.11       32%
cap2+HiCache (frontier anchor)       2        1.13       1.00       11%
Foyer base (hw=0,t=0.95,h=3)         4        1.91       0.50       74%  ← 超过一半
horizon=1                            3        4.65       4.40        5%
cap3+HiCache (frontier anchor)       3        1.72       0.80       53%  ← 超过一半
cap3 device-only (paired)            2        6.74       4.90       27%
horizon=2 (the closest arm)          2        0.51       1.00      −95%
scans the queue                      3        1.87       0.50       73%  ← 超过一半
single-flight off                    2        0.68       0.70       −3%
```

**读法**（不是方差分解 —— 墙钟与 SLO 是相关的，所以只做「墙钟取组均值」这一个反事实）：

- **三组的 Δ 散布有一半以上来自墙钟**（Foyer base 74%、`scans the queue` 73%、
  cap3+HiCache 53%）；
- 两组是**负的**（horizon=2、single-flight off）—— 那两组里墙钟与 SLO 的变动
  本来就在**互相抵消**，把墙钟钉住反而让散布变大；
- 论文引的「0.5 to 4.6 pp」是**五个控制器组**的 min/max：控制器组实测是
  0.51 / 0.68 / 1.87 / 1.91 / 4.65 ⇒ **0.5 与 4.6** ✓ 与正文相符。

## 三、头条那条臂（`scans the queue`）的三次读数

```
run              wall      slo   front_slo    delta   判词
foyer_scan       266.3   88.5886   87.2842   +1.3044  ABOVE
foyer_scan_r2    262.6   88.8889   86.7289   +2.1600  ABOVE
foyer_scan_r3    271.7   88.3884   88.0936   +0.2948  ON
```

实测 Δ 全距 **1.8652 pp**。其中：

```
墙钟项（front_slo 的变动）  86.7289 → 88.0936 = 1.3647 pp   ← 73%
SLO 项                       88.3884 → 88.8889 = 0.5005 pp   ← 27%
```

**反事实**：若三次墙钟都取组均值 266.9 分（`front_slo = 87.3742`），则

```
r2 : 88.8889 − 87.3742 = +1.5147   ABOVE
scan: 88.5886 − 87.3742 = +1.2144  ABOVE
r3 : 88.3884 − 87.3742 = +1.0142   ABOVE   ← 刚过带（带是 1.0）
```

⇒ **三次会全部落在带上方**（第三次只多 0.014 pp）。

## 四、⚠⚠ 偏差的方向：**对论文的负结论有利**，必须写出来

注意上一条 —— 把墙钟钉住之后，**三次都越线**，正文现在写的是「two of three,
not a stable crossing」。也就是说：

> **几何项惩罚跑得慢的 run**（墙钟长 ⇒ `front_slo` 抬高 ⇒ Δ 变低），
> 而 `scan_r3` 恰好是三次里最慢的一次（271.7 分），**它掉出带外有一部分是这个惩罚**。

所以这一处偏差**帮的是论文的负结论**。本项目有明文纪律：
**「偏差方向对自己有利时更要写出来」**。这条不能因为「结论不动」就不记。

⚠ **但也不能反过来说「其实三次都越线、负结论不成立」**：
- 正文**已经**报了一条**替代时钟**（把许可等待也算进去的「permit clock」），
  那条时钟下**三次一条都不越线**（−0.56 / +0.96 / −1.07）—— 结论另有支撑；
- 墙钟与 SLO 是**相关的**（跑得慢的 run SLO 也低），所以「钉住墙钟」不是一个
  物理上可实现的对照，它只是把**几何项**单独拎出来看；
- 前沿的构造本身是对的：一次 271.7 分钟的 run **就应该**在 271.7 分钟处被比较。

## 五、这件事真正的用处：**补跑落地的解读**（已写进 `POST_RUN_PLAN.md`）

补跑要让这条臂**再多两次读数**。而第 1 组的实测显示：**这次补跑的墙钟比历史长
~5–7%（309.5 / 304.5 vs 293.2）**。若这个漂移对 8 个组普遍成立，那么：

> **每条臂在补跑里的 Δ 会被系统性地压低（跑得慢 ⇒ 基准抬高）**，
> 而**压低的方向正好是「看起来更在带下方」= 对负结论有利**。

⇒ 落地时必须做分解（`Δ差 = SLO分量 − front_slo分量`），并且：

- **若某条臂的判决翻转，先看是哪个分量**；墙钟分量主导的话，
  **不许**写成「控制器变了」或「重复散布变大了」——那是**运行时长漂移**；
- **若补跑让越线的那条臂不再越线**，也**不许**直接写成「越线不重现」——
  要先扣掉墙钟项，再说是哪一个在起作用。

## 六、要不要写进论文：**待定，记在这里**

- **支持写**：审稿人若问「同一条臂三次差 1.9 pp，为什么？」，现在正文没有答案；
  几何项是个**机制性**的解释，写出来比「run-to-run spread」更有信息量。
  而且它**预答**了「你的判决量怎么会同配置差这么多」。
- **反对写**：(a) 正文正好卡在 11 页硬限，加句子有越页风险；
  (b) 结论**不动**（正文已用 permit clock 那条更强的证据）；
  (c) 一旦写，就得把「0.5 to 4.6 pp」重新表述成「一部分是几何项」，
  牵动 §V/§VI 好几处。
- **决定**：**先不改正文**。等补跑落地后一并看 ——
  若补跑出现「因墙钟漂移而翻转」，那就**必须**写（那时它不再是解释，而是数据的一部分）；
  若没出现，作为 §V 的一句披露 / Limitations 的一句，在最后一轮篇幅结算时定夺。
