# 台阶的独立验证与分解（2026-09-21）

> 全部数据来自磁盘上已有的 `metrics.csv`，**没有新跑任何实验**。
> 目的：用与墙钟**完全不同的一个量**去独立检验"墙钟-并发是台阶"这个中心主张。
> 如果台阶是真的，它应该同时出现在吞吐上；如果只出现在墙钟上，那它更可能是
> 调度/记账的假象。

---

## 方法

对每个完整 run（有 `summary.json`、且跨度 > 60 分钟——排除掉在跑的 cap4_hc 和
两个废弃的 `*_fixed` 残骸），从 `metrics.csv` 算：

```
墙钟        = 最后一个 ts - 第一个 ts
总生成 token = max(generation_tokens_total)      （计数器，取 max 防重启归零）
有效吞吐     = 总生成 token / 墙钟
引擎忙占比   = num_running_reqs > 0 的采样占比
忙时吞吐     = 有效吞吐 / 引擎忙占比
引擎并发     = mean(num_running_reqs)
```

**可比性检查（必须先过）**：所有 run 回放同一条 200 会话 trace，所以总工作量应当
相同。实测总生成 token 落在 **700,704 – 706,021**，离散度 **0.76%**。

```
14 个 run 的总生成 token 极差 = 5,317 token = 0.76%
```

所以"吞吐"的差异不是"干了不同的活"造成的，**分母是干净的**。这一条不成立的话
下面全部作废。

---

**这就是中心主张的独立验证**：墙钟掉 14% 和吞吐涨 20% 是**同一个事实的两种量法**，
而且两个量是从完全不同的原始量算出来的（墙钟来自 run 的时间戳，吞吐来自
`generation_tokens_total` 计数器）。它们对上了。

## 分解：约一半是"少空转"，约一半是"忙的时候更快"

```
吞吐比      43.5 / 36.3 = 1.20
忙占比比    88.5 / 81.6 = 1.08
忙时吞吐比  49.2 / 44.4 = 1.11
检验        1.08 × 1.11 = 1.20  ✓  与总比一致
```

所以台阶的另一侧不是单纯"少闲着"：

- **+8%** 来自引擎更少空转（忙占比 81.6% → 88.5%）
- **+11%** 来自**忙的时候每秒钟解码更多 token**（44.4 → 49.2）

第二项是**批处理收益**——更多并发序列共享同一次前向。

> 我在 `docs/three_paths_20260921.md` 里写过"至于'接住'的具体机制是解码批处理
> 还是别的，我们**没有测**，不要在论文里断言"。**这条现在可以改了**：忙时吞吐
> 确实随并发上升（+11%），是批处理的直接证据。仍然注意这是**跨策略的观察比较，
> 不是受控实验**——策略之间除了并发还差着命中率等，所以这是**证据**，不是**因果**。

## 一个反例，把结论收窄（重要）

`pois200_default`（完全无管控）**破坏了"并发高就快"的简单版本**：

```
引擎并发 1.69（最高档）  忙占比 88.6%（高）  但 tok/s 只有 39.6，忙时只有 44.7
```

它并发和忙占比都在高组，吞吐却掉回低组。原因很清楚：它的**缓存命中率只有 1.6%**
（主表里唯一一个），几乎所有前缀都要**重算**。对照 §216× 的测量：
重算比搬运贵 216 倍，所以它的算力被 prefill 吃掉了，没留给 decode。

**所以正确的判据不是"并发高"，而是"并发高 ∧ 命中率没崩"**：

```
cap3_r2 / cap4 / aimd2 / cap5   并发 1.44–1.62   命中 45.9–49.8%   → 43–46 tok/s
default                         并发 1.69         命中  1.6%        → 39.6 tok/s
```

## 一个对我们不利、但必须自己先说清楚的推论

在引擎并发 ~1.4 这一点上，**批处理收益（+20%）大于命中率损失**：

```
cap4    命中 45.9%   45.5 tok/s   257.6 分
Foyer   命中 65.6%   39.2 tok/s   299.3 分
```

Foyer 的命中率比 cap4 **高 20 个百分点**，吞吐却**低 14%**。也就是说
**在当前这个负载/硬件上，多 20pp 的命中率买不回少掉的那部分批处理**。

这把我们问题的性质说清楚了：Foyer 的保守不是"为了质量牺牲了一点速度"，
而是**停在了批处理收益的拐点之前**。这正是 #32（rl90fix/rl99fix）要判决的——
记账修好之后引擎并发能不能从 1.12 推到 1.4 一线。

**如果推不上去**，那么诚实的结论是：在 3090 + 7B + 这张 trace 上，
准入控制无法同时拿到批处理收益和质量，论文的主张要相应收窄（不能声称帕累托改进）。

## §4 会话并发 vs 引擎并发：控制变量选错了

主表用的是**会话级**并发（in-flight sessions，含 tool_wait），
`num_running_reqs` 是**引擎级**（真的在 GPU 上跑）：

```
         会话并发   引擎并发   引擎/会话
cap1       1.00      0.64      0.64
cap2       1.99      1.04      0.52
Foyer      2.12      1.12      0.53
cap4       3.94      1.48      0.38
```

**会话级并发把引擎占用高估了约 2 倍，而且这个比值不是常数**（0.38–0.64，
随并发升高而下降——因为放进来的人越多，处于 tool_wait 的比例越大）。

这与主表"账本读到 92%、引擎实测 52%"是**同一件事的两个侧面**：

```
逻辑上下文之和 → 物理驻留 KV      高估 ~1.8×   （前缀共享）
在飞会话数     → 引擎在跑请求数   高估 ~2.0×   （tool_wait）
```

**两个都指向同一条主张**：按会话侧的量做准入，系统性地高估引擎的真实占用，
于是**系统性地过度保守**。这就是论文第 5 条主张（校准规则）的实证基础，
而且现在有**两个独立来源**支撑它，不是一个。

## §6 更强的检验：把混淆彻底去掉（同日稍后补充）

§2 的分组比较有个我自己该先说的问题：**两组不只是并发不同，还是不同策略**
（高组主要是静态 cap，低组主要是 Foyer）。所以它分不开"更并发→解码更快"和
"静态 cap 有别的什么不同"。

**同一 run 内配对可以彻底去掉这个混淆**：每个 5s 采样的区间，用区间内新增 token
除以区间时长得到瞬时速率，与该区间**起点**观测到的 `num_running_reqs` 配对。
两个数来自同一个 run、同一个策略、同一个 server。

```
run                        n=1      n=2      n=3      n=4
pois200_cap2              35.3     74.7        -        -
pois200_foyer             34.3     72.5     91.6        -
pois200_foyer_t85         34.3     58.7     82.6        -
pois200_cap4              34.2     58.7     87.6    108.3
pois200_foyer_rl90        30.4     58.7     77.9    153.4
pois200_foyer_rl99        32.6     50.5     64.4     68.4

跨策略：  n=1 均值 33.5（30.4–35.3，离散 15%）
          n=2 均值 62.3（50.5–74.7，离散 39%）
          n=3 均值 80.8（64.4–91.6，离散 34%）
          n=4 均值 110.0（68.4–153.4，离散 77%，但只有 3 个 run、22–24 个采样点，别依赖它）
```

**结论**：

1. **每个 run 内部，速率都随并发单调陡升**，1→2 大致翻倍（均值 +86%）。
   这是批处理的直接证据，且**没有跨策略混淆**。§3 里那个"+11% 忙时吞吐"
   现在可以升级成这个更强的说法。
2. **曲线是共享的形状，不是普适常数**：同一并发下跨策略离散 15–39%。
   `rl99` 在每一个 n 上都最低（32.6/50.5/64.4/68.4）——它的硬阀抖动。
   所以"引擎常数"这个说法**过强，不要说**。
3. **聚合差异由"分布"解释**：看各 run 花在 n≥2 的采样占比——

```
cap2     n=1 73%  n=2 27%              → 27% 的时间在 n>=2
Foyer    n=1 70%  n=2 26%  n=3  4%     → 30%
cap4     n=1 48%  n=2 39%  n=3 12%  n=4 1%  → 52%
```

cap4 有一半时间在 n≥2，cap2 只有四分之一。乘以上面那条曲线，就是聚合吞吐的差。

（脚本 `scripts/batching_curve.py` 一键复现，出图 `fig_batching.png`。）

## §7 ⚠ 这条结果反过来削弱了"台阶"的锐度（必须自己先说）

这是 §6 做完之后才看清的，而且**它对我自己的中心主张不利**：

**同 run 曲线是平滑且凹的（33.5 → 62.3 → 80.8 → 110）。** 如果一个策略只是
把并发**分布**平滑地往右挪，聚合吞吐就应该**平滑上升**，墙钟就应该**平滑下降**——
不该出现台阶。

回头看墙钟数据到底长什么样：

```
并发 1.03–1.33：364.0, 310.5, 339.9, 321.8, 299.3, 297.6, 362.0, 300.2
                → 在 297–364 之间震荡，没有趋势
并发 1.44–1.62：259.2, 257.6, 264.4, 267.0
                → 明显更低的一簇
中间 (1.33, 1.44)：**一个观测点都没有**
```

所以诚实的状态是：

- 数据**确实落在两个带里，中间是空的**——这一点是事实。
- 但**"台阶（不连续）"与"陡峭但平滑的下降"这两种解释，现有数据分不开**，
  因为分界处恰恰没有采样。
- 而且 §6 的平滑曲线**倾向于支持后者**（平滑）。

**所以"台阶"这个词目前是过强的。** 现在能说的准确表述是：
"数据分成两簇、中间无观测；过渡是台阶还是陡降未被分辨。"

**`cap3_fixed` 因此变成了贡献 1 的关键测量**，而且比之前认为的更关键：
cap=3 会话对应的引擎并发正落在 1.33–1.44 这个缺口里。

```
cap3_fixed 落在 ~300 分（和低簇一致）→ 过渡是陡降，且比想象的更陡 → "台阶"站得住
cap3_fixed 落在 ~258 分（和高簇一致）→ 缺口被填上，两簇其实连续 → "台阶"要撤回，
                                          改说"平滑下降 + 我们采样不足"
```

**这两种结果都是好结果**：前者给出一个真正的相变，后者是一个关于"采样密度决定
你看到几个台阶"的方法学发现。但**必须等它落地才知道写哪个**。

在此之前，草稿与决议里所有"台阶"的表述都已标注为待判决，摘要里也已经改成
"分成两簇、中间无过渡带"这种不预设不连续的说法。

1. `default` 的命中率 1.6% 是**一个** run，且它是唯一无管控的 run。要把它当作
   "命中率崩了吞吐就掉"的证据，最好补一次重复（它同时也能给"无管控"提供误差棒）。
2. 忙时吞吐 vs 并发的关系只有 14 个点、且是跨策略的。要做成论文里的图，
   应该**按策略分色**，让读者看到这不是一条曲线而是两簇。
3. ~~本节所有数字应可由 `scripts/throughput_decomp.py` 一键复现~~ **已写**
   （`scripts/throughput_decomp.py`），且脚本内置了"总生成 token 离散度 > 5% 就
   报错退出"的可比性闸门——因为这一节的全部结论都建立在"分母一样"之上，
   而这一点必须由脚本自己每次检查，不能靠人记得。
