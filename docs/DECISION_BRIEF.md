## 三、还站得住的

```
A. 问题陈述（强）
   长上下文 agentic 负载下，KV 缓存总容量远小于工作集（303K vs 1.14M token）。
   不受控的引擎在这种条件下把 90% 的算力花在重复 prefill 上（浪费 10.02x），
   而且会打死会话（big27 上 4 个）。
   我们的准入控制器把浪费降到 3.04x，整批快 1.43x，18/19 个会话更快。

B. 内存效率论证（强、可量化）
   无控制臂要 46.5 GB 主机内存才到 178.8 分；我们用 11.6 GB 就到 165.2 分。
   ⇒ 省 35 GB。每 token KV = 56 KiB 是可复算的。

C. 缓存容量敏感性分析（已做完，是一个诚实的负面结果）
   hc2/hc8 四个点表明：时间复用（我们的做法）和空间复用（加大 host 缓存）
   是【替代品】。这一点必须主动写，藏不住。

D. 一个尚未验证的机制（§18.4）
   device 命中免费，host 命中要把 KV 从主机内存搬进显存。
   ⚠ 搬运速率【没有实测】：§18.3 的 286 MB/s 是从「prefill 时间」倒推的，
     而那个 prefill 时间本身是估的；§21.3 已证明这两个数循环依赖。
     所以这里只能说"有搬运费"，不能说具体多快。
   而 SGLang 的 `sglang:cached_tokens_total{cache_source="device"|"host"}`
   本来就分开计 —— 解析器 bug 已修，下次 hc run 就有分解。
   ⇒ 若成立，准入应该按【命中的层次】定价，而不是命中/未命中二值。
```

## 六、这一夜里修好的四个真问题（都是会静默毁数据的那种）

```
① permit 文件按 lane 命名，而 lane 永远是 atonce
   ⇒ 两条并行 run 的控制器写同一个文件，准入名单互相覆盖。
      改成按 run 名命名。（run_matrix.py，三处）
② monitor.py 的 fetch() 用 out[name] = v，同名不同标签的序列互相覆盖
   ⇒ SGLang 本来按 cache_source 分开计的 device/host 命中被叠成一条。
      改成把 cache_source 带进 key，COUNTERS 加两列。
      代价：2026-10-17~18 那四个臂的分解【取不回来】，只能重跑。
③ drive_one.sh 不抗 SIGHUP ⇒ ssh 链路一断，等卡的进程就被收走。
      加 trap '' HUP。
④ 没有热降频守卫 ⇒ 在 345MHz 的卡上闷头跑 100 分钟才发现慢 10 倍。
      加空闲温度门 + 运行时 SM 时钟门，不达标就自杀并留 VOID_THERMAL 标记。
```
