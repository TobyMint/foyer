# 小论文 idea

给显存受限的 GPU 上的 agentic 服务做会话级准入控制——在请求进推理引擎之前决定放行还是排队。

和上周相比，这周补充了更多的数据和实验，paper 中的创新点的偏向也在跟着数据调整。



## 创新点

1. 容量核算准入。 准入时刻显式核算「池子容量 / 在场会话占用 + 预测增长 / 新到会话体量」，用命名许可保证准入计划与执行一致。

$$Admit(s) \iff m\left[\sum_{i \in \mathcal{A}}\left(x_i + \hat{g}_i\right) + \left(x_s + \hat{g}_s\right)\right] \le \rho C_{\mathrm{pool}}$$

1. 分层缓存的状态保留式挂起。 需要腾空间时把会话 KV 从显存挪到主机层，L1 立即释放、历史保留；复活时只需搬回，不必重算。实测搬运 0.005 ms/token 对重算 1.08 ms/token，差两个数量级。
2. 等待-代价比的复活排序。 被挂起的会话不按 FIFO 回归，按 $W/T$ 排序，等待越久、复活代价越小的越先回来。

现有工作（如 Concur）盯着缓存命中率做反馈，信号变坏的时候，缓存系统已经崩溃过了。我们看在途请求的体量做前瞻预估，请求本身的体量在排队中就已经是已知的，不必等系统出问题之后再处理。

**第 2、3 条要说清强度。**第 2 条推翻了我们自己的旧结论——先前看到的"并发↑ → 单请求速率↑"是测量方法造出来的假象，换成逐请求测量后方向反转；但它**只能算关联，不能算因果**，因为 TTFT 与解码窗口的时间起点不同源，`first_token_ms` 也不保证恰好一个 token。第 3 条本周拿到了更大的样本（8910 拍），结论比原来更强。

### 二、性能上，我们落在前沿的哪个位置

同一批 run、两条口径，赢家不同：

- **对缓存命中率**：`cap4 + HiCache` 在最左上。
- **对 SLO**：同一个点掉到左下，`Foyer + HiCache` 在最上。

这周新出的点是 `cap4 + HiCache`：它同时拿到 **219 分钟**和 **68.1% 命中率**，而 `cap4` 是快但丢缓存（45.9%）、`cap2` 是保缓存但慢（310.5 分钟）。**分层缓存把"保缓存 vs 提并发"这个取舍本身消掉了**——而且它是个静态配置，没有控制器。

**门槛是选的不是测的。** 取 SLO ≥ 85% 时我们的 `Foyer + HiCache` 领先 `cap2`**4.3%**；取 60% 时 `cap4 + HiCache` 领先 **26%**。同一份数据，门槛一换赢家就翻。

而那 4.3% 的幅度，**与控制器自身的波动同阶**——同一配置重复三次是 286.0 / 295.7 / 297.6，极差 4.1%——所以它现在还不是一个可以写进论文的主张。

这个数本来指望**配对实验**（两臂并发、同机器同条件）来答。**配对跑了两波，都没答成**：调度把两臂排成了一前一后，实际重叠只有 3% 和 5.6%，配对差里仍然带着设计本来要消掉的那个量。

但它买回了一批**同配置重复**，而重复把问题答了：`Foyer + HiCache` 三次 286.0 / 295.7 / 297.6，`cap2` 两次 310.5 / 310.6——**两组不重叠，最差的 Foyer 仍比最好的 cap2 快 12.9 分钟**。另外静态档跨天、跨卡只差 0.03%，说明波动不来自机器，来自控制器自己。

### 三、本周核验/修掉的三处

- **「三个并发会话需要 117% 池子，所以必须超订」**——那是**五个**会话的数，四个是 91.4%，装得下。
- **`cap3_r2` 曾被我们误判，读源码后纠正**——曾据"195/200 次准入发生在 `active=3`"判定它跑的是 cap4。读源码发现 `active` 记的是**自增之后**的计数（CAS 是 `while cur < cap`，`cur = cap` 不可达），所以那个签名**正是 cap3 应有的样子**。它一直是有效的 cap3。
- **一次 run 静默停摆 29 分钟，重启控制器后立刻恢复**——`rl90fix` 在 894/999 处停死：runner 一个请求都没在提交，而控制器认为没人在等。我们一度判定为"控制器状态漂移"，**这个归因已撤回**：离线重放得到 21 个在等的会话而在线是 0，是因为重放脚本漏处理了 `resume` 事件；补上之后两边一致。**停摆现象是真的，机制仍不明**，已加了一条只查症状、不依赖机制的检测。

## 之后怎么做

1. **定口径**：性能主张 / 测量主张，二选一——因为上面那个门槛问题。
2. **`cap3_fixed` / `rl90fix` 都已落地**：`rl90fix` 的记账修复（`committed ≤ 红线` 的占比 50.6% → 57.2%）验收结果是**机械目标达成、结果指标测不出改善**（墙钟 300.2 → 319.1，命中率 57.7% → 53.7%）——且它带着 17.1% 的邻居占核重叠。它和 `cap3_fixed` 现在的主要价值是**给同配置重复添了两条**，不是补工作点。
3. **五类资源数据累积**：下一个控制器路线的 run 起自动记录。
4. **控制器加自检**：每 N 拍从零重放事件、与增量状态比对——用来查明那次**停摆**为什么会发生、为什么重启能恢复。**注意自检本身现在还不自洽，不能先信它的输出。**
