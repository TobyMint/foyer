# 26-09-21周报

# 小论文 idea

给显存受限的 GPU 上的 agentic 服务做会话级准入控制——在请求进推理引擎之前决定放行还是排队。

和上周相比，这周补充了更多的数据和实验，paper 中的创新点的偏向也在跟着数据调整。、

## 创新点

1. 容量核算准入。 准入时刻显式核算「池子容量 / 在场会话占用 + 预测增长 / 新到会话体量」，用命名许可保证准入计划与执行一致。

$$Admit(s) \iff m\left[\sum_{i \in \mathcal{A}}\left(x_i + \hat{g}_i\right) + \left(x_s + \hat{g}_s\right)\right] \le \rho C_{\mathrm{pool}}$$

1. 分层缓存的状态保留式挂起。 需要腾空间时把会话 KV 从显存挪到主机层，L1 立即释放、历史保留；复活时只需搬回，不必重算。实测搬运 0.005 ms/token 对重算 1.08 ms/token，差两个数量级。
2. 等待-代价比的复活排序。 被挂起的会话不按 FIFO 回归，按 $W/T$ 排序，等待越久、复活代价越小的越先回来。

现有工作（如 Concur）盯着缓存命中率做反馈，信号变坏的时候，缓存系统已经崩溃过了。我们看在途请求的体量做前瞻预估，请求本身的体量在排队中就已经是已知的，不必等系统出问题之后再处理。

## 目前的状态

### 一、本周测出来的四件事

| | 结论 | 数字 |
|---|---|---|
| 1 | **不治理会坍塌** | 命中率 1.6%、TTFT 中位 29.6 分钟、SLO 3.0%、999 步里 121 步失败 |
| 2 | **逐请求解码速率不随并发上升** | 并发 1/2/3 为 36.4 / 34.6 / 33.4 tok/s；会话内配对中位 0.95–0.97 |
| 3 | **会话侧与引擎侧之间没有稳定换算系数** | 同一时刻、同一会话集合上比值 0.72–1.44，**符号会翻转** |
| 4 | **"搬"比"算"便宜两个数量级** | 0.005 vs 1.08 ms/token |

第 3 条是本周新得的。第 2 条**推翻了我们自己的旧结论**——先前看到的"并发↑ → 单请求速率↑"是测量方法造出来的假象，换成逐请求测量后方向反转。这两条也直接支撑了创新点 1 和 2。

### 二、性能上，我们落在前沿的哪个位置

同一批 run、两条口径，赢家不同：

- **对缓存命中率**：`cap4 + HiCache` 在最左上。
- **对 SLO**：同一个点掉到左下，`Foyer + HiCache` 在最上。

这周新出的点是 `cap4 + HiCache`：它同时拿到 **219 分钟**和 **68.1% 命中率**，而 `cap4` 是快但丢缓存（45.9%）、`cap2` 是保缓存但慢（310.5 分钟）。**分层缓存把"保缓存 vs 提并发"这个取舍本身消掉了**——而且它是个静态配置，没有控制器。

| 策略 | 墙钟(min) | 命中率 | SLO% | TTFT p50 |
|---|---|---|---|---|
| cap4 + HiCache | 219.0 | 68.1% | 63.4% | 5473 ms |
| cap4 | 257.6 | 45.9% | 55.7% | 7215 ms |
| Foyer + HiCache | 297.6 | 69.7% | 89.8% | 2228 ms |
| cap2 | 310.5 | 67.7% | 89.5% | 2183 ms |

**门槛是选的不是测的。** 取 SLO ≥ 85% 时我们的 `Foyer + HiCache` 领先 `cap2` **4.3%**；取 60% 时 `cap4 + HiCache` 领先 **26%**。同一份数据，门槛一换赢家就翻。

而那 4.3% 的幅度，**与跨天不可归因的量级同阶**——所以它现在不是一个可以写进论文的主张。能干净回答它的只有**配对实验**（两臂并发、同机器同条件），协议已定。

### 三、本周核验/修掉的三处

- **「三个并发会话需要 117% 池子，所以必须超订」**——那是**五个**会话的数，四个是 91.4%，装得下。
- **`cap3_r2` 实测跑的是 cap4**——`cap` 字段写着 3，但 195/200 次准入发生在 `active=3` 时，落地后 4 个在飞。已作废重跑。
- **控制器状态漂移会让 run 静默停摆**——`rl90fix` 在 894/999 处停死 29 分钟：runner 一个请求都没在提交，而控制器认为没人在等。把控制器自己的规则离线重放一遍，得到 21 个在等的会话；在线状态却是 0。重启控制器后立刻恢复（894 → 919）。**机制尚未查明**，已加了一条只查症状、不依赖机制的检测。

## 之后怎么做

1. **定口径**：性能主张 / 测量主张，二选一——因为上面那个门槛问题。
2. **`cap3_fixed` / `rl90fix` 验收**：判据是事件重建 `max active ≤ 3` 与记账不变量，不是看墙钟。
3. **五类资源数据累积**：下一个控制器路线的 run 起自动记录。
4. **控制器加自检**：每 N 拍从零重放事件、与增量状态比对——这是查明漂移机制的唯一办法。
