## 一、今天最重要的四个发现

### 1. 「Foyer 快 4%」不能当卖点（§三十八、§三十九）

```
               墙钟(min)      SLO%        实测并发
foyer_hc    279.6 / 289.4 / 291.1   89.3–89.8   2.06–2.14
cap2+HC     294.8 / 304.3           90.6–91.6   1.96–1.99
```

**Foyer 快 1.2–4.5%，但 SLO 低 0.8–2.3pp。两者都在 Pareto 前沿上，互不支配。**
而控制器自身重复跑一次就差 4.1%。**"更快"的幅度和噪声同阶。**

更麻烦的是：**换一个 SLO 门槛结论就反过来。** 门槛设 85%，Foyer 最快；
门槛设 90%，Foyer 三条全部够不到，只剩 cap2+HC。

### 2. 静态 cap 会掉进"驱逐螺旋"，而且它自己看不见（§四十）

同配置、同 trace 的两次 `static=3`：

```
cap3_r2     命中率 63 → 27（单调下滑）   单步耗时 22s → 66s   全程 SLO 62.2
cap3_fixed  命中率稳在 55 左右           单步耗时稳在 30s      全程 SLO 74.4
```

**机制**：静态 cap 只会数"现在几个在跑"，看不见池子被驻留会话占了多少。
run 推进 → 驻留变多 → cap3 照放 3 个 → 新来的驱逐别人的前缀 → 命中率掉 →
每个请求要重算更多 prefill → 占位更久 → 压力更大。**正反馈。**

**这是真的**，而且是实测的机制。**但它不是 Foyer 的卖点**（见第 4 条）。

### 3. 但 cap2 **不会**掉进去（§四十一）

```
cap1    (94.8, 段标准差 2.5)   稳 —— 远在悬崖这侧
cap2    (89.5, 段标准差 6.4)   稳
cap2+HC (91.6, 段标准差 3.8)   稳   ← 全表最稳
Foyer   (89.8, 段标准差 4.4–5.0) 稳
cap3    (62–74, 段标准差 8–21)  不稳 ← 骑在悬崖上
cap4    (55.7, 段标准差 16.1)   不稳
```

**"静态不稳、自适应才稳"这个说法是错的，我上午写过，下午自己推翻了（§四十→§四十一）。**
正确的是：**越过悬崖才螺旋**，而 cap2 没越过。

### 4. Foyer 根本没跑到悬崖边上——它几乎停在 cap2 的位置（§四十三）

```
cap2        并发 1.99
foyer_hc    并发 2.06     ← 只高 3.5%
cap3_fixed  并发 2.89     ← 悬崖在这儿
cap4        并发 3.94
```

**而且把它往悬崖推就崩**（`foyer_rl90fix` 推到 2.45 段标准差就 15.5）。

**所以控制器比不过一个固定数字**：cap3 能稳在 2.9，Foyer 到 2.45 就不稳。

## 二、为什么（这一步只查到一半）

控制了 8784 个周期里，**42% 在拒绝准入**。那些周期里：

```
投影       121.8% 池     ← 控制器认为超了
预算        95.0% 池
真实占用     67.6% 池     ← 引擎只用了三分之二
→ 池子空着 27%，门外排着 69 个会话
```

**但「预留是浪费」这个直觉被它自己的消融反驳了**（§四十四）：
代码里本来就有 `predictor={ema,zero,global,oracle}`，
而 **`oracle`（精确知道未来增长）比默认 EMA 更保守**（并发 0.66 vs 1.20）。
**说明真实增长比 EMA 估的更大——控制器是在低估，不是虚报。**

去掉预留是**拿 SLO 换并发**，不是修 bug。别的 trace 上标价：
`budget200c` +50% 并发 / −4pp SLO；`load25c` +27% / −0.8pp。
**pois200 上还没量过。**

唯一还没排掉的怀疑：作为**基数**的 `ctx_sum`（每会话"曾经有多少上下文"之和）
可能高估驻留——引擎报 50% 占用，而 ctx_sum 报 56.9%。**基数虚高 + 预留再叠一次 = 双重保守。**
