## 现在论文主张什么

### 贡献 1：并发买到的是并行度，不是效率

**测量方法**：每个请求的原始记录（`steps.jsonl`）里有它自己的
`submit_timestamp`、`complete_timestamp`、`first_token_ms`、`output_len_actual`。

```
逐请求解码速率 = (output_len - 1) / (total_duration - first_token_ms)
```

（首 token 在 TTFT 时刻到达，其余 token 摊在剩余时间里。）
并发取该请求 `[submit, complete]` 窗口内 `num_running_reqs` 的均值。
只保留 `output_len ≥ 32` 的步——更短的轮次被 `finish_reason=length` 截断。

**结果**（6 个 run，同一 trace，不同并发策略）：

| 并发 | run 数 | 逐请求 tok/s | 命中率 | 未缓存 prompt | 上下文 |
|---|---|---|---|---|---|
| 1 | 6 | **36.4** | 52.3% | 14,580 | 33,554 |
| 2 | 6 | **34.6** | 55.2% | 10,937 | 26,739 |
| 3 | 5 | **33.4** | 64.5% | 7,182 | 21,840 |
| 4 | 1 | 28.7 | 57.2% | 8,628 | 20,554 |

**每请求解码速率不随并发上升，反而略降（1→2 为 0.95×）。** 六个 run 里五个单独看
方向一致（cap2 42.2→40.5，Foyer 41.0→37.9，t85 38.6→35.1，rl90 32.5→31.4，
rl99 32.2→29.0→25.6）。聚合吞吐随并发上升，**只因为同时在飞的请求更多**。

**推论**：若聚合吞吐 ≈ 并发 × 逐请求速率，且速率随并发缓降，则墙钟近似正比于
并发的 −1/2 次方。代入实测：`(1.48/1.04)^0.5 = 1.19`，实测墙钟比
`310.5/257.6 = 1.21`。因此数据支持一条**平滑单调**的曲线。

**主表观察**：14 条策略里，引擎并发 <1.4 的墙钟全部落在 297–340 分钟且彼此不单调
（并发 1.11 的 321.8 分比 1.04 的 310.5 分还慢）；≥1.4 的落在 257–271 分钟；
**中间 (1.33, 1.44) 一个观测点都没有**。我们**不**把这叫台阶，只说"两簇、中间未采样"。

### 贡献 2：控制变量必须取实测物理占用，不能取会话侧台账

同一批 run 上测到**两个独立**的系统性高估：

```
逻辑上下文之和 → 物理驻留 KV      高估 ~1.8×   （前缀共享：多会话共享前缀，
                                                  逻辑和远大于实际驻留）
在飞会话数     → 引擎在跑请求数   高估 ~2.0×   （tool_wait：会话在等工具返回时
                                                  不占引擎，但被算作"在飞"）
```

第二个的比值还**不是常数**，随并发从 0.64 漂移到 0.38。

实证：我们的控制器账本在准入时刻读到池子占用的 **92%**，而引擎遥测实测只占 **52%**。
控制器忠实地执行了一个偏高两倍的预算，因此**系统性过度保守**。

### 我们的控制器（Foyer）

按贡献 2 设计：只读引擎遥测的实测物理占用，不读会话台账。用命名许可把
"计划放行的会话集合"与"实际运行的集合"绑定。

主表上（泊松 200 会话档）：Foyer+HiCache 297.6 分钟 / 命中率 69.7% / SLO 89.8% /
并发 2.11；最快的静态档 cap4 是 257.6 分钟 / 45.9% / 55.7% / 3.94；
Concur 忠实复现（同控制律、重调参数）264.6 分钟 / 40.1% / 52.8% / 4.52。

**第 5 条的细节**（这是要找你看的核心）：原曲线从 `metrics.csv` 的
`generation_tokens_total` 差分算，两个错：

1. 引擎计数器**不是每次抓取都更新**，约每 10 秒批量跳一次。按固定 5 秒采样差分，
   一次突发会整个落进恰好接住它的区间，中间区间读数为零 → **低并发档被系统性
   低估约 25%**。同一份数据：按采样差分 33.5 tok/s，按更新周期 45.1 tok/s。
2. 修正粒度后 1→2 从 +86% 变成 +47%；此时又发现 t=2 的周期**处理了按比例更少的
   prefill**（prompt/gen 39.7 vs 44.5）且**命中率更高**（58.7% vs 53.1%）——
   所以那 +47% 里有一部分是"每个生成 token 摊到的重算更少"。

换成逐请求测量后两个问题一起消失，方向翻转成 **−5%**。

## 请你核查的具体问题

**A.（最重要）逐请求测量本身有没有混淆？**
我算的是 `(output_len-1)/(duration-TTFT)`，并发取该请求存活窗口内
`num_running_reqs` 的均值。注意上表里**并发越高，命中率越高、上下文越小**——
这与常识（并发高→驱逐多→命中率低）相反，说明分桶可能存在选择性。
**这个选择性会不会本身就把"速率随并发下降"造出来了？** 如果有，正确的做法是什么？

**B. "墙钟 ∝ 并发^−1/2"这个拟合是不是过度解读？**
它是从"聚合 ≈ 并发 × 速率"和三个速率点（36.4/34.6/33.4）推的，
而这三个点是**跨策略**的平均，不是同一个策略在不同并发下。
用两个数据点（1.19 预测 vs 1.21 实测）去支持"平滑"这个结论，够吗？

**C. 撤到只剩这些，还够 CCF-B / 中科院二区吗？**
现在两个贡献都是测量：一条"每请求速率不随并发上升"（偏负面/澄清性），
