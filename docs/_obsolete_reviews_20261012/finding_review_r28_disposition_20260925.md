## 一、最重的一条：半池的 −4.6 pp **是错的**，已撤

**症状**：`paper/data/pool50.csv` 报 `cap2_hp` 兑现率 **87.1241%**，据此写进
§III 与 §I 的净效应 **−4.6 pp**。

**真相**（我逐条独立复核，与两份报告一致）：

    cap2_hp：104/999 步被引擎服务成【1-token 退化响应】
             server_prompt_tokens=1、output_len_actual=1、first_token_ms=None、
             finish_reason=None、error=None —— **runner 记成 SUCCESS**
             计划 prompt 与实测差 6,515,669 tokens，**其中 100.00% 来自这 104 步**
             引擎自报命中 = 12,251,190 / 21,540,371 = **56.88%**

**根因**：`gen_a100.one()` 的 `reuse_tok = 计划 prompt − 实测 uncached`。
一步没被服务时，它的**计划 prompt 整块**减去约 0 的 uncached，差额被算成了「复用」。
干净 run 里计划==实测，看不出问题 —— 这正是它活了这么久的原因。

**同一函数也放过「有失败步」的 run**（失败步 `server_prompt_tokens=None`）：
`pois200_foyer_hz2` 2 步 → 虚报 60,314（0.28 pp）、`budget200c_default` 121 步 → 4.76M。

**爆炸半径（我扫了全部 136 条 run）**：

| | |
|---|---|
| 缺口 >100k 的 run | 8 条：三条 hp、`budget200c_default`、`default`、`pois200_foyer_r2`（114 步未完成）、`load50_default`、`budget200c_budget3_r2` |
| **主兑现率表 `reuse.csv` 的 27 条 run** | **一条都不在名单里** ✓ |
| **A100 的 7 条**（`a100_cap1..5` / `a100_default` / `a100_foyer_hz2`） | 缺口**全为 0** ✓ |

**主表为什么没事**：`gen_reuse.py` 的兑现率读的是 **`eviction.csv`**，
而 `gen_eviction.py` 早就写明「prompt 必须与 uncached **同源**」并**断言**
`prompt_tokens_total == 计划 prefill`。**同一个量有两份实现，坏的那份没断言。**

**处置**：
1. `gen_a100.one()` **加硬断言**：计划 != 实测就 `SystemExit`，消息写明缺口与占比。
   反向测试：对 `cap2_hp` 跑 `one()` 立刻报错 ✓。
2. `gen_pool50.py` 的 OK 判据从「999 步 + 0 失败」扩到**三条**（加「计划==实测」），
   `cap2_hp` 与另两条一样判 **INFEASIBLE**，`half_real` / `delta_pp` 一律留空；
   新增 `unserved_steps` / `prompt_gap_tok` / `gap_pct_of_bound` 三列。
3. §III 与 §I **重写**：不再有 −4.6 pp，改为「半池在这条 trace 上**给不出兑现率**」。

**新写进 §III 的读数**（全部有守卫）：

    cap2_hp  999 步、0 失败、**104 步未被真正服务**、缺口占 trace 上界 **30.2%**
    cap3_hp  807/999 步、50 失败、122 步未被真正服务
    cap4_hp  549/999 步、116 失败、155 步未被真正服务

即：**半池把这条负载从「兑现率随并发下降」变成「回放跑不起来」。**

⚠ **不要从这个数上退一步去写 56.88%** —— 那是揭示错误的诊断数，不是新的兑现率：
服务的工作量已经不同（三分之一的 prompt 根本没处理）。

## 二、`gate_full` 是**恒等式**，不是观测

`controller_budget3.py:389`：

    gate_full = bool(args.round_gate) and running_n >= args.round_gate

`round_gate` 默认 0、`run_matrix.py` 从不传 `--round-gate`、日志里
2762 个采样的 `round_gate` **全是 0** —— 于是这个字段**恒为 False**。
原来写在 §A100 的「it was full in 0.0% of its 2762 control cycles」是**定义决定的**，
跟负载、池子、卡都没关系。

**处置**：换成三条**真的会变**的观测，并进 `a100_delta.csv`：

    安全阀（valve）为真的采样      0.0%      （usage 到 0.85 才开，池子峰值 51.9%）
    shed_n 峰值                    0
    准入等待（只看 admit 事件）     p50 1.6 s、max 51.7 s、71% 的会话等过 >1 s

⚠ **`waiting_n>0` 不能当限流证据**：它含「已到达、本轮未 active」的会话（含轮间
tool-wait）。⚠ **`admissions.jsonl` 的 `waited_ms` 要按事件类型分开**：`queued` 恒 0、
`release` 的是会话驻留时长（最大 791 s）—— 我第一版把三种混在一起算，
p90 得出 152 s，比真值大一个数量级。
