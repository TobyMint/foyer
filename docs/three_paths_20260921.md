# 决议（2026-09-21 下午）

## 一、路线 B 被自己的测量否掉了——但否掉的方式比 B 本身有用

B 的前提是"搬运 vs 重算存在交叉点，我们去表征它"。微基准测完：**交叉点不存在**。

```
prefill 重算（实测拟合）      924 tok/s   → 1.08 ms/token
PCIe 搬运（实测）                          0.005 ms/token
比值                                       216×
```

原因不神秘，而且这个"不神秘"正是重点：搬运代价 = 字节数 ÷ PCIe 带宽；
重算代价 = token 数 ÷ prefill 吞吐。上下文变长时，KV 字节数和重算 token 数
**同比例线性增长，约掉了**。所以 216× 是个**硬件常数**，不随模型、上下文、
负载改变（换 A100 会变，换上下文长度不会）。

**这反过来组织了论文**：既然搬运在所有量级上都压倒性便宜，"搬还是算"就**不是**
一个代价权衡，而是一个**容量问题**——只有当主机层装不下时重算才被迫发生。
MORI 的"适配任意硬件比例"因此应当**重述**为"主机层容量决定被迫重算的比例"：
一个**单调的、可实测的**关系，而不是一条有待寻找交叉点的曲线。

而且这条曲线我们**已经有数据**：HiCache 开/关 × 不同池压力（25 档 cap6 那一组，
以及 200 档 cap2 的对照——后者是干净的空结果，正好做下界）。

## 二、真正的发现是"台阶"，不是"斜率"

> **⚠ 2026-09-21 晚些时候的重要修正**：做完 §6 的同 run 配对（`batching_curve.py`）之后，
> "台阶"这个说法**被证明是过强的**。同 run 内速率对并发是**平滑凹曲线**
> （33.5 → 62.3 → 80.8 → 110），而平滑的分布移动应当产生平滑的聚合曲线。
> 数据**确实分成两簇且中间无观测**（这是事实），但**"不连续"与"陡峭平滑下降"
> 分不开**，因为分界处 (1.33, 1.44) 恰好一点采样都没有。
> 完整论证见 `docs/throughput_decomposition_20260921.md` §6、§7。
>
> **所以本节以下所有"台阶"字样都应读作"两簇 + 未分辨的间隙"。**
> `cap3_fixed` 落在缺口正中，是唯一的判决测量。

Poisson λ=0.04 主表（200 会话，13 条策略）按并发排序：

```
并发 1.00  →  533.6 分   cap1
并发 1.90  →  339.9 分   Foyer t85
并发 1.99  →  310.5 分   cap2
并发 2.04  →  321.8 分   Foyer t90
并发 2.11  →  297.6 分   Foyer + HiCache      ← 本区间最快
并发 2.12  →  299.3 分   Foyer
并发 2.24  →  364.3 分   Concur（原参数，⚠ 数据不可用）
并发 2.84  →  300.2 分   Foyer rl90
并发 3.30  →  362.0 分   Foyer rl99
──────────────── 台阶 ────────────────
并发 3.56  →  259.2 分   cap3
并发 3.94  →  257.6 分   cap4
并发 4.52  →  264.6 分   Concur（重调）
并发 4.89  →  267.0 分   cap5
```

**⚠ 先更正上表的一行**：那个"并发 3.56"的 cap3 点**不是 cap3**。
它是 `pois200_cap3_r2`，被 runner 的 cap 竞态污染过——实测 admissions.jsonl：

```
cap 字段          全部 200 条都是 3
admit 时的 active  1:2 条   2:3 条   3:195 条
admit 后的在飞数   2:2 条   3:3 条   4:195 条   ← 195/200 落在 cap 之上
```

也就是说它**跑在 4 上，不是 3**。它的 259.2 分是**第二个 cap4 测量**，
不是崖左侧的第一个点。（竞态本身已定位并用 CAS 修好；`cap3_fixed` 会给出
第一个真正干净的 cap=3 点。）

**这个更正反而给了我们一个噪声估计**：两个独立的 cap≈4 测量——污染的 259.2
和干净的 257.6——相差 1.6 分（**0.6%**）。这是目前 Poisson 主表上唯一一对
可比的重复。

**台阶本身仍然成立**，而且更正后更干净：

- **低区间**（并发 1.0–2.84）：533.6 / 339.9 / 310.5 / 321.8 / 297.6 / 299.3 / 300.2
  ——跨越 1.8 个单位的并发，墙钟落在 297–340，且**彼此无单调关系**
  （2.04 的 321.8 比 1.99 的 310.5 还慢）
- **高区间**（并发 3.56–4.89）：259.2 / 257.6 / 264.6 / 267.0，全部落在 257–267
- **中间 (2.84, 3.56) 是一个空缺**——崖的精确位置**被夹住但没有被分辨**

**崖在哪一侧落地，正是 `cap3_fixed` 要回答的**：它要么落在 ~300（崖在 3 以上），
要么落在 ~258（崖在 3 以下）。这就是为什么 `cap3_fixed` 现在是队列里
**最值钱的一个 run**——不是"补一条基线"，是**唯一能把崖定住的测量**。

这改变了整个论证的落点：**准入控制的价值不在于"把并发调到最优"（台阶上没有最优
值可调），而在于"落不落到台阶的另一侧"。** 高区间快的那 ~14%（300 → 258），
来源就是越过了池子的安全点——而不是"调对了并发数字"。

（旁证：那个被污染的 cap3_r2，其引擎空转率 11% 与干净 cap4 的 10% 吻合，
又一次说明它测的就是 cap4 这个条件。）

**⚠ 一个必须自己先说的反例**：rl99 并发 3.30、墙钟 362.0——**两个区间都不在**，
比低并发区间还慢。归因已做：它的硬阀在 2162 次决策里触发 971 次（45%），
引擎**零请求在跑**的时间占比 24%（cap3 是 11%，Foyer 16%）。所以**并发是必要
不充分条件**：台阶的另一侧要求的是"并发**且引擎真的在干活**"，不是并发数字本身。

（数值口径：零请求占比从 `sglang:num_running_reqs` 重算得出。早先用
`token_usage > 30%` 当"引擎忙"的代理指标是错的，`docs/STATUS_20260921.md` §6.3
里的 28%/13% 是那个错口径的产物，以 24%/11% 为准。）

这对论文是加强不是削弱——它说明越过安全点之所以有效，前提是**多出来的会话真的
被引擎接住了**；如果多出来的并发只是把引擎推开、让它空转（rl99，以及 Concur
原参数的 364.3），那就两头落空：既付了并发，又没拿到台阶下的墙钟。
这也正是 #32 要判决的东西。

### 补充：台阶已用**另一个量**独立验证，并已分解

`docs/throughput_decomposition_20260921.md` 用磁盘上已有的 `metrics.csv` 重算了
**聚合解码吞吐**（`generation_tokens_total` / 墙钟）——一个与墙钟完全不同的量、
来自完全不同的原始数据：

```
引擎并发 <  1.40   n=9   34.7 tok/s   忙 79.6%
引擎并发 >= 1.40   n=5   43.5 tok/s   忙 88.5%
                  比值 1.26×（去掉离群点 cap1 后 1.20×）
```

**分母先被验证过**：14 个 run 的总生成 token 离散度 0.76%，所以吞吐差异不是
"干了不同的活"。两个量对上了 → 台阶是真的，不是记账假象。

分解：`1.20× = 1.08×（忙占比）× 1.11×（忙时吞吐）`。**约一半是"少空转"，
一半是"忙的时候每秒解码更多 token"**——后者是批处理的直接证据，本节上面那句
"机制没有测、不要断言"**已作废**（证据级别：跨策略观察，非受控实验）。

**一条对我们不利的**：在引擎并发 ~1.4 上，批处理收益**大于**命中率损失。

```
cap4    命中 45.9%   45.5 tok/s   257.6 分
Foyer   命中 65.6%   39.2 tok/s   299.3 分
```

Foyer 命中率高 20pp，吞吐却低 14%。**多出来的命中率买不回少掉的那部分批处理。**
所以 §四 第 4 条（帕累托优于 cap2）能不能保住，取决于 #32 能不能把引擎并发
从 1.12 推到 1.4 一线。**推不上去的话，第 4 条要撤。**

## 三、把 SLO 当约束而不是目标，结论翻转

我之前对用户说的"端到端比不过静态 cap"，是在**无约束地比 makespan**。而无约束
makespan 的最优解是 cap4：257.6 分，**SLO 55.7%**。一个 SLO 55.7% 的策略在任何
服务系统里都不可部署——它的 TTFT p50 是 7.2 秒。把 SLO 当约束（这是 SLO 的定义）
重新排序：

```
SLO ≥ 85% 的可行集合：
  297.6 分  69.7%  89.8%  并发 2.11   Foyer + HiCache   ← 最快
  299.3 分  65.6%  88.6%  并发 2.12   Foyer
  310.5 分  67.7%  89.5%  并发 1.99   cap2              ← 最快静态
  321.8 分  65.5%  87.7%  并发 2.04   Foyer t90
  339.9 分  67.3%  89.9%  并发 1.90   Foyer t85
  533.6 分  69.9%  94.8%  并发 1.00   cap1

不可行：cap3（62.2%）、cap4（55.7%）、cap5（27.1%）、Concur 重调（52.8%）
```

**在 SLO ≥ 85% 下，Foyer+HiCache 是 13 条策略里最快的，并且四项全胜最强的可行
静态基线 cap2**（297.6 / 69.7% / 89.8% / 2.11 对 310.5 / 67.7% / 89.5% / 1.99）——
墙钟、命中率、SLO、并发**同时**更好。这是帕累托改进，不是"差一点"。

**⚠ 但这是单 run。** 25 档上同配置两次重复的离散度是 2.7%，这里差 4.2%，
略高于噪声。**写进论文前必须重复一次**（两条各 5 小时，见 §五）。

## 四、所以论文的主张（已定）

**一句话**：在 agentic serving 上，准入控制不是吞吐机制，是**可行性**机制。

1. 墙钟-并发关系是**台阶**（实测，反直觉，且解释了为什么"调参"永远调不动）
2. 台阶另一侧的 14% 收益是用 **27–33 pp 的 SLO** 买的，不是免费的
3. 因此 SLO 是**约束**，按约束求解后最强的静态基线是 cap2，不是 cap3/cap4
4. 一个只读引擎遥测的闭环控制器（Foyer）在约束下**帕累托优于** cap2
5. **主张落在"控制变量该取什么"，不落在机制新颖性上**：账本按逻辑上下文之和记账时
   读到 92%，而引擎实测占用只有 52%（前缀共享让逻辑和远高于物理驻留）。
   按逻辑账本准入的策略**系统性地过度保守**，正好停在台阶边缘。

第 5 条是新的落点，也是唯一没被 ThunderAgent/MORI 覆盖的部分：他们做容量核算，
但核算的**输入**是请求声明的长度；我们用**引擎遥测的物理占用**。92%/52% 这个
测量差距就是这条主张的实证支撑。

**与文献的关系**：不再声称机制新（已被覆盖）。声称**校准规则**新——控制变量取
实测物理占用而非逻辑台账。这是可被实验证伪的，见 §五 的 #32。

## 路线 A：有界性理论

**核心主张**：在硬 token 预算 + 分档复活代价（搬运 / 重算，且互相挤占预算）下，
给出被挂起会话**复活延迟的上界**，并给出达到该界的策略。

**为什么它可能成立**：HRRN 的致命处在于 S（服务时间）是外生给定的。我们的场景里
**复活代价是调度器自己选的决策变量**——同一个会话可以搬（占 PCIe 带宽）也可以重算
（占 GPU 算力和 pool），而选择本身改变别人的代价。这带来拥塞外部性，超出 HRRN 的模型。
InferCept 有这个思想（式(1)(2)(3)(5) 比 preserve/discard/swap 的浪费），
但它做的是**单请求的贪心**，没有界、没有会话、没有硬预算。

**需要的新东西**：
1. 一个形式化模型（状态、代价、预算约束）
2. 一条定理：在上界意义下的最优或近似最优策略
3. 与 HRRN / Gittins index / c-mu 规则 / FCFS 的对照实验

**成本**：
```
理论        从零做。5–6 周内要出可发表的定理，风险高
实验        3–5 个 run × 5 小时 ≈ 25 GPU 时（现有装置够用）
写作        与系统论文完全不同的写法（定理 + 证明 + 仿真验证）
```

**风险**：
- 高。可能证不出非平凡的界，或者证出来的界平凡（例如退化成"队列长度 × 最坏服务时间"）
- 我们没有理论方面的积累，这条路的产出高度不确定

**新颖性**：三篇里**没有**"有界"这个概念（InferCept 只说 FCFS "avoids starvation"，
MORI 和 ThunderAgent 连 starvation 都没提）。这是唯一没被抢走的词。

**天花板**：如果做成了，是一篇调度理论方向的论文，但和现在的系统论文积累关系不大。

## 路线 B：表征论文（我倾向这条）

**核心主张**：量化"搬运 vs 重算"的交叉点在哪里，并**把 MORI 的"适配任意硬件比例"
当作待检验假设去实测**。

**为什么它可能成立**：
- MORI §7.1 **书面**把第三层（SSD）和跨节点列为 future work：
  > "MORI is described and evaluated on a two-tier memory hierarchy... We leave extending MORI to future work"
- 它的实验最小只到 **80GB 级 GPU**，主机内存假设是 **TB 级**（§3.4 的 DGX 1TB/2TB 例子）
- 它声称"适配任意比例"，**但没测过极端比例**

**⚠ 一个必须先解决的障碍**：我们的 lab 机器有 **251GB 主机内存，根本不紧**。
"我们的主机内存也紧"这个差异化，在当前硬件上不成立。

**但是**——这个约束**可以在不改硬件的情况下造出来**：SGLang 的 HiCache 大小是可配的
（我们现在用 `--hicache-ratio 2`）。把 host tier 缩小就能造出"MORI 没测过的比例"。

**需要的新东西**：
1. 一组"受约束主机层"的配置（小 hicache、慢 PCIe 路径）
2. 搬运代价 vs 重算代价的微基准（PCIe 带宽实测）
3. 在这些配置下，两层模型的失效点在哪里

**成本**：
```
微基准      2–3 天（PCIe 带宽 / prefill 算力 / 交叉点）
实验        8–12 个 run × 5 小时 ≈ 50 GPU 时（现有装置直接可用）
写作        测量/表征类，和我们已有的表格、图、日志完全契合
```

**风险**：中。
- 主要风险是"测出来发现 MORI 的适配性其实没问题"——那也是一篇诚实的负面结果，
  但作为主贡献就弱了
- 需要造出真实可信的约束条件，不能让审稿人觉得是人为构造

**新颖性**：这条曲线**不存在于文献中**（调研 grep 过 12 个官方页面与多篇论文，
没有任何实测的 p99-对-KV-占用曲线，也没有工作把"任意硬件比例"当作待检验假设）。

**天花板**：测量类论文在 CCF-B / 中科院二区是够的，尤其如果有反直觉的发现。

---

## 路线 C：收窄问题，承认机制被占

**核心主张**：agentic 负载下准入策略的实测权衡——不做机制主张，只做
"在这类负载上，准入控制能带来什么、不能带来什么"的严格测量。

**成本**：
```
实验        已基本足够（现有数据 + cap3/cap4 重跑）
写作        最快，2–3 周可以初稿
```

**风险**：低技术风险，**高录用风险**。"我们又测了一遍准入控制"很难过审。

**新颖性**：低。除非有强反直觉发现。

## 三路对比

| | A 有界性理论 | B 表征（倾向） | C 收窄 |
|---|---|---|---|
| 新颖性 | 高（"有界"无人做） | 中高（曲线不存在） | 低 |

## 我的建议

**路线 B**，理由是它把最大的既有资产（精确可控的装置 + 已测的干净数据）变成产出，
而路线 A 要从零建理论框架、5–6 周内风险过高。

**但 B 有一个必须先验证的前提**：造出"受约束主机层"之后，两层模型是不是真的会失效。
这件事**可以在 2 天内用现有装置验证**——先做一个小的 prefill-vs-transfer 微基准，
量出交叉点。如果交叉点在合理的 host 层大小下就出现了，B 成立；如果 MORI 的适配性
在小 host 层下依然稳健，那 B 也弱，要回到 A 或 C。

**所以无论走哪条，下一步是同一个：先做那个微基准。**它便宜（不占整卡，可以和重跑并行）、
快（2 天）、而且结论直接决定路线选择。
