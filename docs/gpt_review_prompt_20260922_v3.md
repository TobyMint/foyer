## 三、今天（2026-09-22）发生了什么——**三件事，两件是坏消息**

### 1. 「调参 / 关掉节流」这条路被**四重否证**

四条独立的证据，指向同一件事：

```
§二十七  结构论证：只用池子占用做准入的控制器，其可达点【不会超过】静态前沿。
         因为对任意一个"放 N 个"的结果都有一个 cap-N 在同一位置，
         而静态扫描已经把前沿穷举过了。用一个看不见缓存的信号去控制一个
         由缓存决定的结果，只能靠碰巧。
§三十九  实测：把静态 cap 扫描连成一条（墙钟 × SLO）曲线后，Foyer 的三个点
         落在静态+HiCache 插值线的【下方】0.67pp。不是"更好"，只是"更细"。
§四十三  实测：Foyer 实测并发 2.06，cap2 是 1.99，而悬崖在 2.9。
         Foyer 离悬崖还有 30%——它不是"找到了安全操作点"，而是几乎停在 cap2 的位置。
§四十六  实测：把三个安全节流【全部关掉】（foyfix_hc），并发只从 2.06 抬到 2.62（+27%），
```

## 四、今天改的代码：`--charge-mode delta`

### 改动的动机

准入块里原来这一行：

```python
base = s["ctx"] or s["prompt0"]
n = (base + forecast(s)) * args.margin
if projection + n <= budget: ...
```

`ctx` 是会话**这一轮的整轮 prompt 长度**（约 20k token 量级）。
但一个**热会话**（跑过至少一轮又回来）的前缀**已经在引擎里**，
而 `projection` 的第一项 `resident`（引擎实测占用）**已经算了它**：

```python
projection = max(resident, ctx_sum) + growth_sum
                    ↑ 引擎实测占用，已含热会话的驻留前缀
```

**再按 `ctx` 收一次，同一批 token 计费两次。**

实测差距（这个 trace 上）：

```
round 0   未命中中位 15,720 token   ← 真的要从头 prefill
round 1+  未命中中位  1,933 token   ← 前缀基本都在
会话间隔（tool_wait）中位 0.1 秒     ← 所以前缀几乎必然还在
```

### 改法（`controller_budget3.py`）

```python
ap.add_argument("--charge-mode", choices=["full", "delta"], default="full")

# 记录引擎自己量的边际代价
unc = rec.get("server_uncached_prompt_tokens")
if unc is not None:
    s["uncached"] = float(unc)

# 准入计费
base = s["ctx"] or s["prompt0"]
if (args.charge_mode == "delta" and s["last_round"] >= 0
        and s.get("uncached") is not None):
    base = s["uncached"]        # 引擎实测，不是模型估的
n = (base + forecast(s)) * args.margin
```

**实验是严格单变量的**：

```
对照   budget3:hw=0;target=0.95
处理   budget3:hw=0;target=0.95;charge=delta     ← 只多这一个参数
```

### 部署安全性（这一步值得单独说）

控制器有一个**重启循环**——它一退出就从磁盘重新拉起。所以改这个文件有"中途换控制器"的风险。

**这次的边界是"新参数默认值 = 旧行为"**：运行中的进程不重读源文件；万一半夜重启，
新进程拿到默认 `full`，与旧版逐字相同。只有显式传 `charge=delta` 才走新逻辑。

**在跑（2026-09-22 17:40 起）**：短 trace 上 `charge=delta`，
出结果后跑全程版本。

## 六、请你核查的具体问题

### A.（最重要）`charge=delta` 这个改动，逻辑上对吗？

我的论证是"热会话的前缀已经在 `resident` 里，再按 `ctx` 收就是重复计费"。
**但这个论证有一个我没验的前提**：`projection = max(resident, ctx_sum) + growth_sum`
里的 `max` 意味着 `ctx_sum` 有 57% 的周期压过 `resident`
（实测 8784 个控制周期：`ctx_sum` 主导 4973 次，`resident` 主导 3811 次）。

**如果 `ctx_sum` 主导，那 `resident` 根本没被计入，我的"重复计费"就不成立。**

请判断：**在 `max(resident, ctx_sum)` 这个结构下，"重复计费"的说法还站得住吗？**
如果站不住，`charge=delta` 是不是就变成了"单纯把账放松"（那会掉 SLO，而不是修 bug）？

### B. 出路（前缀身份准入）是对的吗？

§二十七 说"用看不见缓存的信号去控制由缓存决定的结果，只能靠碰巧"。
**这个论证有没有漏洞？** 比如：如果控制器的信号虽然看不见缓存，
但它与缓存状态足够相关（比如池占用高 → 驱逐多 → 命中率低），那是不是就够用了？

**而且我们实测到 `resident` 中位 49.2% 时 `ctx_sum` 中位 56.9%——
两者差距不大。这支持还是削弱"池占用与缓存状态脱钩"这个前提？**

### C. 如果 v4 也失败，这篇论文还剩什么？

现在的候选只有：

2. 一条测量（静态 cap 越过悬崖会掉进"驱逐螺旋"，run 内部可见：
