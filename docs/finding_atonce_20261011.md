## 五、这一轮**没有**达到「3~4 倍」

用户的目标是「我们的方案 vs 完全不管，端到端 3~4 倍」。实测：

```
整批时间    1.41×   ✗
单会话端到端 2.68×   ≈（接近但没到 3）
deadline 达标 153×   ✓ 远超
```

**为什么整批时间上不去**（三条，都要写进结论）：

1. **重算的代价是「时间」不是「token」。** 工作量比 10 倍是 **token** 口径，
   而 re-prefill 的 token 在 3090 上是**便宜**的（prefill 吞吐高、decode 才是瓶颈）。
   每个 warm 步约 6.0 s，其中被 re-prefill 多花的只有约 4~5 s ⇒ 时间口径的浪费只有 ~30%，
   于是 makespan 上限就是 `1/(1−0.3) ≈ 1.4`。**与实测逐位相符。**
2. **我们自己的空转（26%）** —— 见 §四②，是控制器记账造成的，可修（队列里已排）。
3. **池子把并发锁在 1~2** —— 上下文 40~65K，池 101K，物理上最多装 2 个。

## 五之二、为什么 makespan 上不去：**结构性上限 ≈ (D+P(ctx))/(D+P(inc))**

重算的代价是**时间**，不是 token。设每步服务时间 = 解码时间 D + prefill 时间 P：

```
makespan 倍数 = (D + P(完整上下文)) / (D + P(增量))
```

用本轮实测反解（foyer 每步 6.0 s，default 每步约 13.8 s 服务时间，上下文 ~40K）：

```
倍数 1.60  ⇒  D ≈ P(61K token)
⇒ 上下文 91K 时：倍数 ≈ (D+P(91K))/(D+P(2K)) = 152333/63333 ≈ **2.4×**（空转归零前）
```

**三条推论**：

1. **上下文越长，倍数越高**（P(ctx) ∝ ctx，D 固定）—— 但**池子/宿主要装得下**：
   上下文 91K 时池子（101K）只装 1 个，宿主的 203K 只装 2 个，**我们自己的复用优势也会消失**。
   所以有一个最优点，**medium trace（40~65K）已经在它附近**。
2. **解码越快，倍数越高**（D 越小）。⇒ **换小模型（Qwen3-4B）对倍数是有利的**，
   尽管它的 KV/token 是 7B 的 2.57 倍、池子更小。（用户 2026-10-10 的直觉在这一维度上是对的，
   在「池子更大」那一维度上是反的 —— 两件事要分开说。）
3. **空转是纯损失**：我们空转 26.1%、无控制 15.8%。把我们的空转压到 5%，
   makespan 从 91.2 → 约 71 分钟 ⇒ 倍数 **1.82×**，且不影响工作量比。
