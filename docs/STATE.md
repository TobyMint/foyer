- **lab-A100**（`100.64.0.2`）：3× A100 80GB，**不可用作退路**——利用率常驻 60–91%（wall time 会被污染），且无 turnstile 环境 / 模型 / trace。


**双脚本树是已踩过的坑**：改代码前必须确认改的是 lane 实际引用的路径，不能假定。

**每个 run 目录**：`summary.json`（指标汇总）、`metadata.json`（溯源：池子/trace 哈希/代码哈希/argv）、`steps.jsonl`（每步）、`admissions.jsonl`（准入事件）、`controller.jsonl`（决策）、`metrics.csv`（引擎时间序列）、`runner.out`。

**管线（2026-09-20 起，自愈式）**：cron 每 5 分钟执行 `watchdog.sh` → 若某张卡的工作流不在，就用 setsid 拉起 `queue_stream.sh <gpu> <worklist>` → 工作流逐行读工作清单（`worklist_gpu2.txt` / `worklist_gpu3.txt`，每行 `<lane 脚本> <marker run>`），已完成（marker 的 summary 存在）就跳过，否则等卡→跑→重试，直到整条清单跑完 → `wait_gpu_then_run_fast.sh`（30 秒轮询、连续 2 次低于 FREE_MIB=1000 即起跑；旧的 `wait_gpu_then_run.sh` 需 25 分钟，是池子守卫出现前的遗留保守设定）→ `lane_*.sh`（一条 lane 若干 arm，set -e）→ `run_matrix.py`（起服→校验池子→起 controller→跑 runner）。

**加新实验**：往对应 worklist 文件追加一行即可（`lane_xxx.sh marker_run`），工作流跑到那一行会自动执行；marker 必须是该 lane 的**最后一个** run。

等待策略的依据：池子守卫会解算 mem_fraction_static 把池子拉回 101,432，可吸收约 1,150 MiB 的邻居残留；超出则**在记录任何产物之前**中止并重试。因此与即将起跑的邻居抢跑只损失一次尝试，不会污染数据。

**关键机制**：

- **池子守卫**：起服后校验池子，不符则按实测斜率解算 memfrac 重试（上限 0.90），仍不符则中止且不记录；
- **按 run 跳过**：已有 `summary.json` 的 run 会被跳过，整条 lane 重试只重做未完成的；
- **metadata 提前落盘**：配置确定即写，被杀只损失结果不损失溯源。

## 8. ⚠ 墙钟指标对 CPU 争用高度敏感（2026-09-21 发现）

**观测**：2026-09-20 23:16，同机用户 `cjy` 起了一个吃 **2378% CPU（约 24 核 / 48 核）** 的任务（`build_oof_teacher_targets.py`）。此后：

```
                       负载前      负载后
pois200_cap1          2.39 步/分 → 1.98 步/分    −17%
pois200_aimd2_paper   4.40 步/分 → 3.32 步/分    −25%

同一时段服务器解码吞吐   45.2 → 44.4 tok/s        −2%
```

**GPU 几乎没被抢，掉的是 CPU 侧。**我们的 agentic 管线里 runner 提交、tokenizer、调度器都在 CPU 上；CPU 被饿住，喂给 GPU 的活就变慢，而 GPU 本身一直在正常解码。

**为什么这件事严重**：被污染的幅度（17–25%）**大于我们要测的策略差异**（Foyer 299min vs cap4 258min = 14%）。因此——

- **墙钟只在 CPU 条件可比时才可比**。跨天、跨负载状态比较墙钟是不成立的。
- **质量类指标（命中率 / SLO / TTFT p50）不受影响**，它们是按步统计的。所以"质量轴"稳健，"时间轴"脆弱。
- 论文的评测节应写明这一点，并说明墙钟对比是在什么条件下取得的。

**待办**：`pois200_cap1` 与 `pois200_aimd2_paper` 的墙钟被中途污染（cap1 前三小时干净，之后被拖慢），其**命中率/SLO 有效，墙钟偏大**。若这两个数要进主表，需在安静环境下重跑。
