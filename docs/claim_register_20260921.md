### Q1 专节：两个候选解释都被否掉了（2026-09-21 晚，读 lab 上安装的 SGLang 源码）

**候选一（GPT 提出）：`token_usage = (pool − available − evictable)/pool`，即扣除了可回收缓存。**
那个式子确实存在，但在 `srt/managers/scheduler_runtime_checker_mixin.py` 的
`_get_token_info()` 里——**一个供内部检查用的辅助函数，不是 Prometheus 指标的来源**。
指标的来源是 `srt/observability/scheduler_metrics_mixin.py`，另有定义。**该引用张冠李戴。**

**候选二（我提出）：`full_token_usage − token_usage` 就是可回收部分。**
看起来很有说服力：差值恒 ≥0；随并发**反向**变化（cap1 有 24.8% 的采样不等、cap4 只有 0.10%）；
幅度中位 21.6pp、最大 74.2pp；而且**持续存在**——cap1 里最长连续 54 拍 = 270 秒，
**不是抓取竞态**（竞态只会产生单拍毛刺）。行为完全像可回收缓存。

但两个 gauge 自己的说明文字是：

```
sglang:token_usage       "The token usage."
sglang:full_token_usage  "The token usage for full attention layers."
```

**`full_token_usage` 是混合注意力模型里"全注意力层"的用量，不是"含可回收的全部驻留 KV"。**
而且 `is_hybrid_swa` 是**按架构白名单**判定的（Llama4 / GptOss / MiMoV2 / Step3p5），
`Qwen2ForCausalLM` 不在其中；源码里该模型走的那条路径下两者被赋成**同一个值**。
**源码与实际观测矛盾，机制未查明。**

**结论：这两列给不出"锁定 vs 可回收"的分解，Q1 必须实测，不能从盘上已有的列反推。**
**值得记的是：候选二当时看起来同样自洽、同样"有数据支持"——
它没变成今天第四条被撤回的断言，唯一原因是先查了源码。**

## 八、Q1 追加：机制查明（2026-09-21 深夜，直接采样 metrics 端点）

**先撤回我 20 分钟前的警报**：我曾看到端口 30033 上 `token_usage=0.0` 而
`full_token_usage=0.834`，判断"控制器是瞎的、`measured` 不可信"。**那是误读，收回。**

连采四拍，机制很清楚：

```
running=0  ->  token=0.000   full=0.834     ← 空闲
running=1  ->  token=0.194   full=0.194     ← 有请求，两者相等
running=1  ->  token=0.205   full=0.205
running=1  ->  token=0.224   full=0.224
```

**有请求在跑时两者恒等；空闲时 `token_usage` 正确归零，而 `full_token_usage` 停在上一次的值。**

这一条**完整解释了 §四 Q1 那个"完整 attention 层"的谜**（此前只能说是"源码与观测矛盾"）：

| 观测到的现象 | 由"空闲时 full 不变"解释 |
|---|---|
| 差值只出现在部分采样 | 只出现在空闲采样 |
| 与并发**反向**（cap1 24.8% / cap4 0.10%） | 低并发空闲时间长 |
| 幅度最大到池子 74pp | 陈旧峰值 − 当前值，空闲越久越大 |
| 持续到 270 秒 | 空闲时段本来就那么长 |
| 恒 ≥0 | 陈旧值 ≥ 当前值 |

**结论（两条，都是可用的）**
1. **`token_usage` 是可信的**——它跟着现实走，空闲归零。**控制器的 `measured` 没有语义问题。**
2. **`full_token_usage` 是陷阱**——空闲不更新。**任何分析都不许拿它作参照或分母。**
   写进 `monitor.py` 的抓取说明里，免得以后有人再用它。

**顺带（对论文有用）**：cap4_hc 上 `sglang:hicache_host_used_tokens = 201,420`，
`hicache_host_total_tokens = 202,865`，而 GPU 池只有 **101,432**——
**主机层持有约两倍于 GPU 池的 token，且已用 99.3%。**
主机层不是"小缓冲区"，它是同量级的存储。之前论文里对 HiCache 的表述偏保守了。

**未查明**：源码里非 hybrid 路径下两者应被赋成同一个值，与观测不符；
具体是哪条路径导致 `full` 不更新，没有追到底。**但结论不依赖它**——
上面两条结论是直接从端点的实测行为得出的。

## 九、Q1 结案：1.8× 是拿预测比实测，而且对应的控制器已经不存在了

**来源定位**：`docs/throughput_decomposition_20260921.md` §4 末尾

```
这与主表"账本读到 92%、引擎实测 52%"是同一件事的两个侧面：
逻辑上下文之和 → 物理驻留 KV      高估 ~1.8×   （前缀共享）
```

**92 / 52 = 1.77。** 这就是 1.8× 的全部来历。

**为什么它不成立**（两个独立的理由，任一都足够）：

1. **量纲不对等。** 92% 不是"逻辑上下文之和"，是 `controller_budget3.py` 的
   `projection / budget`，而 `projection = max(engine_truth, sharing_blind_logical_sum)
   + growth reserve for EVERY resident`——**一个含未来增长预留的预测上界**。
   52% 是引擎当前实测。**预测上界高于当前值，是预测该有的样子，不是估计偏差。**
   （GPT 在 D1 条已经点过这一处；今天找到了它的出处。）
2. **对应的实现已经不在树上了。** 那个三重悲观式的 v3 控制器已被
   `controller_foyer.py` 取代，后者明确不再建模逻辑和、只读引擎遥测。
   所以 1.8× 描述的是一个**已废弃实现**的行为，不能作为现行方法的证据。

### 同量纲直接实测（2026-09-21，99 拍，rl90fix 运行中）

用 `controller_foyer.py` 新增的第 8 步日志（`ctx_sum` vs `measured`），
影子控制器读真实 run 的 `admissions.jsonl` / `steps.jsonl`（只读；它写的 permit
文件无人消费，决策是惰性的），所以 `ctx_sum` 跟的是真实会话集合：

| resident | running | n | ctx_sum/measured 中位 |
|---|---|---|---|
| 1 | 1 | 4 | 0.994 |
| 2 | 1 | 34 | 1.158 |
| 4 | 1 | 8 | **1.437** |
| 4 | 2 | 18 | 1.067 |
| 4 | 3 | 13 | 0.979 |
| 4 | 4 | 3 | 0.959 |

**结论（可写进论文的）**：同量纲下比值**不是常数**，99 拍里 0.72–1.44 都有，
**符号会翻转**（既有高估也有低估）；单会话驻留时两者几乎完全相等（0.994）。
**"会话侧记账系统性高估引擎占用"这个方向性说法，同量纲下不成立。**

## 十五、SLO 前沿：门槛一换，赢家就翻（2026-09-21 14:25）

SLO 定义取自 `make_tables.py`：**TTFT < 10,000 ms 的请求占比**。全部由 `steps.jsonl`

| foyer_rl90 | 300.2 | 77.8% | 4036 |

### 两条结论

**1. 草稿的"在 SLO ≥85% 约束下最快"成立，但只快 4.3%。**
`foyer_hc` **支配** `cap2`：墙钟更短（297.6 < 310.5）**且** SLO 更高（89.8% > 89.5%）。
但 4.3% 正是那个跨天不可归因的量级——**配对实验要测的就是它**，这条主张的强度完全取决于那个数。

**2. `cap4_hc` 把"取舍"本身消掉了。**

**HiCache 让"保缓存"和"提并发"不再互斥**——而这**是个静态配置，没有控制器**。
Foyer 的存在理由（自适应准入才能在保缓存的同时提并发）被它绕过了。
Foyer 剩下的唯一优势是 TTFT 那条轴。

### 真正的框架问题（**这一条要你定，不是测量问题**）

**门槛是选的，不是测的。** `SLO_MS = 10000.0` 是个常数，`85%` 也是：

```
SLO ≥ 85%  →  候选只有 foyer_hc 与 cap2，foyer_hc 快 4.3%
SLO ≥ 60%  →  cap4_hc 快 26%
```

**同一份数据，换个门槛，"谁是赢家"翻过来。**

而且 10 秒这个阈值本身也没有依据。cap4_hc 的 5.5 秒中位 TTFT 对一个 agentic
编码助手并不算不可用。

**所以框架问题的形状不是"我们的控制器快不快"，而是"服务等级定在哪"。**
那是个**产品判断**。定了 SLO 门槛，赢家就定了；门槛不定，任何一方都能声称赢。

**不许做的事**：先看谁赢再选门槛。那是 R7（"14 条全部落在两簇"）的同一类错误——
**用一个事后挑选的口径去支持一个事先想好的结论。**

## 十六、控制器状态漂移：一次让 run 永久停摆的 bug（2026-09-21 16:17–16:46）

### 症状

`pois200_foyer_rl90fix` 在 **894/999 步、179/200 会话**处**完全停住 29 分钟**：

```
runner:      steps 894/999  completed=894  submitted=894  active=0  sessions 179/200
controller:  active_n=0  waiting_n=0  measured=0  committed=0
```

`submitted == completed` 且 `active=0` —— **runner 一个请求都没在跑，也没在提交。**
控制器则认为自己知道的人全部处理完了。

### 排查（逐条排除）

| 假设 | 证据 | 结论 |
|---|---|---|
| trace 里有超长 tool_wait | **实测：最长 300,000 ms = 5 分钟**（中位 73 ms，>5 分钟的 0 条） | **排除** |
| 某个进程死了 | 四个进程全在，`metrics.csv`/`runner.out` 每 0.5 秒还在写 | **排除** |
| 控制器抛异常 | `grep -c cycle_error` = **0** | **排除** |
| 控制器重启过、丢了历史 | 进程从 11:44:59 起**从未重启**；且 `read_jsonl` **每拍重读整个文件** | **排除** |
| 引擎侧卡住 | `measured=0`，`metrics.csv` 正常 | **排除** |

### 定位

`admissions.jsonl` 的账：**queued 200 / admit 179 / release 179**。

**把控制器自己的规则离线重放一遍**（queued→arrived、admit→active、release→finished、
pause→未结束），得到 **`waiting = 21`**，与 runner 的 "200 − 179 = 21 个会话没跑" **完全吻合**。

**而 live 控制器报 `waiting_n = 0`。同一份文件、同一套规则，两者不一致。**

### 处置与结果

**杀掉控制器进程（PID 170734），让 supervisor 自动拉起。** 新进程重读全部事件：

```
重启前   active=0   waiting=0
重启后   active=3   waiting=18      ← 21 个里当场放行 3 个
```

**run 随即续跑**（894 → 910 步，会话 179 → 181）。**5 卡时救回来了。**

### ⚠ 机制**未查明**

`read_jsonl` 每拍重读整个文件，而事件应用是**幂等**的（每条事件对状态是确定的赋值）——
**按这个设计，漂移不可能发生。** 所以下面两条必有一条成立，而我**没有区分出来**：

1. 实际部署的代码在准入路径上与仓库里这份不同；
2. 存在一处我**没找到的**对 `active` / `finished` 的写入。

**没有把"我猜的机制"写在这里。** 上面第 1 条只是未排除，不是结论。

### 必须做的两件事

1. **给控制器加自检**：每 N 拍从零重放一次事件、与增量状态比对，不一致就记日志。
   **这是唯一能把机制钉下来的办法**——现在只有症状和旁证。
2. **给监视器加"停摆"判据**：`runner 有未提交的会话` 而 `controller 报 waiting=0`
   → 直接重启控制器。**这个判据不依赖机制**，能立刻止血，且下一个 run（rl99fix）
   用的是同一份代码，**还会再犯**。

前十六次都是"**我以为某个数/某张表/某个流程是什么**"。

## 十八、§十六 的**诊断被推翻**：那是我的脚本 bug，不是控制器的

### 我改了什么结论

§十六 写着：把控制器自己的规则离线重放得到 `waiting = 21`，而 live 报 0，
**因此控制器状态漂移**。**这个诊断是错的。**

### 错在哪

**live 控制器处理五种准入事件**（`queued / admit / resume / pause / release`），
**我那个离线重放只处理四种——漏了 `resume`。** 漏掉它会把"已恢复"的会话算成非活动，
于是 `waiting` 被算高。

**修正 `resume` 之后，同一份日志给出 `waiting = 0`，与 live 完全一致。**

### 我在这一件事上给过三个数，全错

| 我给出的 | 实际 | 错因 |
|---|---|---|
| 诊断当时："重放得 21，live 是 0 → 漂移" | 重放应为 0 | 重放漏 `resume` |
| 修 `resume` 后："停摆那刻重放得 11" | 仍待定 | 时间轴截断位置未核 |
| 自检首跑："live a=True / replay a=False" | 方向相反 | 同一个 `resume` 遗漏 |
| 修 `resume` 后自检："live a=False / replay a=True，但两边 waiting 都是 95" | **自检自相矛盾** | **未查明，自检本身还不可信** |

### 现在能确定的与不能确定的

**能确定**：
1. **停摆是真的**——runner 在 894/999 停死 29 分钟，`submitted == completed` 且 `active=0`。
2. **重启控制器确实让 run 恢复**（894 → 919 → 999 完成）。
3. **live 控制器在停摆时的状态与"重读日志"一致**（修正后 `waiting=0` 两侧相同）。

**不能确定**：**为什么重启会让它恢复。** 如果 live 状态本来就是对的，
那"重启修好了状态漂移"这个解释**站不住**——恢复的原因现在**完全不明**。

### 教训（这是今天最重的一条）

**我差点把"漂移"作为一个已证实的机制写进断言登记表，而它是我的脚本 bug。**
§十六 里我写了"机制未查明"，那是对的；**但同一条里把"重放得 21"当成了旁证**——
而那个数本身就是错的。**"机制未查明"救了我，但只救了一半**：

## 十九、**V3 被源码推翻**：`cap3_r2` 从来就是有效的 cap3

### 原来的 V3

> `cap3_r2` **跑的其实是 cap4**：`cap` 字段 200 条全是 3，但 **195/200 次准入发生在
> `active=3` 时，落地后 4 个在飞**。

**这句的依据是"`active` 是放行【前】的在飞数"。源码说不是。**

### 源码（`TraceLab/replay/src/session.rs:186-226`，逐字）

```rust
let mut cur = state.active_sessions.load(Ordering::Acquire);
while cur < cap {                                   // ← 循环条件
    match state.active_sessions.compare_exchange_weak(cur, cur + 1, ...) {
        Ok(_) => { claimed = true; break; }
        Err(actual) => cur = actual,
    }
}
if claimed {
    state.log_admission("admit", session_id, session_ordinal, cap,
                        cur + 1,                    // ← 记录的是【自增之后】的值
                        waited_since, prompt_tokens);
```

**两条都是决定性的**：

1. 记录的 `active` 是 `cur + 1` —— **放行之后的计数**；
2. CAS 的循环条件是 `cur < cap`，**`cur = 3` 时不可能放行**。

所以"准入发生在 `active=3`"= **"放行后 3 个在飞"** = **正确的 cap-3 行为**。
**V3 的推理（"落地后 4 个在飞"）建立在错误的字段语义上。**

### 今天的重跑是独立佐证

`cap3_fixed`（今天重跑）与 `cap3_r2` 的准入分布**完全相同**：

```
两条都是：admit 200 / release 200
两条都是：active=1 → 2 次 (1.0%)，active=2 → 3 次 (1.5%)，active=3 → 195 次 (97.5%)
```

**同一个签名 = 同一个行为。** 一条被我们判为"有效"、一条被判为"无效"，
而它们在做同一件事。

### 后果

- **`cap3_r2` 的数据是有效的**，可以进表。任务 #31 的前提（"原数据无效"）**不成立**。

## 三十、熔断在保护缓存，而它的判据是池子——把今天所有线索串起来（2026-09-22 12:10）

### 起点：一个说不通的现象

`foyfix_hc` 跑到 341/999 时平均并发稳在 **2.78**（三个节流关掉了、目标 0.95、带 HiCache）。
查控制器日志：

```
卡住周期      87.0% → 22.9%     ← 三个节流确实咬人，修对了
卡住时 headroom 中位 −10,008，79.3% 为负   ← 现在是"真装不下"，行为正确
★ valve 触发  2032 / 3067 = 66%
     valve 时 池子占用 中位 0.345   ← 池子只用 34.5%
     valve 时 TTFT 中位 16,807 ms   ← 但延迟 16.8 秒
   非valve 时 池子占用 0.664 / TTFT 4,688 ms
```

`valve` 的两个触发条件（`controller_foyer.py:414-417`）：

```python
valve = usage >= 0.93                    # ① 池子占用 —— 没触发（只有 0.345）
valve = valve or TTFT中位 > 10000 ms     # ② 延迟 —— 这个触发了（16.8 秒）
```

**熔断在保护延迟，而池子空着 65%。**

### 为什么池子空着 TTFT 还高：TTFT 就是 prefill

按【需要重算的 prompt token 数】分桶（`pois200_foyfix_hc/steps.jsonl`，406 个成功步）：

| uncached token | n | TTFT 中位 | TTFT p90 | 命中率 |
|---:|---:|---:|---:|---:|
| 1–2,000 | 113 | 4,881 ms | 28,597 | 95.7% |
| 2,000–8,000 | 111 | 2,364 ms | 17,466 | 77.8% |
| 8,000–20,000 | 129 | 11,394 ms | 31,940 | 20.0% |
| 20,000–40,000 | 48 | 16,804 ms | 85,398 | 16.6% |

**TTFT 的量级 = 要重算的 token 数 × 1.08 ms/token**（重算 20k–40k → 实测 16.8 秒；
按 1.08 ms/token 算是 21.6–43 秒，同量级）。**pool 有多空，跟 TTFT 没关系——TTFT 是 prefill，不是 decode。**

### 那重算是从哪来的：拆成两块

用 `planned_prefix_hit_rate`（trace 期望能命中的比例）对 `server_prefix_hit_rate`（引擎实测）：

```
planned 中位 0.845    server 中位 0.761
  planned ≈ server（差 ≤5pp）   : 316/406 = 77.8%
  planned 远高于 server（>30pp）:  80/406 = 19.7%   ← 该命中却没命中

server 命中率按轮次：
  round 0  0.000      ← 冷启动
  round 1  0.621
  round 2  0.877
  round 3  0.907
  round 4  0.917
```

**重算有两个来源，性质完全不同：**

```
① 冷启动（round 0，占 21% 的轮次）  →  不可避免：每个会话第一轮都要 prefill 完整 prompt
② 该命中却被挤掉（19.7% 的轮次）     →  【可避免】——这是准入控制唯一能使上劲的地方
```

### 于是所有线索串成一条

```
准入判据看【池子占用】
      ↓  但最优点上池子只用 66%（§二十七）
真正先耗尽的是【前缀缓存】
      ↓  缓存被挤 → planned 该命中却没命中（19.7%）
      ↓  命中率掉 → 要重算的 token 变多
      ↓  TTFT = 重算 token × 1.08 ms → 16.8 秒
      ↓  SLO 熔断触发（66% 的时间）
      ↓  不放人 → 平均并发卡在 2.78，墙钟输给 cap4
```

**熔断在保护的东西是缓存，而它的判据是池子。两者之间没有因果关系——只是碰巧相关。**

### 顺带纠正我今天说过的一个错

我先前解释"4 个会话只产生 1.5 个在跑请求"时说"**agentic 会话在 tool_wait 里不占 KV**"。
实测 `tool_wait_after_ms`：**中位 0.1 秒**（p90 12.6 s，>10s 的只占 11.3%）。

**这条 trace 根本没有 agentic 的"等工具"间隙。** 那个解释对这条负载不成立，撤回。

**真正的原因**：每次请求 **45% 的时间花在首 token 之前**（中位），也就是在 prefill——
引擎的 `num_running_reqs` 低估了在飞会话，是因为大量时间在 prefill 而非 decode。

**判据**：解释"为什么数值对不上"之前，先看**这个负载的构成**。我以为的 agentic 形态和这条 trace 不是一回事。

## 三十一、上限测试的初步结果：**关掉三个节流没有赢，反而两头都更差**（2026-09-22 12:35）

### 数（341/999 步，同 trace 进度比较）

```
run            平均并发   客户端TTFT中位   p90      引擎侧
cap4_hc          3.93       5,324 ms    23,436     (全程)
foyer_hc         2.06       2,073 ms     7,115     (全程)
foyfix_hc        2.78       6,630 ms    30,165     (前341步)
```

**`foyfix_hc` 被 `cap4_hc` 全面压制**：并发更低、TTFT 更差。
**连 `foyer_hc` 都比不过**——TTFT 差了 3.2 倍。

### 所以 §二十四 那个诊断只对了一半

**对的部分**：三个节流确实在咬人。卡住周期 **87.0% → 22.9%**，
卡住时的 headroom 中位从 **+46,658（有地方却不放）** 变成 **−10,008（真装不下）**，行为修对了。

**错的部分**：**修好节流并没有换来墙钟或延迟的改善。**

原因是：**控制器有两个保护延迟的机制，关掉一个，另一个立刻接管。**

```
三个遗留节流    关掉  →  熔断改成 66% 的时间在触发
                        ↓
                 放人更猛 → 要重算的 prefill 更多 → TTFT 冲到 16.8 秒
                        ↓
                 熔断锁死 → 不放人 → 并发卡在 2.78
```

**净效果比原来更差**：原来两个机制一起温和地限流（并发 2.06，TTFT 2.07 秒）；
现在一个机制粗暴地限流（并发 2.78，TTFT 6.63 秒）。

### 这条对论文意味着什么

**并发不是被 bug 限住的，是被控制器自己的延迟目标限住的。**
把 bug 修掉，目标本身还在那里。**要在这个目标下拿到 cap4 的墙钟，在逻辑上就不可能**——
因为 cap4 的墙钟正是【放弃这个目标】换来的（cap4_hc 的 SLO 只有 63.4%）。

**这是从控制器内部，第三次验证同一个结论**（前两次：§二十七 的结构性论证、§十五 的门槛翻转）。

### 但还有一个乐观的读法，我没排除

熔断**是振荡的**（放人→TTFT 冲高→锁死→慢请求走完→回落→再放人）。
**振荡本身可能是控制环没调好，而不是目标本身不可达。**

```
悲观读法：控制器到头了，目标决定上限
乐观读法：控制环在剧烈摆动，阻尼调好可能【两头都改善】
```

**这两种读法可以用同一个实验区分**：给熔断加滞回（hysteresis），看并发和 TTFT 能不能同时改善。
**这是"调策略"里最便宜的一个。**

### 状态

`foyfix_hc` 跑到 ~14:10 结束。届时：
- 若全程仍被 cap4_hc 压制 → 悲观读法成立，考虑是否放弃"墙钟反超"
- 若后段并发爬上去而 TTFT 回落 → 乐观读法有戏，试滞回

**判据修正**：§二十四 写的"平均并发 3.8–4.0 = 成功"**不够**——那只看了并发。
**必须同时看 TTFT**：拿到并发却毁掉 TTFT，只是用另一种方式变成了 cap4。

## 三十二、策略方向：**熔断期间不要停，改成"只放缓存友好的"**（2026-09-22 12:55）

### 先排掉三个候选 bug（都不是）

1. **熔断窗口有偏？** 控制器报的 `ttft_p50` 对真实"近 60 秒完成"的中位，
   中位差 **−294 ms**——**没有系统性偏高**。不是 bug。
2. **熔断在抖动还是锁死？** 116 个开关段：**ON 段中位 6.1 秒**、OFF 中位 21.3 秒
   （控制环约 2 秒一拍）。**是 bang-bang 抖动**，另有少数长段（p90 597 秒）。
3. **触发率对得上吗？** 真实"最近 20 个完成"中位 > 10 秒的时间占比 **48.9%**，
   控制器 valve=True 占 **66.0%**——差约 17pp，正好是 `usage >= 0.93` 那条触发贡献的。
   **熔断照规则做事，没有 bug。**

### 真正的发现：按时间加权和按请求数加权，结论相反

```
按【请求数】加权   SLO = 89.8%     九成请求在 10 秒内
按【时间】加权     熔断触发占 49%   一半的生命在"停止放人"
```

**两个都对，因为熔断一开就没请求完成**——高 TTFT 的时段里请求少，
于是请求数加权看不出来，时间加权一看就是一半。

**一半的墙钟花在空等。**

### 所以策略改哪儿

熔断现在的动作是**全停**。但它停的时候，系统并非无事可做——**它只是不能承受"再来一个冷 prefill"。**

而实测：

```
round 0   命中率 0.000    ← 新会话第一轮，要全量 prefill（约 21k × 1.08ms ≈ 23 秒）
round 1   命中率 0.621
round 2   命中率 0.877
round 3+  命中率 0.907+   ← 已经很便宜的增量 prefill
```

**所以：熔断期间不该全停，该"只放缓存友好的"。**

```
熔断 ON 时：
  已经在跑的会话（round ≥ 1）  →  继续放，它们的增量 prefill 很小
  全新会话（round 0）          →  拦住，它们会带来一次全量 prefill
```

**理由**：round-0 会话的边际代价是约 23 秒的 prefill；round-2+ 会话的边际代价是
上下文的增量（几百到几千 token）。**两者差两个数量级，而现在的熔断把它们一视同仁。**

**这是策略改动，不是调参**：改的是"熔断时做什么"，不是"熔断在哪个阈值触发"。

**而且它不需要 clairvoyance**：会话已经跑到第几轮，是中间件本来就能观测到的状态，
不是对未来的预测。

### 待验

- **假说**：熔断期间放 round≥1 的会话，能同时改善并发和 TTFT（因为用掉了空等的容量，
  且不引入长 prefill）。
- **反例**：如果 round≥1 的增量 prefill 也不小，或者引擎的调度让它们和已有请求抢带宽，
  那并发上去了 TTFT 还是掉——那就说明空等是必要的。
- **怎么测**：现有 run 都在，这是一个纯控制器改动，`foyfix_hc` 跑完后可以立刻试。

### 补记（13:15）：部署这件事本身有两个坑，都差点踩上

**坑一：看门狗会从路径重启。** 部署脚本是原子的（`scp` 到临时名再同目录 `mv`，
即 `rename(2)`），所以**正在跑的进程保持旧 inode，不会被撕裂**——这一点脚本头部已经写明，
是因为 09-21 踩过（`scp` 就地截断，bash 逐行读取时执行了半行拼接）。

**但那是另一个问题。这里的坑是：看门狗用 `bash -c while ...; do python <路径>; done` 重启。**
部署之后一旦控制器被杀，**重启出来的就是新代码——实验中途静默换掉控制器**。
而"控制器被杀"正是 09-21 停摆那个场景，它真的会发生。
**所以：有 run 在跑时，不部署它正在用的那个控制器。**

**坑二：本地 `run_matrix.py` 比 lab 的旧。**

```
本地  scripts/run_matrix.py                        4af0bb3309c2
lab   TraceLab/replay/scripts/run_matrix.py        90958758c26b
```

**按常规"改本地再部署"会把 lab 上的新版本覆盖回去。** 差的内容没细看，
但既然 lab 是新的，**默认假设 lab 是对的、本地是欠同步的**。

**绕开的办法**：把新行为做成**默认开启**（`--disable-valve-warm` 关掉），
于是 lane 脚本的策略串**一个字符都不用改**，也就不需要动 `run_matrix.py`。
行为差异由 metadata 里的**控制器代码哈希**记录——那才是真正管用的凭据。

**判据**：**改动之前先比两面 md5。** 仓库里的副本不一定是 lab 上正在跑的那份。

## 三十三、文献调研（2026-09-22，外部 agent 检索）：**一条大威胁 + 一条干净的缝**

### 🔴 最大的威胁：MARS + muyuan 插件

`MARS`（arXiv:2604.26963，Duke；**二手**）+ openEuler 的 **muyuan offloading plugin**（**代码，非论文**）：
**外部控制面 + KV-only 准入闸门 + AIMD 自适应窗口 + out-of-tree 不改引擎源码 + 双压力遥测（CPU + KV）**。

差别只在：它是多资源（CPU+KV）、面向 vLLM/Ascend、**判据是 KV 占用而非前缀缓存外部性**。

> **行动：列为下一篇必读，逐条 diff。** 在没读完之前，不能在任何地方声称"我们是第一个引擎外做会话准入的"。

### 🟢 看起来还干净的缝

1. **准入的输入是"这条到达请求对前缀缓存的【外部性】"**——它会不会共享已有前缀、会不会把别人在等的块挤掉。
   - `PEEK`（arXiv:2607.02525，**直查 abs**）从"排队需求"侧接近（保护祖先块 + 簇首先放），但它是**引擎内、多卡**，且目的是批内复用，不是评估"放它进来会不会挤掉别人"。
   - `PrefixShield`（arXiv:2608.01657，**二手**）从"块责任"侧接近（admission debt）。
   - **没有论文把"预测的单请求前缀外部性"当准入判据，更没有在会话粒度上做。**
2. **非先知 + 缓存感知的交叉。** 理论线（GSA 2601.22996、regime-aware 2607.09248、WAIT 2504.11320）**明确假设 kill-and-restart、无前缀缓存**，甚至假设同 prompt、离线同时到达。系统线是缓存感知但没有非先知界。**这条缝是干净的。**
3. **"在墙钟最优点上，绑定资源是前缀缓存而非 KV 池"这个解离现象**——没找到任何论文报过。
   我们的实测（池 66% 占用 / 逐出 +64% / 命中 −22pp / N=4→5 悬崖）是这条缝里**唯一的实测锚点**。
4. **会话 wall-clock 与每用户 SLO 的双目标前沿显式刻画 + 在此之上选准入工作点。**
   现有文献要么说指标本身错了（arXiv:2410.14257），要么说延迟优先调度在 agentic 下错了（PipeSwift 2609.16491、Astraea 2512.14142），**没人画这条前沿并给出选点规则**。

### 📗 支持我们机制叙事的可引证据

- **Metronome**（arXiv:2607.02640，**直查 abs**）：单卡上"无界 per-session 状态会按 per-request 延迟看不见的时钟耗光 KV 池"，
  导致硬崩溃；并明说**没有 per-session 窗口时，同一个控制器会 over-admit 撞墙**。
  **这条直接支撑"熔断在保护缓存、判据却看池子"那个机制叙事。**
- **Sarathi-Serve**（OSDI '24，**二手**）：prefill 优先调度造成 generation stall 可达数秒。chunked prefill 把迭代延迟与 prompt 长度解耦。
- **Nexus**（arXiv:2507.06608，**二手**）：**量化了干扰幅度**——prefill 的 KV 从 2K 增到 10K，decode 延迟 **+36%**。

  这直接解释了 TTFT 的量级，值得在实验机上 `--help` 核实。
- **DistServe**（OSDI '24）自己的 limitations 明说：资源受限（少卡/单卡）场景下 PD 分离**可能不如共置**（**二手**）。

**准入不是最大杠杆，排序才是。** 这与我们"在静态 cap-N 最优点上，准入信号的边际收益已经耗尽"**方向一致**——
但 MARS 从未做这个归因。**我们的 dissocation 是独立的。**

### 裁决

**我们的"下一步机制（prefix-cache externality 准入）"经受住了检验，是干净的空白。**
**但支撑它的那句定位——"外部准入控制"——已经被 MARS 和 muyuan 双重占位，必须改写。**

### 补记（13:50）：§三十 那句"TTFT 就是 prefill"**说过头了**，修正

§三十 写的是「TTFT 的量级 = 要重算的 token 数 × **1.08 ms/token**」。**这是拿带负载的回归系数当纯 prefill 用了。**

服务器启动日志给出的**孤立 prefill 吞吐**（`server_30032_pois200_foyfix_hc.log`）：

```
Prefill batch, #new-token: 2048, #cached-token: 0, input throughput (token/s): 4842.64
```

```
1.08 ms/token  →  925 token/s     ← 账本 R9 的"重算"值：带负载的端到端回归，含排队
0.21 ms/token  →  4,800 token/s   ← 服务器实测的孤立 prefill
                                      差 5 倍
```

**两个数都真，但测的不是一件事。** 于是 TTFT 应该拆成两段：

```
21k prompt 的纯 prefill       ≈ 4.4 秒   （21,480 / 4,800）
实测 TTFT 中位                 6.6 秒
熔断时 TTFT 中位              16.8 秒
                                →  排队占大头，尤其熔断期间
```

**这不削弱策略，反而加强它**：热会话不只在 prefill 上便宜（1,933 vs 15,720 token），
**它们在队里占的时间也短**。所以"熔断期间只放热会话"的理由比 §三十二 写的更足。

**判据**：**同一个物理量在"孤立"和"带负载"下是两个数，别混用。**
另外这条也说明：**服务器的启动日志里有生效配置和吞吐，读它是免费的**——
`chunked_prefill_size=2048`（24GB 卡的自动值，文献报告猜的那个数，实测确认）、
`schedule_policy='fcfs'`、`radix_eviction_policy='lru'`、`hicache_ratio=2.0`。

## 三十五、设计草稿：prefix externality 到底用什么信号（**未实现，只是把可用量列清楚**）

MARS diff（§三十四）把贡献收敛到一条：**把"这条会话到达对前缀缓存的外部性"当准入信号**。
那就得回答：**零引擎改动的前提下，这个量测得到吗？** 把可用量列一遍：

### 逐会话（来自 `steps.jsonl`，控制器每拍已经在读）

```
prefix_len / input_len / prompt_len          这一轮的上下文构成
server_cached_prompt_tokens                  实际命中多少
server_uncached_prompt_tokens                实际要重算多少   ← 直接就是"这一轮的外部性"
server_prefix_hit_rate / planned_prefix_hit_rate   实测 vs trace 期望（两者之差 = 被挤掉的量）
round_idx / tool_wait_after_ms               跑到第几轮
```

### 引擎聚合（来自 Prometheus，控制器每拍已经在读）

```
sglang:evicted_tokens_total      逐出速率        ← 缓存压力的直接读数
sglang:cached_tokens_total       累计命中
sglang:cache_hit_rate            聚合命中率
sglang:token_usage               池占用（现在只用了这个）
```

### 第一步（已实现，`foywarm_hc`）：**用"跑到第几轮"当外部性的粗代理**

理由是实测出来的：**round 0 的未命中量中位 15,720 token，round 1+ 是 1,933——差 8 倍**（§三十）。
`warm_only` 就是在熔断期间只放后者。

### 第二步（**未实现**）：把"逐出速率"加进来

```
冷会话 + 逐出速率高   →  它会挤掉别人   →  拦
冷会话 + 逐出速率低   →  池子有余量     →  放（现在这一步也放，但熔断会把它一起拦掉）
热会话               →  总是便宜         →  总是放
```

`evicted_tokens_total` 是现成的累计计数器，取相邻差就是速率。**这一步不需要新的可观测量。**

### 还没解决的问题（写在这里免得忘）

**"共享"这一侧测不到。** 上表全都是**事后**的量（这一轮已经跑完了才知道命中多少）。
要**事前**判断"这个新会话会不会命中已有前缀"，需要知道引擎 radix 树里有什么——
而 SGLang 只暴露聚合命中率，**不暴露树**。

**这是一个真问题，不是实现细节。** 候选出路：

1. **用同会话历史外推**——一个会话上一轮命中率高，下一轮大概率也高（agentic 的 prompt 是单调增长的）。
   **这条不需要引擎配合**，而且我们已经有 `server_prefix_hit_rate` 的历史。
2. **用 trace 的 planned 值**——但那是 clairvoyance，不做。
3. **让 runner 把前缀指纹报给控制器**——runner 是我们自己的，不算改引擎。但会引入新的耦合。

**倾向 1**，因为它保持在"只读遥测"这条线上，且不需要新信息。
**待验**：同会话相邻两轮的命中率相关性有多高？这个用现有数据就能算。

### 补记（14:05）：同会话逐轮命中率的相关性——**测了，是弱信号**

§三十五 留的那个待验问题，用现有数据（`foyfix_hc` + `foyer_hc`）算掉了：

```
相邻两轮配对 n = 1237
上一轮命中均值 0.557   这一轮命中均值 0.769
Pearson r = 0.382                                   ← 弱正相关

按上一轮命中分桶 → 本轮中位：
  上轮 0.00-0.10 (n=377)  →  0.728
  上轮 0.10-0.50 (n=107)  →  0.843
  上轮 0.50-0.80 (n=192)  →  0.859
  上轮 0.80-0.95 (n=335)  →  0.918
  上轮 0.95-1.01 (n=226)  →  0.951
```

**两条结论：**

1. **上一轮命中率可用但弱**（r=0.382）。分桶均值单调且分得开（0.73 → 0.95），
   所以"比不用好"，但**精度不足以支撑依赖它的决策**。
2. **更重要的：哪怕上一轮命中 0%，这一轮也有 73%。**
   **所以粗代理"跑过一轮就算热"抓住了绝大部分**——这正好支持已经写好的 `warm_only` 改动。

**设计上的排序因此改变**：第二步（把"逐出速率"加进判据）**比**第三步（逐轮预测命中率）更值得做。
预测那条的边际收益被 r=0.382 限住了，而逐出速率是**当前**的、不需要外推。

### 补记（14:00）：守望第四次出问题——**把"状态"当成了"事件"**

持久守望每 5 分钟重复报一次 `DONE cap3_hc`。原因：


**"文件存在"是一个【状态】，不是一次【事件】。** 状态该在**变化时**报一次（边沿触发），

**改法**：记住上一轮的状态，只在 `0 → 1` 时输出。

## 四十、**机制抓到了：静态 cap 会掉进"驱逐螺旋"，而且它自己看不见**（2026-09-22 16:15）

### 怎么找到的

§三十九 留下一个问题：`cap3_r2`（SLO 62.2）与 `cap3_fixed`（SLO 74.4）**同配置、
墙钟只差 2.2%，SLO 差 12.2pp**。要么是"悬崖附近不稳"，要么是 harness 口径差异。

**把 run 内部切成十段看，直接就分开了。** 不是口径差异——是**两种完全不同的运行状态**：

```
每 100 步的 SLO%
  cap3_r2     98 → 64 → 91 → 80 → 61 → 61 → 42 → 53 → 44 → 27    ← 一路滑下去
  cap3_fixed  74   76   75   83   66   76   88   75   72   59    ← 在带内摆，无趋势
  foyer_hc    97   94   93   91   91   80   92   87   82   91    ← 稳

每 100 步的前缀缓存命中率 %
  cap3_r2     63 → 51 → 60 → 59 → 53 → 52 → 40 → 43 → 32 → 27   ← 命中率崩了
  cap3_fixed  57   58   56   59   58   53   60   57   54   53   ← 平
  foyer_hc    67   63   65   66   63   63   68   64   64   64   ← 平

每 100 步的平均单步耗时 (秒)
  cap3_r2     22 → 40 → 21 → 39 → 35 → 41 → 52 → 48 → 51 → 66   ← 退化 3 倍
  cap3_fixed  33   31   24   30   48   28   20   30   32   46   ← 平
  foyer_hc    18   24   26   24   22   26   18   24   27   26   ← 平
```

**而这三条 run 的输入长度分布是重叠的**（约 5,400–8,500 之间摆动，三条同区间），
**负载没有变重。** 变的只有命中率。

### 所以机制是

**静态 cap 只看"现在有几个在跑"，看不见池子被驻留会话占了多少。**

```
run 推进 → 驻留会话越来越多 → 它们的前缀占住池子
        → cap3 仍然照放 3 个（它只会数数）
        → 新请求进来要驱逐别人的前缀
        → 命中率掉 → 每个请求要重算更多 prefill → 更慢
        → 在跑的那 3 个占位更久 → 池子压力更大
        → 命中率再掉……                        ← 正反馈
```

**这是一个螺旋，不是噪声。** `cap3_r2` 掉进去了（63→27），`cap3_fixed` 没有（稳在 55）。
**同一个配置、同一条 trace、两次运行，落在螺旋的两侧。**

> **这就是 §二十七 和 §三十五 一直在找的那个"缓存外部性"，
> 现在有直接的测量了：它不是理论担忧，它决定了 run 是活着还是崩掉。**

### 为什么这条比"快 4%"强得多

```
原来能写的    Foyer 比静态 cap 快 1.2–4.5%              ← 对 2.2–4.1% 的噪声，等于没有
现在能写的    静态 cap 在悬崖附近是【双稳态】的：
              同一配置同一 trace，一次保住 SLO 74.4%，一次掉进螺旋只剩 62.2%，
              而且螺旋在 run 内部可见（命中率单调下滑，单步耗时退化 3 倍）。
              Foyer 的利用率目标控制把命中率钉平，run 内部 SLO 稳在 80–97。
```

**准入控制卖的是 SLO 保证，不是墙钟。这条主张正好落在它该落的地方。**

### 但它还缺三块，都有 run 在排队

```
缺什么                              用哪条判              预计落地
──────────────────────────────────────────────────────────────────
cap3_r2 是不是 harness 假象         cap3_r3（当前 harness）   ~22:50
高负载下螺旋是不是提前（cap2 也掉）   cap2_x2 / cap3_x2        ~01:10 / ~05:00
低负载下静态 cap 是不是纯浪费        foyer_x05               ~09:00
```

**`cap3_r3` 是最关键的一条**：如果它也掉进螺旋 → 双稳态是真实的；
如果它稳稳落在 74.4 → `cap3_r2` 是孤立事件，这条立论要收回。

**判据写在这里，跑出来之前不改口。**

## 四十四、查了那条假设：**控制器确实被自己的预留吓住，但"预留是浪费"这个结论被它自己的消融反驳了**（2026-09-22 16:10）

### 一、控制器的账本（`pois200_foyer_hc`，8784 个控制周期）

**先修一个我自己的单位错误**：`usage` / `highwater` 是**分数**（0–1），

```
growth_sum    26,762         26.4%      ← 纯预留，无条件相加
```

## 四十七、换策略第一步：**热会话按"实测边际代价"计费，而不是按整轮 ctx**（2026-09-22 17:15）

### 找到的具体抓手

准入块里的这一行：

```
base = s["ctx"] or s["prompt0"]
n = (base + forecast(s)) * args.margin
```

`ctx` 是**这一轮的整轮 prompt 长度**（约 20k 量级）。但一个**热会话**（跑过至少一轮）
的前缀**已经在引擎里**，而 `projection` 的 `resident` 项**已经算了它**：

```
projection = max(resident, ctx_sum) + growth_sum
                    ↑ 引擎实测占用，已含热会话的驻留前缀
```

**再按 `ctx` 收一次 = 同一批 token 计费两次。** 实测差距：

```
round 0   未命中中位 15,720 token   ← 真的要从头 prefill
round 1+  未命中中位  1,933 token   ← 前缀基本都在
tool_wait 中位 0.1 秒                ← 所以前缀几乎必然还在
```

**超收 3–10 倍。这就是控制器停在 2.06、而硬件能撑到 2.9 的最可能原因。**

### 改动（`controller_budget3.py`，加一个开关，默认保持旧行为）

```python
ap.add_argument("--charge-mode", choices=["full", "delta"], default="full")

# 记录引擎自己量的边际代价
unc = rec.get("server_uncached_prompt_tokens")
if unc is not None:
    s["uncached"] = float(unc)

# 准入计费
base = s["ctx"] or s["prompt0"]
if (args.charge_mode == "delta" and s["last_round"] >= 0
        and s.get("uncached") is not None):
    base = s["uncached"]        # 引擎实测的边际代价，不是模型估的
n = (base + forecast(s)) * args.margin
```

**为什么用 `server_uncached_prompt_tokens`**：它是引擎对"这条会话这一轮实际要重算多少"
的**直接测量**，不是我的模型。而且它已经在 `steps.jsonl` 里，控制器每拍都在读。

## 四十八、外部审查（GPT）逐条核实：**三条我错了，一条把 v4 实验判死**（2026-09-22 18:00）

### 一、`charge=delta` 的论证是错的（**我错了**）

我原来的论证：热会话的前缀已经在引擎里，而 `resident` 已经算了它，再按 `ctx` 收就是重复计费。

**GPT 指出：SGLang 的 `token_usage` 减掉了可驱逐的块。** 我去读了实验机上的源码：

```python
def _get_token_info(self: Scheduler):
    available_size = self.token_to_kv_pool_allocator.available_size()
    evictable_size = self.tree_cache.evictable_size()
    num_used = self.max_total_num_tokens - (available_size + evictable_size)
                                              ↑ 可驱逐的块被减掉了
```

**一个热会话回来时，它的前缀正是【可驱逐的】**（会话不活跃 → 块没被锁）。
**所以它不在 `resident` 里。** 放它进来会把这些块**重新锁住**，那确实消耗不可回收的容量。

> **所以不是重复计费。按 `uncached` 收反而【低估】了锁定的代价。**
> `charge=delta` 只能算"待验证的策略"，**不能叫修 bug**。

### 假说四：TTFT 对瞬时并发是凸的 → **成立，而且是唯一没被否掉的**


## 五十二、杠杆找到了：**控制变量应该是"并发总足迹"，不是"并发会话数"**（2026-09-23 00:50）

### 一、我先把上一节的一条结论收回

§五十一 里我说「TTFT 几乎完全由别人排在我前面的 prefill 量解释」——**那是错的**。

`pois200_cap4_hc`：提交时是否有别人的 round0 冷 prefill 在进行

### 二、这个事实指向的那个重复收费

`pois200_foyer_hc`，每 30 秒采样 200 次：

```
同时【存活】会话（持有许可）   中位 2.0   均值 2.10   最大 4
同时【在跑】请求（引擎里）     中位 1.0   均值 1.38   最大 4
停放比 存活/在跑               均值 1.52
存活会话上下文之和            中位 79,950 token = 池的 78.8%
```

**两个会话占着池子的 79%，而其中通常有一个正在停放（不产生任何计算）。**

对照控制器那一行：

```
ctx_sum  = sum(s["ctx"] for sid in active)   ← active = 已准入未结束
                                             ← 【包含正在停放的会话】
resident = 引擎实测占用                        ← SGLang 的 token_usage
                                             ← 【排除可驱逐块】，而停放的 KV 正是可驱逐的
projection = max(resident, ctx_sum) + growth_sum
                    ↑ 于是 ctx_sum 赢：78.8% 对 49.2%
```

> **`ctx_sum` 在给「正在停放、KV 可驱逐、回来时能从 HiCache 恢复」的会话全额收费。**
> 而 round 1+ 实测命中率 **89.8% = trace 计划值**——说明驱逐+恢复这条路是通的，代价已经付过了。
> **所以这笔收费是重复的。**

**§五十 预注册的 `bres` 判据（并发涨、SLO 不掉 → 反超）现在有了机制解释，把握比落地时更大。**
gpu0 在跑，03:20 出。

### 三、第二个发现：TTFT 断崖可能是**调度器假悬崖**，不是容量墙

从实测反推 prefill 速率：

```
并发 0–1 时 round1+ 的 TTFT 中位 857 ms，其未命中中位 2,717 token
  -> prefill 速率 ≈ 2,717 / 0.857 ≈ 3,170 tok/s

冷启动一个会话需 17,268 未命中 token -> 单独就要 5.4 s
并发 3–4 时三个串行 -> 16.3 s        -> 实测 16,841 ms（§五十二），几乎完全吻合
```

**而 SGLang v0.5.10 的 `max_prefill_tokens` 默认是 16,384——比一个冷会话的 17,268 还小。**
**一个冷请求自己就撑爆整个 prefill 批预算，别的请求一个都搭不上车。**

prefill 是访存受限的（读一遍权重），**批量 prefill 的边际成本几乎为零**——这正是
Sarathi-Serve（OSDI'24）拿到 2.6–5.6× 容量的机制，也是外部调研列为
「最想先看到的实验」的那一个：**它能一刀切开「真容量墙」和「调度器假悬崖」。**

### 四、外部对抗性调研的两条关键输入

1. **为什么调参越不过去（形式化）**：cap1…cap5 本质是 `池容量 / (平均上下文 × 安全系数)`
   这个比值的不同切法，不是五种调度策略。自适应控制器在这个集合里做的任何时变选择
   都是这些点的凸组合 → **必然落回前沿**。这比 §二十七 的表述更硬。
   实测吻合：`101,432 / (40,000 × 1) = 2.5`，而我们测到 2.93 稳、3.94 崩。
2. **我漏掉的一维**：我测过「命中率对不同【准入政策】不变」，**没测过「换【驱逐政策】」**。
   SGLang 的 `radix_eviction_policy` 可换（`lru`/`lfu`/`slru`/`priority`/`tlru`），
   官方文档明说 `tlru` 是为 agentic 多轮写的。**这是一个独立的、未测的轴。**

## 五十五、**主押注：round-gate——把「放几个进来」换成「同时在跑几个」**（2026-09-23 01:20）

### 一、这个想法从哪来

把两组实测摆在一起，缺口自己就露出来了：

```
foyer_hc（291.3 min，SLO 89.8）  每 30 秒采样 200 次：
   同时【存活】会话（持有许可）   中位 2.0   均值 2.10
   同时【在跑】请求（引擎里）     中位 1.0   均值 1.38
   停放比                       均值 1.52

静态 cap 的定义就是：限制【存活】会话数 = N
```

> **一个存活会话有一半时间在停放（tool_wait 均值 16.85 秒，§五十三）。**
> **所以 cap=N 在「这 N 个恰好都在停放」的时候，引擎是空转的。**
> **而 cap 对此无能为力——它根本分不清「占着位置」和「在干活」。**

### 二、执行器已经存在，不用改 runner

`session.rs:412-426`：

```rust
// Concur-style step-boundary pause: a paused session finishes its current round,
// then blocks until re-admitted
if state.permit_file.is_some() && state.session_paused(&session_id) {
    ... "pause" ...
    AdmissionGate::wait_unpaused(&state, &session_id).await;
}
```

**被 `paused` 的会话跑完当前轮，就在【下一轮开始前阻塞】，直到重新准入。**
控制器本来就有这条路（`shed` 在用），只是从来没拿它做限流。

### 三、改动：`--round-gate N`（`controller_budget3.py`，默认 0 = 旧行为）

```python
# 5c. ROUND GATE — cap the RUNNING count, not the live count.
if args.round_gate and len(active) > args.round_gate:
    extra = sorted(active, key=lambda s: sess[s]["arrived_ts"] or 0)[args.round_gate:]
    shed = list(dict.fromkeys(list(shed) + extra))
    for sid in extra:
        sess[sid]["active"] = False
```

被闸掉的会话**保持存活、保留许可、保留 KV**，等有人停放或跑完就从正常 FIFO 路径顶上。
决策日志新增 `round_gate` 字段，可事后核对参数生效。

### 五、必须事先写清楚的三个风险

1. **控制量有滞后**：被标 `paused` 的会话要跑完当前轮才真正停下，所以**实际在跑数会瞬时超过闸值**。

3. **可能只是"另一个 cap"**：如果 `rg3` 最终落在 (236, 81) 附近——也就是 **cap3_hc 那个点上**——
   那就说明「限在跑」和「限存活」在这个负载上等价，`nogate` 也会证明这点。**这条假说就死了。**

### 五十五·补一、**上机前的自查抓到一个设计错误**（2026-09-23 01:45）

写完之后我回头核对「控制器数的是不是我以为的那个量」，发现**数错了，而且错法会让整批实验作废**：

```
控制器 active_n        中位 2.0   均值 1.99   ← 匹配【存活】2.0 / 2.10
对照（steps.jsonl 独立算）
  同时【存活】会话      中位 2.0   均值 2.10
  同时【在跑】请求      中位 1.0   均值 1.38   ← 控制器数的【不是】这个
```

**`len(active)` 是【存活】数（含正在停放的会话），不是在跑数。**

原来的实现 `if len(active) > round_gate` 于是变成**又一个会话数 cap**——而存活数本来就只有 2.0，
所以 `rgate=3` **永远不会触发**，`rg3` 会原样复现 `nogate`，
**我会得出「限在跑和限存活等价、假说死掉」的错误结论。** 一个本来成立的机制会被我自己的 bug 杀掉。

**修法**：改用引擎自己报的 `sglang:num_running_reqs`（控制器本来就在读同一个 `/metrics`，
只是没取这个字段；`controller_budget3.py` 的 `em` 里就有）：

```python
running_n = em.get("sglang:num_running_reqs", 0) or 0
if (args.round_gate and running_n >= args.round_gate
        and len(active) > args.round_gate):
    extra = sorted(active, key=lambda s: sess[s]["arrived_ts"] or 0)[args.round_gate:]
    ...暂停...
```

两个条件都要满足：**引擎真的忙到闸值了，才暂停**；否则不碰。

**这次自查还厘清了机制的主次**：存活数只有 2.0，**是因为控制器的预算卡住，不是因为有什么闸**。
所以 `base=resident`（把停放会话从账上摘掉）**才是让存活数上去的主杠杆**，
`round_gate` 是**在存活数上去之后、防止在跑数冲垮 TTFT 的安全阀**。两者必须成对，单独任何一个都不成立。

### 五十五·补二、**把"为什么 round-gate 应该赢"量化**（2026-09-23 02:00）

补一里说清了主次，但还缺一个**可事先量化的预测**。补上。

#### 一、静态 cap 下在跑数是【波动的】，round-gate 下是【钉住的】

```
存活 L 个会话，每个约 1/3 时间在跑（park 占比 = 17s / (17s+45s) ≈ 0.34，
  实测 live/running = 1.52 反推 0.66，吻合）
静态 cap = N    -> 存活恒为 N，在跑数在 [0, N] 之间随机波动，均值 0.66N
round-gate = N  -> 存活可以远大于 N，只要有人停放就有人顶上 -> 在跑数【钉在 N】
```

#### 二、而 TTFT 对在跑数是强凸的，所以"钉住"本身就有巨大价值

`pois200_cap4_hc` 按提交时刻瞬时活跃数分桶：

```
在跑 0-1 :   857 ms
在跑 1-2 : 1,784 ms
在跑 2-3 : 5,038 ms
在跑 3-4 : 16,841 ms      <- 每加一个，TTFT 涨约 2.5-3 倍
```

请求数分布 `53 / 229 / 414 / 303`，加权平均在跑数 **2.47**。

```
E[TTFT]（实际，在跑数波动）  = 7,650 ms
TTFT(在跑数恒为 2.47)        ≈ 5,000 ms        <- 内插
Jensen 缺口                  = 2,650 ms = 35%
```

**即：在平均在跑数完全不变的前提下，只把波动压掉，平均 TTFT 就能掉 35%。**

#### 三、由此得到的预测（结果落地前写死）

```
若 round-gate 能把在跑数钉住（哪怕只钉住一部分）：
  cap4_hc 那一档的在跑数下，平均 TTFT 从 7,650 -> ~5,000 ms
  超 10s 比例从 36.6% -> ~15%
  SLO 从 63.4 -> ~85

  点 (213, 85)：前沿在 213 处 = 63.4  ->  【高出 +21.6pp】
```

**注意这个预测比补一里那个（+4.5pp）大得多**，因为补一用的是「并发→墙钟」的幂律（弱杠杆），
而这里是「波动→TTFT」的凸性（强杠杆）。**两个机制是叠加的，而且凸性这一条更强。**

#### 四、这条预测独有的**可判死**形态

```
若 rg2/rg3/rg4 的 SLO 不比同墙钟的静态点高      -> 在跑数没被钉住（波动没压掉）-> 假说死
若 SLO 高了但墙钟同比变慢，落回线上             -> 钉住换来的收益被墙钟吃掉了 -> 假说死
若 shed_n 的方差很大（反复 pause/unpause 抖动） -> 控制律不稳定，不是机制问题，要调阈值
```

**第二判据（补一里写的）仍然成立**：round1+ 命中率是否守住 89.8%。

### 五十五·补三、**墙钟的物理模型验通了**，以及它给出的精确预测（2026-09-23 02:30）

#### 一、模型

```
墙钟 = (产出token / 在跑均值) × 步时间
```

产出 token 由 trace 固定（70 万），所以**墙钟只依赖【在跑数的均值】和【步时间】**。

**在 10 条 run 上反推步时间**（`wall × 在跑 / 产出`）：

```
run              墙钟min   在跑均值   反推步时间
cap1              527.4     0.64       28.5 ms
cap2              304.2     1.04       26.9
cap3_fixed        258.7     1.32       29.1
cap4              249.9     1.48       31.6
cap5              260.9     1.62       35.9   <-- 唯一的异常值
cap3_hc           236.4     1.36       27.4
cap4_hc           213.0     1.60       29.0
foyer_hc          291.3     1.14       28.2
foyer_hz1         255.8     1.31       28.6
```

**步时间在 27–29 ms 之间几乎恒定**（28 ms ≈ 读一遍 15.2 GB 权重的 1.75 倍，说明步里有 prefill 混进来）。
**`cap5` 是唯一的例外：35.9 ms，比它邻居高 24%**——在跑 1.62 和 `cap4_hc` 的 1.60 几乎相同，
**但步时间涨了。这就是 thrash 把 prefill 挤进 decode 步的代价，也是 `cap5` 比 `cap4` 慢的原因。**

#### 二、这个模型解释了 `bres` 的反例

```
bres 把在跑从 1.14 抬到 1.36（+19%）
按模型墙钟该降到 291 × (1.14/1.36) = 244 分钟
实测持平（150/200/250 步：+3.3% / −4.5% / +0.6%，均值≈0）
```

**唯一的解释是它的步时间同比例涨了**——`cap5` 给了旁证：在跑数上去的同时步时间会涨，两者抵消。

#### 三、而 round-gate 和 `bres` 有本质区别

```
bres      靠【多放会话】抬高在跑数  ->  总量变大 -> 步时间跟着涨 -> 抵消
round-gate 靠【重新分配谁在跑】抬高在跑数 -> 总量不变，只是把波动抹平 -> 步时间不该涨
```

**关键在凸性**：`cap4_hc` 的在跑数分布是 `0:7% 1:39% 2:40% 3:12% 4:1%`（均值 1.60），

```
墙钟只看均值 1.60        ->  213 分钟（实测吻合）
TTFT 看的是整个分布      ->  E[TTFT] = 7,650 ms
而恒定在 1.60 时 TTFT ≈ 1,500 ms（该档实测中位）
```

**把在跑数钉在它的均值上，墙钟不变、TTFT 塌掉。这是 Jensen 不等式，不是估计。**

#### 四、精确预测（结果落地前写死）

```
rg2  在跑钉在 2.0  ->  墙钟 = 70万 × 0.029 / 2.0 = 170 分钟
                      TTFT ≈ 1,784 ms（1-2 档实测）-> SLO ≈ 90%
                      点 (170, 90)
                      前沿锚点从 213 起 -> 【170 在它左边】-> 平凡获胜

rg3  在跑钉在 3.0  ->  墙钟 ≈ 113 分钟，TTFT ≈ 5,038 ms（2-3 档）-> SLO ≈ 67%
                      点 (113, 67) -> 同样在前沿左侧
```

**注意 rg2 的预测同时赢在两条轴上**（更快【且】SLO 更高），而 rg3 是快很多但 SLO 低——
**两者都不在任何静态点的右侧，所以都算赢，只是赢法不同。**

#### 五、已排掉的执行风险

- **死锁**：single-flight 门要求「上一个被准入的会话已完成至少一轮」，而被闸掉的会话正是在
  轮次边界上停的（`last_round >= 0`），所以门照常放行。**无死锁。**
- **准入速率**：999 轮 / 200 分钟 = 每 12 秒一次，远低于每 2 秒一次的准入上限。**不是瓶颈。**

### 五十五·补四、**第二个会让实验作废的缺口：闸只管暂停，不管准入**（2026-09-23 02:50）

写完 round-gate 之后我检查了一遍它的动力学，发现**它本来会什么都不做**：

```
控制器 5c：running >= 闸值  ->  把最年轻的活跃会话标为 paused（移出 active）
          被暂停的会话落到 waiting
下一个周期：准入路径只看【内存】，不看 running
          于是它把刚暂停的那个会话【立刻重新准入】
          -> 会话在 pause/admit 之间来回抖，在跑数一点没被钉住
```

**这是 churn，不是限流。** 而它的表现是沉默的：run 会跑完，`shed_n` 会显示有暂停发生，
数字看起来"做了事"，**但结论会是「钉不住 → 假说死」——而真正的死因是我的实现漏了一半。**

**修法**：把闸加到准入路径上。

```python
running_n = em.get("sglang:num_running_reqs", 0) or 0      # 提到 shedding 之前算
...
gate_full = bool(args.round_gate) and running_n >= args.round_gate
if waiting and not valve and not gate_full and (prev_started or args.disable_single_flight):
    ...正常准入...
```

**闸的两半必须成对**：5c 负责把超出的暂停，准入侧负责在引擎已经忙到闸值时不再放人。
**只有暂停那一半，等于什么都没做。**

**防饿死仍在**：`starve-guard` 的条件是 `floor < 0.5`（内存低），闸下内存本来就低，
所以它会在 `oldest_wait >= 240s` 时强制放行一个——**闸不会把它变成饿死。**
（这也是我特意没有去动 starve-guard 的原因。）

**决策日志新增 `running_n` / `gate_full` 两个字段**，事后可逐周期核对闸是否真的在工作——
不是看 `shed_n` 有没有动，而是看 `gate_full` 的比例。

> **今天第二次了**：上一个缺口（`len(active)` 数的是存活不是在跑）会让 rg3 静默复现 nogate；
> 这一个会让暂停变成 churn。**两个都不会报错，两个都会让结论指向"机制不存在"，
> 而真正的死因是实现。** 教训：**在用一个自制的执行器去证伪一条假说之前，
> 先验证执行器本身在做什么。**

### 二、被证伪的是什么

§四十七/§五十 的假说：`ctx_sum` 在给「正在停放、KV 可驱逐、回来能从 HiCache 恢复」的会话
重复收费，去掉它应该"并发涨、SLO 不掉"。

**实测三条独立证据全部反向：**

```
引擎实测占用   41.0% -> 52.2%        【确实多放了会话】
round1+ 命中率 80.6% -> 80.8%        【没有驱逐螺旋，缓存守住了】
墙钟          291.3 -> 295.5 分钟     【但更慢了】
SLO           89.8% -> 83.8%         【而且 SLO 掉了 6pp】
```

**机制**（§五十五 的模型解释了它）：多放会话抬高了在跑数，**同时也抬高了步时间**
（`cap5` 是同一个现象的直接证据：在跑 1.62 vs `cap4_hc` 的 1.60，步时间 35.9 vs 29.0）。
两者抵消，墙钟没赚，而 SLO 白掉。

> **所以 `ctx_sum` 那笔收费是【承重】的。** 它在为「这些会话等会儿要回来」预留容量。
> **"重复收费"这个判断是错的**——§四十八 已经用 `token_usage` 排除可驱逐块否掉过一次，
> 这是第二次被否掉，这次是用端到端数据。

`hz0`（`horizon=0`，把增长预留整个关掉）同样 BELOW（−13.7pp），与 §五十 的预注册一致。

**rg 那批用的是 `base=resident`——刚刚被证伪的记账底座。** 判它仍值得跑的理由：

而且 `nogate` 正是用来把「记账的效应」和「闸的效应」分开的单变量对照。

**但如果 rg2/rg3/rg4 也失败，下一批应该把底座换回 `base=max`，只留闸。**

### 四、还活着的唯一一条

§五十五·补二 的凸性论证：**墙钟只依赖在跑数的【均值】，TTFT 依赖【分布】**。
在跑数分布是 `0:7% 1:39% 2:40% 3:12% 4:1%`（均值 1.60），抹平波动应能：
**墙钟不变、TTFT 塌掉**。

**这是唯一一条不依赖"多放会话"的机制**，它的实现（round-gate）正在跑（04:47 起）。
**如果它也失败，那就不是"某条路走不通"，而是"这个系统里准入策略与端到端墙钟无关"**——
那时应该转引擎侧（prefill 批预算 / KV 量化），那两条改的是上界本身。
