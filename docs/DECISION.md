## 二、两条事实

**1. `foyer_hc` 支配 `cap2`**：墙钟更短（297.6 < 310.5）**且** SLO 更高（89.8% > 89.5%）。
草稿"在 SLO ≥85% 约束下最快"成立。**但只快 4.3%**——正好是跨天不可归因的量级，
也正是配对实验要测的那一个数。

**2. `cap4_hc` 把取舍本身消掉了。** `cap4` 快但丢缓存（0.459），`cap2` 保缓存但慢（310.5），
而 **`cap4_hc` 命中率 0.681**（≈cap2 的 0.677、≈foyer_hc 的 0.697）**只要 219.0 分钟**。
**HiCache 让"保缓存"和"提并发"不再互斥**——而且它是个**没有控制器的静态配置**。
Foyer 剩下的唯一优势是 TTFT 那条轴（2228 vs 5473 ms）。

## 三、门槛是选的，赢家随它翻

```
SLO ≥ 85%   →  候选只有 foyer_hc 与 cap2，foyer_hc 快 4.3%
SLO ≥ 60%   →  cap4_hc 快 26%
```

同一份数据，换个门槛，"谁是赢家"翻过来。而 `SLO_MS = 10000` 这个常数和 `85%`
这个门槛**都没有依据来源**。

**所以框架问题的形状不是"我们的控制器快不快"，而是"服务等级定在哪"。**
那是产品判断。定了门槛，赢家就定了。

> ⚠ **不许做的事**：先看谁赢再选门槛。那是 R7 的同一类错误——
> 用一个事后挑的口径去支持一个事先想好的结论。

## 五、C 线现在手里有什么

**关于系统**：① 不治理的 agentic serving 在 24GB 卡上坍塌（命中率 1.6%、TTFT 中位 29.6 分、
SLO 3.0%）；② 逐请求解码速率不随并发上升；③ 会话侧与引擎侧之间没有稳定换算系数
（符号会翻转）；④ 216× 搬运比重算便宜。

**关于装置**：池守卫、池子静默缩水、唯一一对同条件重复差 0.6%、总 token 离散度 0.76%。

**方法学骨架（今天十次，同一族）**：差分错对象 → 相除错对象 → 统计量选错 → 仪器选错 →
表比产物旧 → 流程破坏前提 → 验证同义反复 → 进程活着当成在写 → 在写当成写的是有用的 →
**误删一条正确记录**。

> **十次里没有一次是数据错或算错。** 全是"这个数 / 这张表 / 这个流程，
> 已经不是我以为的那个东西了"。
> 最后一条性质不同：前九次的代价是**我以为的不对**，第十次的代价是
> **我把对的改成了错的**，而且没有机制会把它翻回来。
