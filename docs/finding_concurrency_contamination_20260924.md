# 发现：同机 ≥4 条车道会把步成本抬高 24~41%，四条控制器臂的数据作废

**日期** 2026-09-24 · **脚本** `scripts/lab/gen_concurrency.py`（审计）、
`scripts/lab/probe_concurrency.py`（时间分箱） · **数据** `paper/data/concurrency.csv`

## 怎么发现的

在做方向 B（把「host tier 决定准入控制有没有空间」做成主线）时，去查论文
§III 自己标为「the largest open question」的那件事：HiCache 族的九条臂
**重算量几乎恒定（8.6~9.1 M），但 τ₁ 却在 27.0~35.7 ms 之间散开**，论文原话是
"Whatever moves τ there is not recomputation, and we do not know what it is."

把八条 HiCache 臂的 τ₂（**逐请求 decode 间隔中位**，由 per-request 的
`(total_duration − first_token)/(output_len − 1)` 算出，客户端实测、**不经过采样器**）
按 R̄ 排开之后，出现了一个论文没注意到的分裂：

| 组 | 臂 | τ₂ |
|---|---|---|
| 正常 | cap4_hc / cap3_hc / foyer_hc / foyer_hz1 / foyer_sf0_r2 | 23.8 ~ 25.7 |
| **抬高** | **foyer_bres / foyer_hz0 / foyer_hz2 / foyer_breshz1** | **30.9 ~ 33.3** |

bres（R̄ 1.481）与 cap3_hc（R̄ 1.509）、foyer_hz1（R̄ 1.524）**连占用率都匹配**
（54.3% vs 55.5% / 54.1%），却慢 6.7 ms。四条高 τ₂ 的臂**恰好就是** 09-22 23:17–23:33
同一分钟启动、彼此重叠约 300 分钟的那一批（详见下表），当时四台 SGLang server
同机运行。

## 判据与验证

### 1. 不是时间局部的（排除"跑到一半有人挤进来"）

把每条 run 的 τ₂ 沿时间分 6~16 箱取中位（`probe_concurrency.py`）：

```
foyer_hz2     33.0 33.1 30.5 31.1 27.9 24.6    全程高
foyer_hz0     34.0 33.8 34.5 30.4 32.5 33.7    全程高
foyer_breshz1 33.5 33.9 34.1 33.9 33.3 28.8    全程高
foyer_hc      24.1 24.4 23.8 22.8 23.6 24.1    全程低
cap4_hc       25.5 27.2 25.4 25.6 26.1 25.5    全程低
```

外部进程**中途挤进来**会表现为某几箱出现台阶。这里是平的，即**整个测量窗口都被
同一个持续条件覆盖**——与"四条车道自始至终互相争用"一致。

### 2. 对照实验 1：cap1 在车道数变化处的跳变

`pois200_cap1`（20:13 起跑）独自跑了 5.5 小时，02:25 rl90/rl99 同时启动：

```
20:37 20:10 21:43 22:16 22:49 23:22 23:55 00:28 01:01 01:34 02:07 | 02:40 03:13 03:46 04:18 04:51
20.5  20.3  21.2  20.6  20.4  20.6  20.4  20.4  20.6  20.5  20.7  | 22.4  27.5  20.9  25.4  24.0
        └──────────── 1~2 条车道，恒在 20.3~20.7 ────────────┘        └── 3~4 条车道 ──┘
```

### 3. 对照实验 2：t85 与 rl99 在同一分钟同时回落

两条**独立**的 run，τ₂ 在 07:09~07:23（rl90 结束前后）**同一时刻**从 ~30 掉到 ~22~25：

```
t85   30.0 25.8 30.9 25.1 31.0 29.5 30.3 | 22.3 23.7 22.6 22.0 22.4 23.4 23.5 24.3 23.4
t90   29.6 25.1 30.2 27.1 30.5 27.3      | 21.4 23.6 21.9 22.2 23.4 23.1 23.5 23.4
rl99  33.0 37.5 32.9 31.4 28.9 30.2 35.0 30.8 35.3 31.0 39.7 31.6 30.4 | 25.3 24.6
                                        └── 07:09~07:23 同时回落 ──┘
```

两个独立的测量在同一个绝对时刻改变水平，只能是**共同的外部条件**，不可能是各自的
工作负载或策略变化。

### 4. 剂量：2~3 条不抬，4 条才抬

| 并发 | 实例 | τ₂ |
|---|---|---|
| 2 条 | 绝大多数 run | 同族正常 |
| 3 条 | `pairB_foyerhc`（277 min）、`cap3_fixed`（163 min）、`foyer_sf0_r2`、`foyer_hz1_r2`、`cap3_hc_r2` | 23.8 ~ 25.0，**均正常** |
| **4 条** | `bres`/`hz0`/`hz2`/`breshz1`（各约 296 min） | **30.9 ~ 33.3** |
| 4 条 | `_failed_4lane_*`（09-24 被 SIGTERM 的两条） | 31.4 / 32.1 |

这一条正是 `CLAUDE.md` 里 2026-09-21 和 2026-09-24 两次踩到的同一个坑
（"不要同时占满四张卡"，四车道会被别的租户的 reaper 杀掉）。当时的结论是
"会被杀"，**这次发现的是更早的代价：即使没被杀，数据也已经不可比了**。

## 审计结果

`paper/data/concurrency.csv`（123 条 run）：

- **CONTESTED（同时 ≥4 条持续 ≥60 分钟）12 条**
- watch（≥3 条持续 ≥60 分钟）4 条
- clean 107 条

表 I 里受影响的臂正好 4 条，全部是控制器变体：

| run | 峰值 | ≥4 条持续 | τ₂ |
|---|---|---|---|
| `foyer_breshz1` | 4 | 296 分钟 | 33.3 |
| `foyer_hz0` | 4 | 296 分钟 | 33.1 |
| `foyer_bres` | 4 | 296 分钟 | 31.3 |
| `foyer_hz2` | 4 | 282 分钟 | 30.9 |

其余 CONTESTED 的 8 条都不在表 I：rl90 / rl99 / t85 / t90（rl 与 t 的扫描）、
var_foyer / var_cap3（变负载族）、以及 09-24 被 SIGTERM 的两条 `_failed_4lane_*`。

`pois200_cap1` 只有 28.8 分钟处于 ≥4 条，记 watch；它的 τ₂ 20.6 是全场最低，
未受影响。

## 影响估计（重测之前，只作量级参考，不进正文）

τ 若按同族干净水平折算，这四条的忙时会缩短约 22%，墙钟大致：

```
foyer_bres    295.5 → ~247 分    对前沿在该点的插值 91.6  →  Δ 由 −7.8 变到约 −0.6
```

**如果这个量级成立，表 I 的判决会变**——这四条的 Δ 可能从"明显在线下"变成
"贴着线"。所以必须重测，不能靠折算。

## 已采取的动作

1. **重跑这四条**（`lane_foyer_r2_batch1.sh` / `lane_foyer_r2_batch2.sh`），
   新 run 名加 `_r2` 后缀，严格 2 条车道。旧目录原样保留，不覆盖不删除。
2. 重跑用 `wait_and_launch.sh` 排队：等前一条车道的**最后一个 run 写出 summary**
   （不是"显存空"——run_matrix 在一条车道的两条 run 之间会卸载 server，
   那一刻显存是空的但车道没结束），启动前再数一次自己的 server 数。
3. 审计脚本进仓，`paper/data/concurrency.csv` 由它生成。

## 对论文的意义（要如实写）

- **表 I 的这四行在重测前不可信**。重测完用新 run 替换，并在可复现性一节
  说明为什么换、怎么发现的。
- 这是一条**方法论发现**，本身值得写：内存受限 serving 的测量对同机并发
  **高度敏感**，而敏感性只体现在 `τ₂` 这种**逐请求的客户端量**上——引擎侧
  `num_running_reqs`、占用率、驱逐量、重算量**全都看不出异常**（这四条臂在这四列上
  与干净 run 不可区分）。如果只盯着引擎指标，这批数据会被当成好的。
- 与 §III 那条"最大未解问题"的关系：论文原来写"HiCache 族重算恒定而 τ 散开，
  我们不知道为什么"。**其中一部分现在有答案了——那四条臂的 τ 不是被什么都西推动的，
  是被同机争用推动的**。剩下五条（hc/hz1/hz2 之外的）重算恒定而 τ 在 27.0~29.2 之间
  小范围移动，这是重测之后要重新面对的问题，范围比原来小得多。
