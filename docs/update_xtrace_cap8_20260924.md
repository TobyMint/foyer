## 二、弹性判据（这一条是实质变化）

模型自洽的 ε(τ₁)（τ₁ 随 R̄ 的对数斜率）：

| 段 | R̄ | ε(τ₁) | ε(τ₂) | ±10% 扰动区间（τ₁） |
|---|---|---|---|---|
| cap2→cap3 | 1.08→1.16 | −2.40 | +0.41 | [−5.20, +0.41] |
| cap3→cap4 | 1.16→1.29 | −0.28 | +0.48 | [−2.17, +1.61] |
| **cap4→cap5** | 1.29→1.41 | **+1.00** | +0.45 | [−1.25, +3.26] |
| cap5→cap6 | 1.41→1.43 | +0.18 | −1.25 | [−14.07, +14.43] |
| **cap6→cap8** | 1.43→1.50 | **+0.87** | +0.73 | [−3.33, +5.07] |

**原来正文写「这条 trace 的弹性在两个段上都是负的，所以它的测量范围里没有任何东西说明
加并发是自毁的」——现在不成立**：R̄ 超过约 1.29 之后弹性转正，并且在 cap4→cap5 那一段
点估计正好到 1.00。

处置：§VI 与 §criterion 都改成
- **方向迁移了**：第二条 trace 也会到达判据的「贵」分支（主 trace 在 1.53 越过、以 +1.15 起，
  这条在 1.29 之后转正：+1.0/+0.18/+0.87）；
- **位置没有迁移**，而且**两条 trace 都定位不了**：±10% 的 τ₁ 扰动把**每一段**的区间都推过
  零点（后三段还推过 1）——这与 §criterion 早就写下的那条保留（悬崖是「拟合点的描述，
  不是精确定位的阈值」）是同一件事，现在有第二条 trace 佐证；
- 控制器运行在 1.22，**低于两条 trace 的转折点**，所以判据在两条 trace 上都没解释它的失败。

## 四、重复对落地（cap4_r2）：把「这不算输」改成「墙钟上确实更慢」

`realhr_cap4_r2`（390 步）落地后，第二条 trace 有了自己的重复对：

| run | R̄_busy | 兑现率 | 墙钟 | SLO |
|---|---|---|---|---|
| cap4 | 1.286969 | 67.50% | 66.85 min | 99.49% |
| cap4_r2 | 1.289773 | 66.92% | 68.00 min | 99.49% |

散布：兑现率 **0.6 点**、墙钟 **1.7%**、SLO 完全相同。

**这改了一句话的结论。** 正文原来写「foyer 比最快的静态 run 慢 14.3%，但这个差距落在
重复散布之内（引的是主 trace 的 22.4%），所以我们不说它输了」。现在有了这条 trace
自己的重复对：14.3% 是它自己散布（1.7%）的**约八倍**，不能说落在散布内了。

已改为：「在这条 trace 上控制器确实更慢，约是重复散布的八倍，我们在墙钟轴上按**输**报；
SLO 轴上仍不构成输（+0.40pp，在打平带内）」。

顺带修了 `gen_slope.py` 的一个真 bug：加入 `cap4_r2` 后，斜率生成器把重复点当成了扫描点，
造出一个 ΔR̄=0.003 的假段，斜率读到 **−207**。已加「排除 `_r\\d+$` 重复 run」的过滤
（重复只进散布，不进斜率）。`slope.csv` 现在的 xtrace 段是
−31.2 / −36.8 / −28.4 / −93.0 / −67.6、全范围 −40.9，与 §VI 正文逐位相符。
