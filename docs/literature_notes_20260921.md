# 文献核查：「内存当护栏」这个重构站得住吗（2026-09-21）

> 背景：设计 `controller_foyer.py` 时提出的重构是——**内存容量是护栏，不是优化目标**；
> 应该把利用率推向 80–85%，而不是像 v3 那样在实测 52% 时就停止准入。
> 派了一个调研去查这个重构有没有既有工作支撑、有没有已知的反例。
>
> **结论：这个重构的朴素版本被文献否掉了，但核心的"记账错了"这一条仍然成立。**
> 下面按"哪几条改变了我们的计划"来组织，不按论文罗列。

---

## 1. 三条独立证据都指向同一件事：把利用率推高是错的方向

### 1.1 吞吐量根本不是准入控制能改善的东西

**Dai, Deng, Li, Peng — [2504.07347](https://arxiv.org/abs/2504.07347)** 证明
work-conserving 调度已经达到最大吞吐，并指出 Orca 与 Sarathi-Serve 是吞吐最优的，
而 FasterTransformer 与原版 vLLM 不是。

**推论**：如果调度器已经是 work-conserving，**准入控制不可能增加吞吐**——它唯一的
正当理由只有两个：延迟/SLO，或缓存命中率的保全。所以「把吞吐当目标」对一个准入
控制器而言近乎自我否证。

→ **对我们的影响**：目标要重新表述成 **goodput-under-SLO**（或"在端到端约束下最大化
缓存命中"），不能写成"最大化吞吐"。这个改动是措辞层面的，但决定审稿人会不会一句话打死。

### 1.2 高占用是**可证不稳定**的，不只是"慢"

**Ao, Dong, Luo, Simchi-Levi — [2606.15555](https://arxiv.org/abs/2606.15555)**
（2026-06，101 页，math.OC）：

- **定理 2（基线不稳定性）**：无驱逐不动点**不稳定**；最大驱逐极限环是渐近稳定的，
  且其吸引域包含几乎所有内存边界初态。
- 相对无驱逐均衡，**吞吐损失最高达 50%**（解码长度相对输入较长时；最坏比值落在 (1/2, 1)）。
- **定理 3（GCD 稳定条件）**：解码长度之 gcd 为 `g`，`g > 1` 会让无驱逐均衡线性不稳定，
  `g = 1` 则全局渐近稳定——互质解码长度稳定，非互质会产生同步化失稳模式。
- 可借用的表述：**"服务过程本身制造未来的容量压力"**；基线准入在"到达超过最坏周期吞吐"
  时就会堆积积压，**即使到达率仍低于名义上的无驱逐均衡吞吐**。

→ **对我们的影响**：如果我们把红线推到接近池子容量，审稿人会拿这篇说我们在往一个不稳定
不动点上开。**保守臂（target=0.90）受影响小，激进臂（target=0.99）首当其冲。**

⚠ **证据强度**：抓取到的 HTML 里**缺 §6 数值实验与附录 D.3（Vidur + 真机）**，
所以它的 GPU 佐证是"声称但未验证"。且 101 页预印本，未见同行评议记录。**不要当作定论引用。**

### 1.3 低占用与 SLO 崩塌可以并存

**[inference-fleet-sim, 2603.16054](https://arxiv.org/abs/2603.16054)** 声明利用率上限
`ρ_max = 0.85`，然后报告：**一个利用率约 30% 的集群仍然 SLO 不达标**——
24×H100、λ=20 req/s、TTFT SLO 1000ms → **P99 TTFT 1052ms，FAIL**。
原因是我们的负载形态：agent 服务时长跨 10–300 秒，所以
**"一个 300 秒的请求会把一个 KV 槽位锁住五分钟"**。
该文的自我定位很诚实：解析模型"不会偏向安全的一侧——**它会批准已经坏掉的集群**"。

→ **对我们的影响（最重要的一条）**：我们观测到引擎停在池子的 52%，并把它读作
"控制器过于悲观"。**这篇说：在重尾 agent 负载下，低占用 + SLO 失败是兼容的**——
队列长可能因为服务时长重尾，而不（只）因为账本悲观。

**我们自己的日志支持悲观那一侧的解释**（16.1% 的排队周期里账本确实有余量），
但两个效应同时存在。**所以正确的动作是把两者分解开，而不是假定。**

⚠ 这是商业化路由器的关联方预印本，取其"低占用不等于安全"这一点即可，别引它的模型。

## 2. 一条关键的算术，两个方向都确认了：**要 cap3/cap4 的速度就必须超订**

```
我们实测：每活跃会话约占池子 23.6K，新会话到达需 20K
         → 4 个并发 = 117K > 池子 101,432        （我的推算）
调研独立得出：要把实测利用率做到 80–85%，需要 ρ ≈ 1.24–1.29，即刻意超订
```

**同一个结论，两条路各算一遍。**这也解释了 cap3/cap4 为什么跑在 3.56/3.94 却只有
46–50% 命中率——它们靠 SGLang 自己的驱逐腾地方，超订的代价就记在命中率上。

→ **对我们的影响**：`--target-util` 如果不超过 1.0，并发就被锁在 ~3，够不到 cap4。
但这正是 §1.2 警告的不稳定区。**这是个真实的取舍，不是可以绕开的技术细节。**

## 3. 两个文献确实空着、我们可以自己占的缺口

### 3.1 保证 prefill 余量的**内存代价**，没有人量化过

现有工作把 headroom 当作**计算/token 预算**处理（Sarathi-Serve、TAPER、Sangam）；
**内存侧的 headroom 只以两个不成体系的形式存在**：SGLang 的 ×0.95 / ×0.85 粗暴折扣
（[PR#6726](https://github.com/sgl-project/sglang/pull/6726)：<96GiB GPU 上把
`mem_fraction_static` 乘 0.95），以及 vLLM 里未被报告的 `transient_peak_headroom` 项。

**这正好落在我们的场景里。**佐证（同硬件类）：
- vLLM [#57475](https://github.com/vllm-project/vllm/issues/57475)：`gpu_memory_utilization=0.98`
  时 KV 分配通过（150,745 token）但图捕获 OOM，仅剩 120.88 MiB；**0.97 正常启动**。
- SGLang [#35777](https://github.com/sgl-project/sglang/issues/35777)：cookbook 推荐 0.90–0.94，
  报告者试 0.94/0.90/0.85/0.88 **全部失败**，只有 **0.80 + 关闭 prefill graph** 能启动。
- 社区 3090 数据（club-3090 HARDWARE.md）点名"**Cliff 1（约 25K token 的工具 prefill**，
  FFN 中间缓冲）"——**正好压在我们 17K 中位首轮 prompt 上面**；0.95 未加载完就崩，0.944 能起。

### 3.2 实测的 **p99 vs KV 占用曲线**不存在

调研 grep 了 12 个官方页面与多篇论文：**没有任何实测的 p99-对-KV-占用曲线**，
**也没有同行评议工作用 Kingman 或 Pollaczek–Khinchine 论证利用率上限**。
最近的擦边是 Nie et al.、Ao et al.(2606.15555) 和 inference-fleet-sim。

**如果我们把这曲线做出来，是在填一个被明确点名的空白。**
（这也让"激进臂"从'我们的方法'变成'探索这条未知曲线'——叙事上更好。）

### 3.3 有实测 SLO 悬崖的最近邻

**DistServe (OSDI '24) 表 2** —— vLLM 同置部署的 SLO 达成率 vs 负载：
1.0 rps → **97.0%**；1.5 → **65.5%**；2.0 → 52.8%；3.0 → 36.7%；4.0 → 23.6%。
**负载涨 50%，达成率掉 31.5 个百分点。**机制原文："一旦 GPU 变成计算受限，
往批里再加请求不再提升 GPU 效率，而是按比例延长总处理时间。"

## 4. 对当前计划的直接影响

| 项 | 结论 |
|---|---|
| **核心事实仍然成立** | 账本说 92%、引擎实测 52%——**这是实测的，不受上述文献影响** |
| **目标表述要改** | 不写"最大化吞吐"，写 **goodput-under-SLO**（§1.1） |
| **target=0.90 保守臂** | 受影响小，可以跑 |
| **target=0.99 激进臂** | 落在 §1.2 警告的不稳定区，**跑之前先说明这是探索，不是卖点** |
| **不要预设结论** | §1.3：低占用也可能因重尾而 SLO 崩，**必须把"账本悲观"和"服务重尾"分解开再下结论** |
| **可占的缺口** | §3.1 prefill 余量的内存代价；§3.2 p99-vs-占用曲线 |

## 5. 本次调研未覆盖的部分（不要当已查证）

- **Question A 整块没回来**：HiCache / LMCache / Mooncake / Pensieve / Impress / CacheGen
  是否用主机层来**提高准入并发**（而非单纯避免驱逐）。已知碎片：**InferCept**（工具调用处
  暂停、保留/换出以腾出内存给更多请求，1.6–2×）、**Talaria**（可主机恢复的 KV + 准入租约）、

  **Mooncake 的过载拒绝策略、LMCache 的并发主张：未找到。**
- 若干更正（免得我们继续带着错前提）：VAttention 是 **ASPLOS 2025** 不是 OSDI '25；
  PagedAttention SOSP '23 原文**没有** "60–80%" 和 "<4%" 这两个数（那是 vLLM 博客的，
  论文自己的数是 20.4%–38.2%），且它确实报告了 **20–26% 的注意力核延迟开销**。
