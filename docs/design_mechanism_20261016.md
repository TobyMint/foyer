## 一、现在是什么（三个常数，全无推导）

```
每 2 秒：
    projection = 引擎实报占用 + Σ forecast(每个活跃会话)
    forecast(s) = s 自己的每轮增长率 EMA(α=0.4) × 3
    准入:  projection + (会话当前上下文 + forecast(s)) × 1.15  ≤  预算 96,360
```

| 常数 | 现状 | 为什么可疑 |
|---|---|---|
| `3`（horizon） | 预测未来 3 轮 | 会话还剩几轮？不知道。3 是默认值 |
| `1.15`（margin） | 统一安全垫 | 对所有会话、所有情况一视同仁 |
| `2` 秒（interval） | 控制周期 | 没有相对被控对象的时间尺度说话 |

## 二、刚量到的两个事实（**这两个改变了一切**）

### 事实 A：控制器其实**每一轮都在撤销准入**

我之前跟用户说「我们的浪费是因为**准入不可撤销**」—— **那是错的。**
从 `long19_foyer/admissions.jsonl` 逐条数：

```
事件:  queued 19 · admit 19 · release 123 · pause 104 · resume 104

一个会话的真实序列：
  queued → admit(+38.6s) → release(+24.1s) → pause(+0.0s) → resume(+71.0s)
        → release(+81.7s) → pause(+0.0s) → resume(+21.5s)
        → release(+861.1s) → pause(+0.0s) → resume(+1.8s) → …

pause → resume 间隔:  p10 21.5s · p50 401s · p90 2093s · max 6740s
控制器侧:            active_n 中位 1 · 累计 shed 3175 次 · valve 为真 52% 的周期
```

**⇒ 真实机制是「每轮跑完立刻暂停会话，让它重新排队」。**
它的效力来自**撤销**（`active_n` 中位只有 1 ⇒ 池子几乎不超额 ⇒ 引擎很少驱逐），
代价是会话在门外等：**合计 1415 分钟，而整批时间只有 165 分钟**。

**而工具等待的真实分布是：中位 0.1 秒 · p90 11 秒 · 均值 10.4 秒。**
**⇒ 绝大部分暂停远远超过了必要的时长。**

**这一条把论文的故事从「我们加了个准入控制」变成
「我们量出了撤销的代价与收益，并给出判据」。**

### 事实 B：上下文增长是极重尾的，**方差无限**

```
long19 的 583 个「每轮增长」观测：
  p50 = 719     p75 = 2,046    p90 = 4,286
  p95 = 5,729   p99 = 14,287   max = 22,401        均值 1,688

Hill 尾部指数估计：α ≈ 1.53 ~ 1.90（取最高的 30~120 个）
⇒ α < 2  ⇒  【方差不存在】
```

**⇒ 用「均值 ± 标准差」那套东西在这里是没有定义的。** 而现在用的正是 EMA（一种均值）。

### ✗ 被排除：有效带宽 / 随机网络演算 —— **理论上就死**

```

## 四、提出的机制（草案）

**一句话：把三个常数压成【一个显式风险参数 δ + 一个在线分位数估计器 + 一条延迟稳定性判据】。**

### 4.1 准入：从「点估计 + 安全垫」到「分位数 + 覆盖保证」

```
现在    projection + (ctx + EMA×3) × 1.15  ≤  budget

改成    P( projection + Σ_s 未来的增长  >  budget )  ≤  δ
        用在线分位数估计这个上界，δ 是唯一的旋钮
        ⇒ 长期覆盖由 conformal 的定理保证（不是调出来的）
```

> ⚠ **2026-10-17 实测修正**：文献说重尾下"和的分位数由最大项主导，
> 所以不能 n × 分位数"。我拿我们自己的数据验了（2 万次重采样）：
> **n=2 只高估 7%，n=10 才 1.73×。而我们只有 1~2 个活跃会话。**
> ⇒ **这个方向理论对，但我们这里的收益只有 7%，不是主贡献。**
> 真贡献在 §9（撤销判据），不在准入的分位数化。

### 4.2 撤销：从「阀门触发」到「有判据的取舍」

> ⚠ **本节已被 §9 取代。** 这里写的"判据"只有形状；**真正的推导在 §9**。
> 保留原文是为了记录当时还不知道汇率怎么定。

这是**新的主贡献**（事实 A 支撑）：

```
现在    valve（TTFT 太差）为真 ⇒ 一律 shed        ← 反应式、无成本比较
        结果：pause 中位 401 秒，而工具等待中位 0.1 秒

改成    对每个 parked 会话算一笔账：
            持有成本 = 它的上下文 C 占着池子的时间（token·秒）
            让位成本 = 它回来时重算的代价 P(C)（秒）
        只在【持有成本 > 让位成本】时撤销
```

**⚠ 这里的难点（要老实说）**：两项量纲不同（token·秒 vs 秒），而且**两边都是重尾随机量**。
所以判据不能是简单的数值比较，得先把它们放到同一个量纲上 ——
而"一 token·秒的池子值多少秒"这个换算率，本身要从系统里标定。

**这一条是这个设计里最需要想清楚的地方，也是最能撑起"工作量"的地方。**

### 4.3 周期：从「2 秒」到「推导出来的」

用 NCS 的采样定理：控制周期 < min(被控对象时间常数, 观测延迟) / 若干倍。

# 九、撤销判据的推导（2026-10-17）

## 9.1 汇率是 1:1，不是近似

```
前提：池子是瓶颈（有人在等位置）
⇒ 你占着 c 个 token 的 W 秒  =  让某个本来能跑的会话晚了 W 秒
⇒ 而引擎的吞吐是固定的      ⇒  晚 W 秒 = 少做 W 秒的活

保住它：付出 W 秒的别人进度
扔掉它：付出 P(c) 秒的重算
⇒ 保住 ⟺ W < P(c)
```

**1:1 的来源是「时间就是时间」：引擎的吞吐不会因为换了个人跑而变。**
唯一的条件是**必须真的有人在等**（否则占着池子是免费的）。

## 9.2 但 W 不能用均值 —— 要用剩余寿命

```
m(t) = E[ 还要等多久 | 已经等了 t 秒 ]        ← 剩余寿命 (mean residual life)

指数分布（无记忆）： m(t) ≡ 均值       ⇒ 等多久都一样
重尾分布：           m(t) 随 t 递增    ⇒ 等得越久，越该让位
```

**⇒ 一个会话「已经等了 3 秒」这件事本身就在告诉你它落在重尾里。均值看不见这个信息。**

判据：**`m(t) > P(C)` ⇒ 让位**（且 `waiting_n > 0`）。

## 9.3 从 583 个实测观测直接算（不假设任何分布）

```
已经等了 t     m(t)        判据 m(t) > 50s
   0 秒        17.6        保住
   1 秒        38.8        保住
 ★ 2.6 秒      50.0        ← 交叉
   5 秒        73.3        让位
  30 秒       112.9        让位
 100 秒       124.9        让位

⇒ t* = 2.6 秒
```

**⇒ 判据：会话等超过 3 秒还没回来 ⇒ 让位；否则保住。**
**这个 3 秒是从数据里解出来的，不是调的。**

## 9.4 三条策略在同一批 583 次等待上的动作

```
现在（跑完一轮立刻暂停）      583 次 = 100%
用均值  W > P(C)               45 次 =  7.7%
用剩余寿命 m(t) > P(C)        179 次 = 30.7%    ← 理论上正确的那个
```

而实测控制器在 **123 次轮次完成里暂停了 104 次（85%）**
⇒ **判据说 31%，实际做了 85%。多让位了一倍多。**

## 9.5 诚实清单

```
⚠ 工具等待被截到 300 秒 ⇒ t 接近 300 时样本耗尽（t=200 只剩 19 个），尾部估计不可靠
   ⇒ 这个 300 秒截断本身要重新审视（用户 2026-10-16 也提过）
⚠ 只推了「该不该让位」，没推「让给谁」—— 多个等待者时的选择规则还没有
⚠ 全部是离线计算，未上卡验证
```

## 9.6 与文献的关系

- **caching 里的 value-density / GreedyDual-Size** 是最接近的框架（value=重算代价，cost=占用×时间），
  但那些工作假设**已知的命中概率**；我们这里命中概率要从**剩余寿命**估。
- **ski-rental** 的形状对（租到最后一次租金超过买价），但标准 ski-rental 是
  **静态的**（买价固定、不知道还剩几天）；我们是**动态的**（已经等了多久是信息）。
- **⇒ `m(t)` 这个形式是我没在文献里找到对应物的部分**，需要再查证（见下）。

  └ decode  批               4571         4731    一样

prefill 命中缓存的 token    18.74M        3.84M
  命中率                     74.3%        14.5%

decode 吞吐（并发=1）      42 tok/s    41 tok/s    一样
池占用     （并发=1）       62.6%       61.9%      一样
```

**⇒ 两条臂的引擎是同一台机器、同样的速度、同样的单流吞吐、同样的池占用。
唯一的差别是【prefill 要算多少 token】—— 差 3.47 倍。**

## 11.2 那 71 分钟是怎么来的

```
无控制臂比我们多花 71.6 分钟
  = 引擎忙多 102.2 分钟  −  引擎空闲少 30.6 分钟

多忙的 102.2 分钟里，几乎全是 prefill：
  多算了 16.06M token ÷ 102.2 分 = 2624 tok/s
  ↳ 与两条臂各自的 prefill 速率（2850 / 2580 tok/s）吻合
```

**⇒ 一句话：无控制臂用【31 分钟的空闲】换了【102 分钟的重算】。**
**⇒ 它不是在"更充分地利用 GPU"，它是在拿 GPU 反复算同一段前缀。**

## 11.3 为什么并发度卡在 1 —— 这是结构性的，控制器改不了

```
池子 101,432 token
一个长会话的上下文      约 60,000 token  ⇒  占用 62.6%
⇒ 两个会话就要 125%  ⇒  【池子物理上只装得下 1 个】
```

**⇒ 这就是 `running=1` 占 78~85% 的原因，两条臂都一样。**
**⇒ 所以"提高并发度"这条路是死的。唯一的杠杆是【让那 1 个位置坐对人】。**

## 11.4 顺带记一条：metrics 里 `num_running_reqs` 不能用

`metrics.csv` 报 `num_running_reqs` 中位 1、p90 2；而服务器日志同一时刻写
`#running-req: 5`。**以服务器日志为准。**（两者差在采样口径，不是差在事实。）

## 11.5 于是"填满空闲"值多少 —— 用 §9 的判据算

空闲 56.7 分钟，分成 57 段 >5 秒（17 段 >60 秒）。

**要填满它，必须把一个正在等工具的会话换出去、换一个能跑的进来。**
代价：被换出去的会话丢掉前缀，回来时重算 ≈ 40K token ÷ 2850 tok/s ≈ **14 秒**。

```
换 57 次   ⇒ 多付 57 × 14 秒 = 13.3 分钟 prefill
          ⇒ 换来 56.7 分钟空闲
净收益      = 56.7 − 13.3 = 43.4 分钟
makespan   = 165.2 − 43.4 = 121.8 分钟
加速       = 236.1 / 121.8 = 1.94x
```

**⇒ 而"什么时候值得换"就是 §9 的判据：`m(t) > P(C)` ⇒ t* = 2.6 秒。**
**⇒ §9 推出来的 2.6 秒，和这里实测的空闲段（p50 = 10 秒，>2.6 秒的占多数）正好对得上。**
**⇒ 两节在这一点上闭合了：判据不是装饰，它就是那 43 分钟的来源。**

## 11.6 两个上限（long19 上）

```
① 只填空闲、不增加任何重算（不可能达到，是理想）
   165.2 − 56.7 = 108.5 分  ⇒  236.1/108.5 = 2.18x

② 绝对上限：零空闲 + 零重算
   必要量 2.21M ⇒ prefill 1.98M/2850 = 11.6 分
   decode 74.2 分（实测，单流）
   ⇒ 85.8 分  ⇒  236.1/85.8 = 2.75x
```

**⇒ long19 这个负载上，天花板是 2.75x。**
**⇒ 想要 3~4x，只能靠更大的负载 —— 会话越多，无控制臂崩得越狠。**
**⇒ 这就是 `replay_big27`（27 会话）正在跑的原因。**

## 11.7 诚实清单

```
✅ 引擎侧数字来自服务器日志，与 runner 侧独立测得的两条 idle 率
   （33.6% / 10.9% vs 32.2% / 9.2%）互相印证
⚠ §11.5 的 14 秒/次 是「40K token ÷ 实测 prefill 速率」的估计，不是直接测量
⚠ 57 段空闲里有 40 段 <60 秒，换人的开销可能与收益同量级
   ⇒ 真实收益应当低于 1.94x，需要上卡验证（`--revoke-after 2.6` 已在跑）
⚠ 天花板 2.75x 是 long19 的；big27 上应该更高，但尚未测出
```

# 十二、判据的第一次实测：测的是一个 bug（2026-10-17 晚）

## 12.1 结果

同轨迹 A/B（`replay_long19.csv`，其余参数逐字相同，只加 `revoke=2.6;rnw=1`）：

```
                    旧控制器    判据版      差
makespan            165.2 分   162.6 分    −1.6%    ← 无法与噪声区分（无重复实验）
命中率               74.3%      67.5%     −6.8pp
引擎有效工作量        6.72M      8.80M     +31%
冷启动步数            112        129       +15%
Σshed（控制器日志）    3175       7992      +152%
```

**⇒ 判据版让引擎多算了 31% 的 token，整批时间只快了 1.6%。**
**⇒ 更关键：Σshed 不是减少，是增加了 2.5 倍 —— 判据在做相反的事。**

## 12.2 根因：`last_end` 的初值是 0.0

```python
s = sess.setdefault(sid, dict(..., last_end=0.0, ...))   # 第 256 行
...
shed = [sid for sid in shed
        if now - sess[sid].get("last_end", 0.0) > args.revoke_after]   # 第 371 行
```

**一个刚被准入、还没跑完任何一轮的会话 `last_end == 0.0`，于是
`now − 0.0` = 1.79×10⁹ 秒 > 2.6 秒 ⇒ 判据必然为真。**

**⇒ 判据把「刚进来、正在跑第一轮」的会话判成「停摆最久」，第一个踢它。**
**⇒ 它保护的从来不是「跑完一轮正在等工具」的会话，而是相反。**

## 12.3 修法（已改，未部署）

```python
shed = [sid for sid in shed
        if sess[sid].get("last_end", 0.0) > 0.0          # ← 没跑完过 ⇒ 不参与判据
        and now - sess[sid]["last_end"] > args.revoke_after]
```

**理由：`m(t)` 的定义域是「已经等了 t」。没跑完过就没有 t。**
**（用 `arrived_ts` 兜底是错的：一轮中位 14.7 秒，准入 2.6 秒后判它停摆会把所有人都踢掉。）**

## 12.4 ⚠ 部署纪律

**不能在 run 进行中部署。** 控制器是被 `while [ ! -f summary.json ]; do … done`
守护的，**一崩就会重启并读到新代码**，污染正在跑的 run。
⇒ **等 `big27_foyer` 结束后再 `bash scripts/deploy.sh`。**

## 12.5 诚实清单

```
❌ §9 的判据【至今没有任何有效证据】支持它有用。唯一一次实测测的是 bug。
❌ big27_foyer 也是在 bug 下跑的 ⇒ 它是「我们的方法 vs 无控制」的合法数据点，
   但【不是】判据的测试。
⬜ 修好后必须在 long19 上重跑一次 A/B（3 小时），才谈得上判据成不成立。
⚠ 1.6% 的差异没有重复实验支撑，不能当结论。
```

# 十三、空转的根因：SLO 阀门测错了东西（2026-10-17 夜）

§11 量出我们的臂有 **56.7 分钟（34%）引擎空转**，而门外有 15~19 个会话在等。
这一节找到了它是怎么来的。

## 13.1 先排除两个猜错的解释

```
✗ "池子装不下"   —— 不成立。引擎空闲时 token_usage 中位 = 0.000
                    （可驱逐的 KV 引擎本来就没算进去，见 metrics 分档）
✗ "投影吃满了预算" —— 不成立。空闲周期的 projection 中位 2,670 / budget 96,360
```

## 13.2 真正的分解（控制器视角的 33.3 分钟空转）

```
门外有人 / 阀门关 / 门里有人    15.6 分   ← 【可修】
门外没人 / 阀门开 / 门里有人    10.0 分      结构性（所有会话都在等工具）
门外没人 / 阀门开 / 门里空       3.6 分      结构性
门外有人 / 阀门关 / 门里空       3.6 分   ← 【可修】
门外有人 / 阀门开 / 门里有人     0.3 分
门外有人 / 阀门开 / 门里空       0.1 分
─────────────────────────────────────
⇒ 「门外有人、阀门却关着」= 19.2 分 = 58% 的空转，是白等
```

```
引擎空闲 + 门外有人 的 589 个周期：
   阀门关着  575 个（98%）      期间总共只准入了 23 个会话
   这些周期的 ttft_p50_ms 中位  23,387 ms   （阈值 10,000 ms）
```

## 13.3 根因：TTFT 是【服务时间】的函数，不是【排队延迟】的函数

```
阀门 = (最近 20 个已完成请求的 TTFT 中位 > 10 秒)
      且样本保鲜期 --ttft-freshness-s = 600 秒

而一个 60K 的 prefill 本来就要 86 秒（实测 p90）——
这跟有几个并发【无关】。于是：

   大 prefill 在跑 → TTFT 差 → 阀门关 → 不放新人
   → 大 prefill 跑完，会话去等工具 → 引擎空闲
   → 但阀门还关着（样本还新鲜，最多再锁 10 分钟）
   → 空转
```

**⇒ 在长上下文负载下，这个阀门是【恒真】的 —— 它衡量的不是过载，是任务本身有多重。**

## 13.4 修法

```
--valve-needs-pressure      池子占用 < --valve-pressure-usage（默认 0.5）时，阀门强制打开
```

**理由：池子空着的时候，高 TTFT 是这个请求自己的固有时间，不是过载的证据。**
**「过载」的可观测定义是【有请求在争抢 KV】，而池子空着恰恰是它的反面。**

**⚠ 同时排除了另一个猜想：** 我原本打算把投影改成「只算热的会话」（`--base-mode hot`），
但 §13.1 证明 `token_usage` 在引擎空闲时已经是 0 —— **可驱逐的 KV 引擎本来就没算**，
所以那一改是多余的。已实现但**不使用**。

## 13.5 诚实清单

```
✅ 分解是实测的（long19_foyer 的 4999 个控制周期逐条分类）
⚠ 只解释了 58% 的空转；剩下 41%（13.6 分钟）是结构性的
   —— 门里那个在等工具，而门外确实没人排队
❌ 还没上卡验证。已部署，`long19_foyer_vnp` 已排队等卡
⚠ 阀门原本是防止 TTFT 爆炸的安全阀；加了压力门之后它在池子空时会失效。
   理论上池子空 ⇒ 不会有排队 ⇒ 不需要它。但这要实测确认。
```

# 十四、阀门修好了，然后证明【空转不是浪费】（2026-10-18）

## 14.1 阀门完全按预期工作

```
              控制周期  空转时间   其中「门外有人但阀门关」  阀门关比例  总准入
旧             4999    33.3 分         19.6 分              98%      122
revoke(修前)    5052    25.7 分         10.0 分              97%       97
vnp(阀门修)     5134    11.4 分          0.8 分               0%      200
```

**⇒ 空转 33.3 → 11.4 分（−21.9 分），「门外有人但阀门关」19.6 → 0.8 分（清零）。**
**⇒ §13 的根因诊断是对的，修法也是对的。**

## 14.2 但整批时间变慢了

```
              步    makespan   命中率   有效算力   浪费   冷启动
旧            542   165.2 分   74.3%    6.72M    3.04    112
revoke(修前)   562   162.6 分   67.5%    8.80M    3.87    129
vnp           563   169.7 分   58.6%   11.20M    4.92    175
```

**账：省下 21.9 分钟空转，多算 4.48M token ⇒ 4.48M ÷ 2850 tok/s = 26.2 分钟。**
**21.9 − 26.2 = −4.3 分钟 ⇒ 与实测的 +4.5 分钟吻合。**

**⇒ 交换比 0.84 < 1。换人不划算。**

## 14.3 为什么 —— 空转是【买前缀驻留】的价钱

```
准入次数     122 → 200（+78）
每次交换     多算 4.48M/78 = 57K token ≈ 20 秒 prefill
             换来 21.9/78 = 0.28 分 = 17 秒空闲
⇒ 付 20 秒，换 17 秒。亏。
```

**而真正的代价不在"多算一次"，在命中率：74.3% → 58.6%。**
**放进来的人多了 ⇒ 池子压力大 ⇒ 前缀留不住 ⇒ 每个会话回来都要重算。**

**⇒ 那 21.9 分钟的空闲，不是"浪费掉的 GPU 时间"，是【保住前缀不被驱逐所付的租金】。**

**⇒ 三个点连成一条线：空转越少 → 命中率越低 → 总时间越长。**

## 14.4 这对 §9 的判据意味着什么

§9.1 的汇率推导说「占着 c 个 token 的 W 秒 = 让别人晚 W 秒 = 少做 W 秒的活」。
**这条推导有一个隐含前提：那 W 秒【本来会被用来做有用的活】。**

**⇒ 但在池子只装得下 1 个会话的负载下，那 W 秒的替代用途是【引擎空转】，
不是【别人在做活】。汇率不是 1:1，是 1:0 —— 空转的秒数本来就在浪费。**

**⇒ 所以正确的比较不是「W 秒 vs P(C)」，而是「W 秒的空转 vs P(C) + 命中率损失」。**
**而实测后者更大。**

## 14.5 诚实清单

```
✅ 三个点都是实测（同轨迹、同参数、只改一处）
✅ 机制诊断正确：阀门确实是空转的直接原因，修完空转确实清零
❌ 但修完之后更慢 ⇒ 【空转不是浪费】这个结论反过来推翻了 §13 的动机
⚠ 只测了一个负载（long19，池子只装得下 1 个会话）。
   会话更短 / 上下文更小的负载上，结论可能相反 —— 那时"换人"不必付 60K 的重算。
⬜ 需要回答：有没有一种【既填空转又不丢命中率】的准入规则？
   线索：池子 101K，驻留会话 62K，剩 39K ⇒ 只有 ctx ≤ 39K 的会话是【免费】的。
   而现在的投影只检查「准入那一刻装得下」，不检查「它跑起来之后还装得下」
   —— forecast 用的是 ema×3 ≈ 5K，而实测一轮能涨 22K（p99）。
```

# 十六、证伪测试：1.43x 里有一大半是【缓存配置】（2026-10-18）

§15.3 发现 host 缓存三条臂上都是 100% 满的（0.2M token，工作集 1.14M）。
于是把 host 层从 `--hicache-ratio 2` 调到 `8`，重跑无控制臂。

## 16.1 结果

```
                makespan   命中率   有效算力   浪费
default  hc2    236.1 分   14.5%   22.79M   10.02x
default  hc8    178.8 分   64.7%    9.58M    4.21x    ← 好了 24%
foyer    hc2    165.2 分   74.3%    6.72M    3.04x
```

**⇒ 只把 host 缓存扩大 4 倍，无控制臂的命中率从 14.5% 涨到 64.7%，
浪费从 10.02x 降到 4.21x，整批时间从 236.1 降到 178.8 分。**

**⇒ 我们相对无控制臂的优势，从 1.43x 掉到 178.8 / 165.2 = 1.08x。**

## 16.2 这说明了什么

**⇒ 我们的控制器做的事，和「把主机缓存扩大 4 倍」是【替代品】，不是互补品。**

机制上说得通：我们的控制器用【时间复用】（一次只让一个会话用池子）
替代【空间复用】（让所有会话的前缀都留在缓存里）。
而加大 host 缓存正是扩展空间。**两者都在解决同一个约束：缓存装不下工作集。**

## 16.3 代价换算（这部分是真的贡献，但比 3~4x 小得多）

```
每 token KV = 28层 x 4 KV头 x 128 head_dim x 2(K,V) x 2字节 = 57,344 字节 = 56 KiB

device 池 101,432 token          =  5.8 GB 显存
hc2  host 202,865 token          = 11.6 GB 主机内存
hc8  host 811,457 token          = 46.5 GB 主机内存
```

**⇒ 无控制臂要 46.5 GB 主机内存才到 178.8 分；我们用 11.6 GB 就到 165.2 分。**
**⇒ 等价于省下 35 GB 主机内存 —— 这是可量化、可复现的。**

## 16.4 诚实清单

```
❌ 1.43x 不能作为主结果呈现 —— 它没有和「加大缓存」这个 baseline 比过
⚠ 2x2 还差一格：foyer@hc8 正在跑。它决定曲线是【替代】还是【互补】：
     若 foyer@hc8 ≈ 165（不改善） ⇒ 纯替代 ⇒ 我们只是省内存
     若 foyer@hc8 ≈ 130（也改善） ⇒ 两个杠杆正交，我们的方法在任意缓存下都加一份
⬜ 还需要 hc4 之类的中间点才能画出曲线（每个点 3 小时）
⚠ host 缓存 46.5 GB 在真实服务节点上不是免费的；这是"省内存"论证的基础，
   但也要老实说 251 GB 的机器给得起
```

## 16.5 对整篇论文的影响

**⇒ 「我们的方法快 1.43x」这个说法不成立。**
**成立的说法只有：「我们的方法把浪费从 10.02x 降到 3.04x，等价于把主机 KV 缓存
扩大 4 倍（11.6 GB → 46.5 GB），而不需要那块内存」。**

**⇒ 3~4x 在这个负载上是不可能的**：§11.6 算出的绝对上限（零空闲 + 零重算）是 2.75x，
而 16.1 表明连 1.43x 里都有一大半不是我们的功劳。

# 十七、2x2 完成：我们的方法是【缓存受限时的替代品】（2026-10-18）

## 17.1 全表

```
                 步    makespan   命中率   有效算力    浪费
default  hc2    562    236.1 分   14.5%   22.79M   10.02x
default  hc8    563    178.8 分   64.7%    9.58M    4.21x
foyer    hc2    542    165.2 分   74.3%    6.72M    3.04x
foyer    hc8    562    201.2 分   90.0%    2.88M    1.27x   ← 命中率最高、浪费最低，却最慢之一

优势：  hc2 上我们快 1.43x        hc8 上我们【慢】0.89x
```

**⇒ foyer@hc8 的浪费只有 1.27x —— 几乎零重算 —— 但整批时间比 foyer@hc2 还长 22%。**

## 17.2 为什么

```
                     步数   空闲     忙      每步忙时
foyer hc2            542   33.3 分  131.9 分   14.6 s
foyer hc8            562   29.5 分  171.7 分   18.3 s
```

**⇒ 空闲几乎没变（33.3 → 29.5），但每步忙时涨了 25%（14.6 → 18.3 秒）。**

两个原因叠加：

```
① 控制器【串行化】太多。它的收益来自"减少重算"，成本是"增加串行等待"。
   hc2 下重算是主要成本（3.04x），所以串行化划算；
   hc8 下重算几乎消失（1.27x），串行化就只剩成本。
   ⇒ 时间复用（我们的做法）和空间复用（加大 host 缓存）是【替代品】。

② 命中率不是充分的指标 —— 【命中的层次】也重要。
   hc8 把命中率从 74.3% 抬到 90.0%，但多出来的命中来自 host 层，
   而 host 命中要把 KV 从主机内存搬进显存。device 命中是免费的，host 命中不是。
   ⇒ 每步忙时 14.6 → 18.3 秒，与这一点一致（尚未直接测量，见诚实清单）。
```

## 17.3 所以论文现在能说什么、不能说什么

```
❌ 不能："我们的方法快 1.43x"  —— hc8 上我们比无控制臂慢 11%
❌ 不能：拿 1.43x 当主结果 —— 它没有和「加大缓存」这个 baseline 比过
✅ 能："在 device 池 5.8 GB + host 11.6 GB（工作集 1.14M token）的配置下，
       我们的方法把重复 prefill 从 10.02x 降到 3.04x，
       等价于把 host KV 缓存扩大 4 倍（11.6 → 46.5 GB），而不需要那块内存"
⚠ 但这个说法有一个立刻会被问到的反驳：那就在 hc8 上跑啊 —— 而 hc8 上我们更慢。
```

## 17.4 唯一可能的救法：让控制器知道 host 层的存在

**⇒ 控制器现在只把 device 池当约束（`base = resident` = device 占用），
完全不知道 host 层有 0.81M token 的余量可以兜住被驱逐的前缀。**

**⇒ 如果准入决策能区分「驱逐 = 真丢」和「驱逐 = 掉到 host 层，还能捞回来」，
那 hc8 下的过度串行化就可以避免。**

**⇒ 但实测 hc2 和 hc8 的 host 层【都是 100% 满】，所以"host 满不满"这个信号区分不了。
   需要的是"这个会话的前缀在不在 host 层里" —— 那是 per-prefix 的信息，
   `metrics` 里没有。**

## 17.5 诚实清单

```
✅ 四个点都是同轨迹、同机器、只改配置
⚠ "host 命中比 device 命中慢"是推断，没有直接测量。要去 server log 里找
   hicache 的传输记录才能定论
⚠ 每步忙时是 makespan − 控制器口径空闲 的粗算，不是精确的引擎忙时
❌ 控制器对 host 层一无所知 —— 这是 hc8 上变慢的最可能原因，但没验证
```

# 十八、hc8 变慢的机制：host 命中不是免费的（2026-10-18）

## 18.1 引擎侧四个点（服务器日志，可靠口径）

```
                 跨度     引擎空闲   引擎忙    prefill新token  running=1的生成吞吐
foyer  hc2      168.9分   56.7分    112.2分     6.49M          42 tok/s
foyer  hc8      206.0分   52.5分    153.5分     2.65M          23 tok/s
default hc2     240.5分   26.1分    214.4分    22.55M          41 tok/s
default hc8     183.4分   27.1分    156.3分     9.34M          34 tok/s
```

## 18.2 拆开算：慢在 prefill，不在 decode

```
decode 批数：hc2 4571 → hc8 4651（几乎不变）⇒ decode 时间没变，约 76 分
⇒ prefill 时间 = 引擎忙 − 76 分：
     foyer hc2   112.2 − 76 =  36 分  ，搬 6.49M 新 token ⇒ 3,005 tok/s
     foyer hc8   153.5 − 76 =  77.5 分，搬 2.65M 新 token ⇒   570 tok/s   ← 慢 5.3 倍
```

**⇒ prefill 速率掉了 5.3 倍，而它要算的 token 少了 59%。**

## 18.3 原因：host 命中要把 KV 从主机内存搬进显存

```
foyer hc8 的 prefill 批里 cached-token 累计 23.79M
   ⇒ 23.79M × 56 KiB = 1.33 TB 要从 host 搬进 device
   ⇒ 77.5 分钟搬 1.33 TB = 286 MB/s
```

**⇒ 286 MB/s 远低于 PCIe 的 25 GB/s —— 说明 hicache 的搬运是逐层、同步做的，很慢。**

**⇒ 所以「命中」不是二值的：device 命中是免费的，host 命中要付 286 MB/s 的搬运费。**

**⇒ 而 `server_cached_prompt_tokens` 把两者算成一个数 —— 这就是为什么「命中率」
在 hc8 下涨到 90% 却更慢。**

```
命中率与真实成本（foyer）：
   hc2  74.3% 命中，其中大部分是 device 命中（免费）  ⇒ 每步忙时 14.6 s
   hc8  90.0% 命中，但多出来的全是 host 命中（要搬）  ⇒ 每步忙时 18.3 s
```

## 18.4 这反而指出一条出路

**⇒ 我们的控制器在 hc8 下"太成功"了：它把命中率推到 90%，而其中大部分是慢的 host 命中。**

**⇒ 它现在只看【命中 / 未命中】的二分（通过 device 占用），看不见【命中在哪一层】。**

**⇒ 正确的准入决策应该按【命中的层次】定价：**
```
   未命中          ⇒ 代价 = 重算 P(C)          （最贵）
   host 命中       ⇒ 代价 = 搬运 C / 286 MB/s  （中等）
   device 命中     ⇒ 代价 = 0                  （免费）
```
**⇒ 而 286 MB/s 这个数是实测的，不是猜的。**

**⇒ 这意味着：在 hc2 下"保守串行化"是对的（因为驱逐 = 真丢 = 重算），
   在 hc8 下"保守串行化"是错的（因为驱逐 = 掉到 host，还能捞回来，代价只是搬运）。**

**⇒ 而控制器现在无法区分这两种情况 —— 它不知道被驱逐的前缀去了哪里。**

## 18.5 诚实清单

```
✅ 286 MB/s 是从服务器日志的 cached-token 总量与 prefill 时间算出来的
⚠ "逐层同步搬运"是推断，没有读 SGLang 的 hicache 实现
⚠ decode 时间「约 76 分」是用 decode 批数 × 1 秒估的（日志时间戳只有秒级精度）
❌ 没有直接测量 device 命中 vs host 命中的比例 —— `metrics` 里没有这个字段
   ⇒ 要坐实 18.4，得先拿到这个比例。可能要去读 SGLang 的源码或加日志
```

# 二十一、更正 §18.2 的一个口径错误（2026-10-19）

   long19 上不会；big27 上会，而且尾巴很重。
③ ③ 那个尾巴正好是准入控制器【该修而没修】的东西 —— 现在的 shed 是按到达顺序，
   不是按"谁等得最久"。而 §9 的 m(t) 判据恰恰是一个公平性机制。
```

## 22.4 诚实清单

```
⚠ big27 的 foyer 臂是在 §12 那个 revoke bug 下跑的 —— 逐会话表里的 3.05x 尾巴
   有一部分可能是那个 bug 造成的，不是机制本身的
⚠ "完成前 K 轮"不是 SLO 意义上的延迟；没有 deadline，所以"饿死"没有绝对判据
❌ 没有测过会话间的公平性指标（Jain's index 之类）—— 只有逐会话比值
```

## 22.5 ⚠ 必须排除被打死的会话 —— 否则会系统性高估无控制臂

§22.2 里 big27 那个 3.05x 的尾巴是假的：那个会话（`6f0b3fbb`）在**无控制臂里
第 8 轮就被服务器打死了**（`connection closed before message completed`，
见 §16.1 那 4 个 FAILED）。它"完成得早"，是因为它死了。

**⇒ 任何按「会话完成时间」比较的分析，都必须先排除在任一条臂上 FAILED 的会话。
不排除的话，无控制臂会因为它打死会话而显得更快。**

修正后：

```
               可比会话   我们更慢   比 p10 / p50 / p90 / max
long19  hc2      18       1/18     0.25 / 0.77 / 0.94 / 1.01
big27   hc2      23       4/23     0.16 / 0.51 / 1.21 / 1.25
```

**⇒ long19：18 个会话 17 个更快，最差那个只慢 1%。**
**⇒ big27：23 个会话 19 个更快，中位快 1.96x，最差慢 25%（不是 3 倍）。**

**⇒ 而且这本身是一条对无控制臂的指控：它会把会话打死，而打死会让它的
统计数字变好看。这一点在写论文时要主动说明，不能装作没看见。**

## 22.6 顺带：热步的 TTFT，和一个必须避开的陷阱

```
热步（只算了新增 token 的步）的首字延迟：
                 n      中位       p90
foyer   hc2     407    1.34 s    23.1 s
foyer   hc8     526    2.40 s    72.2 s
default hc8     368   70.07 s   224.7 s      ← 29 倍
default hc2      64    0.73 s   411.5 s      ← n 太小，不能比
```

**⇒ 在 hc8 下，我们一旦放行一个请求，它 2.4 秒出首字；无控制臂要 70 秒
（因为它把 19 个请求全放进来，引擎队列里排 15 个）。**

**⚠ 但这个指标有陷阱，不能拿去当卖点：TTFT 只统计【已经发出去的请求】。
无控制臂的 TTFT 差是因为它把人放进队列里等；我们的 TTFT 好，
一部分是因为【我们把人在门外挡着，他们根本不产生 TTFT 样本】。**

**⇒ 同一个事实，换个位置就变成优点。正确的口径是从【到达】算的端到端，
那已经在 §22.5 里做了（long19：17/18 更快，最差 +1%）。**

**⇒ 结论：TTFT 这一列写进论文时必须配这句话，否则就是在挑对自己有利的口径。**

# 二十四、并行跑的第二颗雷：permit 文件按 lane 命名，而 lane 永远是 atonce（2026-10-19 04:40）

## 24.1 症状

02:39 起的两条 run，跑了一个多小时：
```
long19_foyer_nohc   47 步 / 114 分 = 0.41 步/分
long19_foyer_rv2    99 步 / 114 分 = 0.87 步/分
```
而历史 `long19_foyer`（hc2）是 **3.28 步/分**。nohc 慢了 8 倍 —— 慢得不合理。

## 24.2 根因

```python
# run_matrix.py（修复前，三处）
permitfile = f"{BASE}/permit_{args.lane}.json"
```

**而 `drive_one.sh` 永远传 `--lane atonce`。**
**⇒ 两条并行 run 的控制器在往【同一个文件】写准入名单，互相覆盖。**

```
两条 runner 的命令行里都是：
   --permit-file /data/xbw/turnstile/permit_atonce.json
```

**⇒ 准入完全混在一起，两条数据都无效。**

## 24.3 修法

```python
permitfile = f"{BASE}/permit_{name}.json"    # name = 这一条 run 的名字
```

**理由：permit 是【这一条 run 自己的状态】—— 它自己的 runner 和 controller 共享，
从来不跨 run 共用。按 lane 命名从一开始就是错的，只是【从来没并行跑过】所以没暴露。**

`--lane` 的其它用途（`cap_{lane}`、`lane_{lane}_DONE` 标记、metadata）都只影响文件名和
元数据，不影响行为，所以 lane 保持 atonce 不动。

## 24.4 这一条比断线更值得记

**断线是环境事故，这个是自己埋的雷。**
项目里有一条规矩叫「开跑前必须挪走同名旧目录，否则追加式日志会静默混合两次 run」——
**同一个道理：任何【被两条 run 共享的文件】都会静默混合它们。**
permit / cap / 任何 `f"{BASE}/xxx_{lane}"` 都是这类东西。

**⇒ 并行之前，先把所有 `{BASE}/` 下的共享路径过一遍。**
**（`grep -n '{BASE}/' run_matrix.py` 就够。）**

废数据已挪到 `results/night/_void_permitcollision_*`，04:45 用修好的代码重起两条。

# 二十五、第三颗雷，而且这颗不是我的：GPU 热降频到 1/10 时钟（2026-10-19 06:40）

## 25.1 症状

04:47 重起的（permit 已修好的）两条 run，106 分钟只跑了 62 / 139 步：

```
                前15分  15-30  30-45  45-60  60-75  75-90  90-105  105-120
历史 foyer hc2    171     49     18     31     23     52     47      59
nohc (在跑)        27      6      5      7      5      5      7       1
rv2  (在跑)        51     28     20      7     10     13      9       6
```

**⇒ 慢 3~6 倍。但开局第一条 decode 批完全一样（#token 13072，46.7/49.1 tok/s
vs 历史的 50.8）—— 说明引擎本身没问题，是【后来】变慢的。**

## 25.2 根因：GPU 被热降频

```
index  clocks.sm  max.sm  temp  fan   power   util
  0      210 MHz   2100    77°C   39%   32 W     0%     ← 空闲
  1      210 MHz   2100    75°C   38%   32 W     0%     ← 空闲
  2      210 MHz   2100    95°C  100%  156 W   100%     ← 满载却停在空闲时钟
  3      240 MHz   2100    89°C  100%  169 W   100%
```

**⇒ 满载卡停在 210 / 240 MHz（最大 2100），时钟掉 10 倍 —— 与步数掉 10 倍吻合。**
**⇒ 功耗只有 156 W，而上限 350 W ⇒ 不是功耗墙，是温度墙。**
**⇒ `clocks_event_reasons.active` = 0x68 (GPU 2) / 0x20 (GPU 3)，都含 SW Thermal Slowdown。**

**⇒ 而【空闲】的卡就有 75~77°C —— 这是机箱/机房散热的问题，不是"我们跑两条把它跑热了"。**
**⇒ 换到 GPU 0/1 也没用：它们空转就 75°C，一跑必然也冲上 90。**

## 25.3 影响：历史 run 是在正常散热下跑的

**⇒ 任何"新 run vs 历史 run"的对比，只要新 run 是被降频的，就全部无效。**
**⇒ 这也说明 §23.4 那个"load 93 vs load 2"的担心不是主要混淆 —— 主要混淆是【时钟】。**

## 25.4 处置

```

**⇒ 判断：只要机房温度不降，今晚跑不出可用的数据。**
**⇒ 下次开跑前，【先查 clocks.sm 和 temperature.gpu】，这是一条新的开跑前检查。**
