# 半池因果实验：判据先定（在看到数据之前写）

`pois200_cap{2,3,4}_hp` 三条跑的是**同一个模型、同一条 trace、同一张卡、同一份代码**，
唯一改动是 `--mem-fraction-static` 让 **KV 池减半**（101,432 → 约 50,716）。
它是论文里唯一能把「容量」单独拎出来的实验 —— 跨 trace 与跨卡都做不到。

## 预测（B 的可证伪形式，先写下来）

如果 host tier 的作用是**把可用容量乘 3**（host 池 = 2× device 池），
那么把 **device 池减半**、host tier 仍在，等效容量从 3× 变成 1.5×，
**复用塌陷的起点应随之左移**：设备侧兑现率开始明显下滑的 $\overline{R}_{\text{busy}}$
应从约 1.5 降到约 0.75–0.9 附近。

反过来，若半池的三条 cap 的兑现率曲线与全池的**几乎重合**（塌陷点不动），
则「容量决定塌陷点」这条就被自己的因果实验否证 —— 我们照原样写。

## 判据（可机械核对）

1. 与全池的同族臂逐点比 **兑现率**（`gen_reuse.py` 的同一套定义，上界仍取主 trace 的
   21,540,371）：半池 cap4 的兑现率应显著低于全池 cap4，且**下降幅度与池子缩小的幅度同量级**；
2. 池子守卫：`metadata.json` 的 `pool_tokens` 必须落在 **50,716 ± 20**，否则该 run 作废
   （与全池的 101,432 ± 20 同一条纪律）；
3. 时间量（τ、墙钟、SLO）只作参考 —— 它们同时受争用影响，而体积量不受；
   判定以兑现率为主。

## 检查清单（数据落地后逐条回答）

- [ ] 三条 run 的 `pool_tokens` 是否都在 50,716 ± 20？
- [ ] 半池 cap4 的兑现率 vs 全池 cap4 的兑现率差多少？方向对不对？
- [ ] 半池三条的兑现率-$\overline{R}$ 曲线，塌陷点相对全池左移了多少倍？
- [ ] 与「乘 3 变 1.5」的预测差多少？如果不符，是容量模型错还是 host tier 的作用不是乘法？

**注意**：这个实验落地前，正文 §IV 那句「A capacity-controlled version ... is queued」
不变；落地后无论结果正负都照实写。
