# 预注册：同卡背靠背的层级配对（`cap3_pd` / `cap3_ph`）

**写下时间**：2026-09-25 00:2x，**在任何数据落地之前**。
**已排队**：GPU 3 车道尾，`cap1_r2` 之后；两个 waiter 已挂
（`pois200_cap1_r2` → `lane_pair_dev.sh`；`pois200_cap3_pd` → `lane_pair_hc.sh`）。

## 为什么补这一对

论文 §III 的因果主张靠一个匹配对支撑：`cap3_fixed`（设备侧）与 `cap3_hc`（+HiCache）
在几乎相同的占用率（55.8% / 55.5%）和在跑数（1.53 / 1.51）下，兑现 **79.0%** 与 **91.3%**。

**但那一对是有混淆的**，论文自己也写着：两条跑在 **09-21 14:21 与 09-22 09:49**
（相隔 19.5 小时），而且**不是同一张卡**（gpu2 / gpu3）。§III 因此写
「two runs on two different days and two different GPUs, not a paired experiment」，
并把同卡的容量对照列为「还在排队」——排的是**半池**实验（改容量），
不是**改梯队**。论文的标题主张是「**梯队**决定并发代价」，所以直接测梯队的那条配对
反而没有同卡版本。

这一对把那个混淆去掉：**同一张卡（gpu3）、背靠背**，只改 HiCache 开不开这一个变量。
同 trace（`replay_pois200_l04.csv`）、同 memfrac（0.85）、同池子（101432±20）、同代码。

## 预注册判据（看结果前定死，与 §III 现有那条同口径）

兑现率 `realization = (prompt − dev_miss + host_hit) / 上界`，同 `gen_reuse.py`。

| 结果 | 结论 |
|---|---|
| 占用率与在跑数各差 <10%，且 `cap3_ph` 的兑现率比 `cap3_pd` **高 ≥10 个点** | 与现有那一对一致；匹配对主张得到**同卡**支持 |
| 差 **<5 个点**，或方向相反 | §III 的匹配对段落**必须改写**，把这一对作为反例写进去 |
| 中间（5–10 个点） | 照实报出差距，并说明它比现有那一对弱多少 |

**两种结果都照实写。** 这一对的价值不在于它支持我们，而在于它把一个
「我们自己承认没控制好的变量」控制住。

## 顺带会得到的东西

- `cap3_pd` 是设备侧 static=3 的**第二个**测量点，与 `cap3_fixed`（258.7 min）
  构成一个重复对，会给设备侧族的 run-to-run 散布再加一个样本；
- 两条都会进 `paper/data/*.csv`（`runs.csv` / `eviction.csv` / `reuse.csv` /
  `decomp.csv` / `occupancy.csv` / `repeat_spread.csv`），并在表 I 里各占一行；
- ⚠ 它们是**静态点**，会成为前沿的包络候选。若其中一条比现有锚点更快且更高，
  会按论文既有规矩顶掉锚点、移动所有人的 Δ —— 那要照实改，不能因为「不想动」而不动。
