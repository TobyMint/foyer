# 实验审计

## 证据优先级

```
原始日志 (results/<run>/metrics.csv, steps.jsonl, runner.out, summary.json)
  > 派生表 (paper/data/*.csv)
    > 论文正文与表格
```

三者不一致时，**以原始日志为准**，然后报告是哪一层错了。不要反过来改日志去迁就正文。

## 重点查什么

- **论文表格 vs 结果文件**：逐个数字对。表里每一行的 run 名在 `results/` 里都要找得到，
  且 steps / wall / SLO 对得上。
- **汇总表是否手算的**。手算的表是这个项目已经中过一次招的地方
  （`decomp.csv` 的一行 busy/idle 来自另一条 run）。汇总表应当由脚本生成并带断言。
- **口径一致性**：同一个量在不同地方是不是同一个定义。例如墙钟有
  `run_summary.py` 的定义（最后一个完成 − 最早一个提交），采样跨度是另一回事，
  两者天然差约 6 分钟，不能混用。
- **采样与解析**：CSV 解析时 ts 和 value 分两个 `try` 块，不要共用一个——
  一个字段解析失败会让两列错位（已犯过）。
- **完成度**：声称"只收跑满的 run"的表里，是否有 995/997/998 步的 run 混进去。
- **运行有效性**：KV pool 是否落在 `101,432 ± 20`；不满足的 run 必须作废。
- **单次运行 vs 多次运行**：只有一条 run 的配置不能拿来说 run-to-run spread。
- **对照公平性**：跨代 harness 的对照（如 25 档旧 harness vs 200 档新 harness）
  只能当方向，不能当量级，且必须在正文里标注。

## 报告方式

区分三类，不要混：

- **确认的 bug** —— 有证据，指明文件与行
- **可疑但未定论** —— 说明还需要什么才能定论
- **风格/次要问题** —— 单独一节，不要和上面混在一起

优先报高影响的有效性问题。每条给出**确切的文件路径**和复现命令。

## 不许做的事

- 不许编造实验或结果。
- 不许为了让表格自洽而悄悄改数字。
- 改动实验代码前先确认原始行为，尽可能保住可复现性；改了什么要写清楚。

## 硬件约束

卡 2/3 为常用；卡 0/1 仅 00:00–08:00 且确认空闲。别人占着卡就等，不要挤。
